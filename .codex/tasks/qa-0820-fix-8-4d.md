# 과제: 팀장 승격 시 부서를 함께 지정 (8-4d) + 점검표 3건 정정

앞선 진단(`.codex/out/code-author-0820-213031.md`)에서 5건 중 **코드 결함은 8-4d 하나**였고,
그마저 "기존 명세와 신규 요구가 충돌"이라 보류됐다. **사용자가 결정했다.**

## 사용자 결정

> **미배정 사원을 팀장으로 승격할 때, 부서를 같은 자리에서 함께 고르게 한다.**

두 번 저장하지 않아도 되고, **부서 없는 팀장이 생기지 않는다.**
기존 방어선(`DEPARTMENT_REQUIRED_FOR_LEADER`)은 **그대로 둔다** — 이건 마지막 그물이다.
바뀌는 것은 "막고 끝"이 아니라 "막는 대신 그 자리에서 해결하게" 하는 것이다.

버린 대안과 이유(사용자가 고르지 않은 것):
- 부서 없이 팀장 허용 → 결재선에 자리가 없어 권한만 뜨고 아무 일도 못 한다
- 지금처럼 막기만 함 → 관리자가 부서 배정 화면으로 갔다가 다시 돌아와야 한다

## 해야 할 일 — 8-4d

`AdminMembersPage`의 **인라인 역할 변경**에서 사원을 `TEAM_LEADER`로 바꾸려 할 때:

- 그 사원에게 **소속 부서가 있으면** 지금과 똑같이 동작한다 (확인 창 → 저장). 바꾸지 말 것
- **부서가 없으면** 확인 창에 **부서 선택**을 함께 띄운다. 부서를 고르지 않으면 진행 불가
- 확정 시 **부서 배정과 역할 변경이 함께** 반영돼야 한다.
  순서가 중요하다 — **부서를 먼저 배정하고 그다음 역할**이어야 서버 가드에 걸리지 않는다.
  둘 중 하나만 성공하고 끝나는 경우가 없게 할 것. 실패하면 **무엇이 반영됐고 무엇이 안 됐는지**
  사용자가 알 수 있어야 한다 (부서만 바뀐 채 끝나면 관리자는 왜 팀장이 안 됐는지 모른다)

**부서 선택지는 계층으로 보여줄 것.** 이미 `frontend/src/utils/departmentTree.js`에
`orderByHierarchy`·`departmentOptionLabel`이 있다 (2026-08-19에 같은 화면에서 쓰려고 만들었다).
새로 만들지 말고 그것을 쓴다.

**기존 팀장 교체 규칙을 건드리지 말 것** — 이미 `UserService.assignDepartmentLeader`가
"역할을 단일 출처로 삼아 승격 시 `leader_id`까지 채우고 기존 팀장은 사원으로 내린다"를
처리한다 (docs/01 §2-9(b)). 그 흐름을 다시 구현하지 마라.

### 백엔드를 바꿔야 하는가

**먼저 판단하라.** 지금 API로 "부서 배정 → 역할 변경"을 순서대로 두 번 부르면 되는지,
아니면 한 번에 처리하는 엔드포인트가 필요한지. **둘 중 하나를 고르고 근거를 써라.**

- 두 번 호출로 가면: 중간에 실패했을 때의 처리를 명확히 할 것
- 한 번에 가면: 기존 엔드포인트를 바꾸지 말고 새로 만들 것. URL은 kebab-case 리소스명만,
  응답은 `ResponseEntity<CommonResponse<?>>`, 실패는 `BusinessException(ErrorCode)`

## 해야 할 일 — `docs/13-QA-체크리스트.md` 정정 3건

세 항목이 **코드가 아니라 점검표가 낡았거나 부정확**한 것으로 판명됐다.
본문을 고치되 **항목 번호는 바꾸지 말 것** (코드 주석이 번호를 참조한다).

### 2-6 — 절차 자체를 수행할 수 없다
2026-08-19부터 본인 행의 퇴직 버튼이 `disabled`다. "눌러서 실패를 본다"가 불가능하다.
사용자 확인: **"버튼이 비활성이라 못 눌렀다."**
→ 절차를 **버튼이 비활성인지 확인 + API 직접 호출로 서버 가드 확인**으로 바꿔라.
기대는 `400 CANNOT_RETIRE_SELF`이고 재직 상태 유지. **마지막 관리자든 아니든 동일**하다는 것도
적을 것 (예전 기대값은 "마지막 관리자라서 막힌다"였는데 지금은 전면 금지다).

### 2-7 — 기대가 부정확하다
`RETIRED_USER`는 **401**이고 프론트 인터셉터가 로그인으로 보내는 것이 맞다. 그런데
`frontend/src/queryClient.js`의 **`staleTime`이 30초**라, 퇴직 직후 메뉴를 클릭하면
캐시가 신선해 **네트워크 요청이 아예 나가지 않는다.** 서버 가드가 걸릴 기회가 없다.
→ 기대를 **"다음 서버 호출에서 로그인 화면으로 밀려난다"**로 고치고,
절차에 **새로고침(F5) 또는 30초 후 재시도**를 넣어라. 왜 그런지(캐시 때문)도 한 줄 적을 것.
**이건 결함이 아니라 SPA의 정상 동작**이라는 점을 분명히 할 것.

### 8-4d — 기대값이 뒤집힌다
위 결정에 맞춰 절차와 기대를 다시 써라. 부서가 있는 사원과 없는 사원 **두 경우 모두**
확인하도록 나눌 것.

또한 1-3c 옆에 한 줄 덧붙여라 — **2026-08-19 이전에는 "설정 저장" 버튼을 따로 눌러야
반영된다는 것이 화면에 드러나지 않았다.** 이 항목이 실패했다면 그 때문일 수 있으므로
**미저장 배지가 사라진 것을 확인한 뒤** 대기 계정을 새로고침하라고 적을 것.

## 테스트

**vitest 검증을 함께 낼 것.** 최소한:
- 부서가 **있는** 사원의 팀장 승격은 지금과 같다 (부서 선택이 뜨지 않는다)
- 부서가 **없는** 사원은 부서를 고르기 전에는 진행할 수 없다
- 확정 시 **부서 배정이 역할 변경보다 먼저** 호출된다 (순서가 뒤집히면 서버 가드에 걸린다)
- 부서 선택지가 **계층 순서**로 나온다

`createMemoryRouter` + `RouterProvider`로 감쌀 것 — **앱은 데이터 라우터다.**
`AdminMembersPage.test.jsx`가 이미 있으니 그 모킹 방식을 따를 것.

백엔드를 바꾼다면 JUnit도 함께. 엔티티를 바꾸면 `db/schema.sql`과
`db/backfill-<날짜>-<주제>.sql` **둘 다** 내야 한다 (CLAUDE.md 배포 절).
