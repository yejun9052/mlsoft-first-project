# 1차 테스트 — 예외·경계값·동시성 감사

배포 전 마지막 점검이다. 자동 테스트 278건이 정상 경로를 덮고 있으니, 너는 **안 덮인 길**을 찾는다.

## 지금 상태

- 자동 테스트: 백엔드 278건 전부 통과 (`backend/src/test/`)
- **오늘(2026-08-12) 이메일 건별 알림이 들어갔다.** 비동기 + `AFTER_COMMIT` + 전용 스레드풀 +
  재시도 스케줄러라 **실패 모드가 가장 많은 신규 코드다. 여기를 최우선으로 봐라.**

## 특히 볼 것

### 이메일 (신규 — 실패 경로가 설계의 핵심이다)
- `EmailNotificationListener`는 `@Async` + `@TransactionalEventListener(AFTER_COMMIT)` +
  `@Transactional(REQUIRES_NEW)`가 한 메서드에 겹쳐 있다. **이 조합이 실제로 의도대로 도는가.**
  커밋 후 다른 스레드에서 새 트랜잭션이 열리는 게 맞는가, 저장이 사라지는 경로는 없는가.
- 리스너가 수신자 여럿을 **한 트랜잭션에서** 돈다. 3번째 수신자에서 DB 예외가 나면
  앞의 2건 이력은 어떻게 되는가.
- `EmailAsyncConfig`의 큐(100)가 가득 차면 작업이 버려진다. **그때 `email_history`에 아무 흔적이
  남지 않는다** — 이게 허용 가능한 설계인지, 아니면 조용한 유실인지 판정하라.
- `EmailRetryScheduler`가 15분마다 돈다. **이전 실행이 안 끝났는데 다음이 시작되면** 같은 건을
  두 번 보내는가. `@Scheduled`는 기본이 단일 스레드인데 이 프로젝트에 다른 `@Scheduled`가 있다 —
  서로 막는가.
- SMTP가 **응답 없이 매달리면**(타임아웃 미설정) 스레드풀 2~4개가 전부 잠긴다. 타임아웃이 있는가.
- `markFailed`가 `retry_count`를 올린다. **재시도 상한에 도달한 건**이 계속 조회 대상에 남는가.

### 스케줄러 (docs/09)
- 서버가 3일 꺼졌다 켜진 경우, 같은 날 두 번 실행된 경우, 사원 1명이 실패한 경우.
- 리셋 → 월차 → 생일 순서 의존이 깨지는 입력이 있는가 (생일 == 기산일, 1주년 당일, 2/29 생일,
  1/31 입사자의 월차 지급일, 윤년).
- 이메일 발행이 스케줄러 안에 들어갔다(`BirthdayLeaveGrantService`). **사원 1명 = 1트랜잭션**
  경계가 이메일 때문에 깨지지 않는가.

### 연차 상태 전이
- 같은 신청에 대해 취소와 승인이 동시에 들어오면. `updateStatusIfCurrent`(CAS)가 지는 쪽을
  제대로 막는가. 막은 뒤 **이미 발행된 이메일 이벤트**는 어떻게 되는가.
- 소급취소 승인 중 서버가 죽으면 `use_days`가 어느 상태로 남는가.

### 경계값
- `BigDecimal` 비교가 `compareTo`인지 `equals`인지 (scale 0.5 vs 0.50).
- 날짜: KST 판정, 월말, 윤년, 과거·미래 상한.
- 문자열 길이 상한(사유 255자 경계는 이미 고쳐졌다 — 다른 필드는?).
- 목록 조회의 크기 상한이 없는 곳.

## 읽어야 할 것

`backend/src/main/java/com/mlsoft/backend/domain/{email,leave,welfare,schedule}/` 전체와
`backend/src/test/` — **테스트를 먼저 읽어 뭐가 덮였는지 확인한 뒤** 안 덮인 것만 보고하라.
기준 문서는 `docs/09`(스케줄러 설계·검산), `docs/02`(DB), `CLAUDE.md`(불변식 규칙).

## 산출물

역할 지시서의 형식을 그대로 따른다. **"자동 테스트가 왜 못 잡는가"를 항목마다 반드시 쓸 것** —
그게 없으면 이미 덮인 것을 다시 적은 것일 가능성이 높다.
