# 과제: 1차 수동 점검에서 실패한 5건 — 원인 추적과 수정

사용자가 브라우저로 95항목을 돌려 **58 통과 / 5 실패 / 32 미확인**이 나왔다.
실패 5건의 **원인을 코드에서 찾아내고 고쳐라.** 증상 설명은 아래가 전부다 —
사용자는 "무엇이 어떻게 달랐는지"를 적지 않았다. 그러니 **기대와 실제가 갈릴 수 있는
지점을 코드에서 직접 찾아야 한다.**

## 가장 중요한 지시

**추측으로 고치지 말 것.** 각 건마다 다음을 먼저 확정하고 결정 표에 써라.

1. 그 동작이 지나가는 **경로 전체** (화면 → 훅 → api 함수 → 컨트롤러 → 서비스 → 리포지토리)
2. 기대대로 동작하게 만드는 **방어선이 실제로 어디에 있는가**
3. 그 방어선이 **왜 안 걸렸는가** — 없어서인지, 다른 경로가 쓰여서인지,
   걸렸는데 화면이 결과를 안 보여줘서인지

**세 번째가 핵심이다.** 아래 두 건은 방어선이 코드에 분명히 있는데도 실패로 보고됐다:
- `UserService`(약 147행)에 `DEPARTMENT_REQUIRED_FOR_LEADER`가 있는데 8-4d가 실패했다
- `AuthService`가 `PolicyConfigKey.ONBOARDING_REVISION_ENABLED`를 읽는데 1-3c가 실패했다

즉 **서버는 맞는데 화면이 다르게 굴거나, 화면이 다른 경로를 타고 있을** 가능성이 높다.
서버 코드만 보고 "이미 되어 있다"고 결론 내지 말 것. **화면부터 역순으로 따라가라.**

## 실패 5건

### 1-3c — 온보딩 "입사일 수정 허용"을 꺼도 화면이 안 따라온다
- 절차: 관리자 화면에서 연차 정책 → `승인 대기 중 입사일 수정 허용`을 **끄고**,
  승인 대기 상태인 계정을 새로고침
- 기대: "입사일 수정" 버튼이 **사라지고** 관리자에게 반려를 요청하라는 안내가 보인다.
  다시 켜면 버튼이 돌아온다
- 확인할 것: 관리자 화면에서 그 설정이 **저장은 되는가**(2026-08-19에 "설정 저장" 버튼을
  따로 눌러야 반영된다는 것이 밝혀졌다 — 사용자가 저장을 눌렀다고 가정하되,
  저장 후 값이 실제로 반영되는 경로를 확인하라).
  `GET /api/auth/me`의 `onboardingRevisable` 판정과 `OnboardingPage.jsx`의 렌더 조건을 대조할 것

### 1-6 — 온보딩 승인 대기 탭의 배지가 안 줄어든다
- 절차: 온보딩 건을 승인 또는 반려한 뒤 관리자 화면의 **승인 대기 탭 배지 숫자**를 본다
- 기대: 방금 처리한 건이 **목록과 배지 양쪽에서** 사라져 있다
- 확인할 것: 승인/반려 뮤테이션이 무효화하는 **쿼리 키**와 배지가 구독하는 쿼리 키가
  같은가. 접두사 규칙(`['leaves', 서브리소스, ...]`)이 어긋나면 목록만 갱신되고 배지가 남는다.
  **배지가 아예 없는 것인지 낡은 것인지**도 구분해서 쓸 것

### 2-6 — 마지막 관리자가 본인 퇴직을 시도했을 때
- 절차: 관리자가 **1명뿐인** 상태에서 본인 퇴직 처리를 시도
- 기대: 실패하고 재직 상태가 유지된다
- 확인할 것: 2026-08-19에 `CANNOT_RETIRE_SELF`(본인 퇴직 전면 금지)가 들어갔고,
  **구성원 관리 표의 퇴직 버튼이 본인 행에서 `disabled`가 됐다.**
  버튼이 비활성이면 사용자는 "시도" 자체를 못 한다 — 이것이 실패로 보고된 원인일 수 있다.
  기대 결과("실패하고 재직 상태 유지")는 충족되지만 **점검 절차를 수행할 수 없는 상태**다.
  이 경우 **코드가 아니라 점검 항목이 낡은 것**이다. 그렇게 판단되면 코드를 고치지 말고
  **그렇게 보고하라** (docs/13의 해당 항목을 어떻게 고쳐야 하는지도 함께)

### 2-7 — 퇴직 처리된 계정이 이미 열려 있던 탭에서 안 막힌다
- 절차: 관리자가 B 계정을 퇴직 처리 → **B가 이미 로그인해 둔 탭**에서 아무 메뉴나 클릭
- 기대: 막힌다. 로그아웃만 된다. JWT는 발급 후 상태 변화를 못 담으므로
  `OnboardingCheckInterceptor`가 매 요청 DB를 본다
- 확인할 것: 인터셉터가 퇴직자를 막는 것은 맞는지, **막은 뒤 프론트가 무엇을 하는지**.
  403이 그냥 토스트만 띄우고 화면에 남아 있으면 사용자 눈에는 "안 막혔다"로 보인다.
  `api/index.js`의 인터셉터는 401만 로그인으로 보낸다 — **퇴직자는 401인가 403인가?**
  이 차이가 이 항목의 핵심일 가능성이 크다

### 8-4d — 부서 미배정 사원을 팀장으로 승격
- 절차: 구성원 관리에서 부서가 "미배정"인 사원의 **역할을 팀장으로** 바꾼다
- 점검표의 기대: `팀장으로 지정하려면 소속 부서를 먼저 배정해야 합니다` 오류
- ⚠️ **이 건은 고치지 말고 진단만 하라.** 사용자가 별도로
  "미배정 부서 팀장 배정 가능"을 요구사항으로 올려 둬서 **기대값 자체가 바뀔 수 있다.**
- 확인할 것: 구성원 관리 표의 **인라인 역할 변경**이 타는 경로가
  `UserService`의 그 가드를 지나는가. 2026-08-16에 표에서 부서·역할을 바로 고치게 바꾸면서
  경로가 갈라졌을 수 있다. **부서 변경과 역할 변경의 순서**도 볼 것 —
  둘을 각각 저장하면 "부서를 먼저 배정"이 성립하지 않는 순간이 생긴다

## 먼저 읽을 것

- `frontend/src/pages/AdminMembersPage.jsx`, `AdminPolicyPage.jsx`, `OnboardingPage.jsx`
- `frontend/src/api/index.js` — 응답 인터셉터. **401과 403을 어떻게 다르게 다루는지**
- `frontend/src/hooks/useUsers.js`, `useAuth.js`, `usePolicies.js` — 무효화 쿼리 키
- `backend/.../domain/user/service/UserService.java`
- `backend/.../domain/auth/service/AuthService.java`
- `backend/.../security/` 와 `OnboardingCheckInterceptor`
- `backend/.../domain/policy/` 전체 (`PolicyConfigKey`, `PolicyConfigReader`)
- `CLAUDE.md` — 특히 "인증 흐름"·"시스템 설정"·"프론트엔드 데이터 흐름"
- `docs/13-QA-체크리스트.md` — 항목 원문

## 산출물

역할 지시서 형식. 다만 **결정 표 앞에 진단 표를 먼저** 낼 것:

```
## 진단
| 항목 | 실제 경로 | 방어선 위치 | 왜 어긋났나 | 고칠 곳 (코드 / 점검표 / 미정) |
```

"고칠 곳"이 **점검표**인 건은 코드를 내지 말고 docs/13을 어떻게 바꿔야 하는지 쓴다.
**미정**인 건(8-4d)은 사용자 결정이 필요한 이유와 선택지별 영향을 쓴다.

코드를 내는 건에는 **vitest 또는 JUnit 검증을 함께** 낼 것.
이 저장소는 테스트가 명세다. 특히 2-7처럼 **화면 동작**이 원인이면 그 동작을 고정하는
프론트 테스트가 있어야 같은 일이 다시 안 생긴다.

프론트 테스트는 `createMemoryRouter` + `RouterProvider`로 감쌀 것 —
**앱은 2026-08-19부터 데이터 라우터다.** `BrowserRouter`로 쓰지 말 것.

`## 반영 순서`에 확인 명령 포함:
```
cd backend && .\gradlew.bat test    # 현재 346건
cd frontend && npm test             # 현재 184건
npm run lint
```
