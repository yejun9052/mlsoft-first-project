# 1차 테스트 — 요구사항 적합성 + 쿼리 감사

두 가지를 본다. **①** 만든 것이 요구사항과 맞는가, **②** 조회 경로가 감당 가능한가.

## ① 요구사항 적합성 (우선)

`docs/01-요구사항-기획.md`를 처음부터 끝까지 읽고, **각 요구사항이 코드에 실제로 있는지** 대조하라.

산출은 표 하나다:

| 요구사항 (docs/01 위치) | 구현 위치 (`파일:줄`) | 판정 |
|---|---|---|

판정은 넷 중 하나:
- **일치** — 요구대로 동작한다
- **어긋남** — 구현이 있는데 요구와 다르게 동작한다 ← **이게 핵심 산출물이다**
- **미구현** — 없다 (알려진 미구현은 아래 목록 참조, 새로 발견한 것만 표시)
- **문서가 낡음** — 코드가 맞고 문서가 안 따라온 경우

**"어긋남"과 "문서가 낡음"을 구분하는 것이 이 감사의 목적이다.** 둘 다 표에서는 비슷해 보이지만
전자는 코드를 고쳐야 하고 후자는 문서를 고쳐야 한다. 어느 쪽이 옳은지 판단하고 근거를 써라.

### 알려진 미구현 (다시 보고하지 마라)
- 관리자 일괄 발송 (docs/01 §2-8) — 이메일 2단계
- Google Workspace `hd` claim 검증 (docs/08 R-2)
- 설정 2키 `reminder_list_days`·`reminder_auto_cycle`의 `PENDING_FEATURE` 상태
- 퇴직자 3년 후 데이터 파기 절차 (docs/08 Y-4)
- Flyway (docs/08 Y-6 — 배포 단계로 연기 결정됨)

### 특히 확인할 것
- **권한 체계**: EMPLOYEE / TEAM_LEADER / SYSTEM_ADMIN (+RETIRED)가 요구대로 갈리는가.
  docs/01의 "누가 무엇을 할 수 있다"와 실제 `@PreAuthorize` + 서비스 검증이 일치하는가.
- **승인 구조**: primary + sub 2단이 요구대로인가. 팀장 퇴직 시 결재 이관(갭분석 B-4).
- **월차 적립**(근로기준법 §60, 갭분석 B-1) — 1년 미만 매월 1일, 최대 11일, 1주년에 중단.
- **미사용 연차 소멸**(갭분석 B-2) — 이월 없음, `leave_reset_history` 기록.
- **오늘 들어간 이메일**이 docs/01 §2-3·2-4(신청/승인 시 수신자)와 일치하는가.

## ② 쿼리 감사 (후순위)

역할 지시서의 기준으로 보되, **오늘 추가된 경로를 우선**한다:
- `EmailNotificationPublisher`가 승인마다 `findByRoleAndIsActiveTrue(SYSTEM_ADMIN)`를 호출한다.
  이게 **업무 트랜잭션 안**에서 도는데, 승인 요청마다 추가 쿼리가 맞는가.
- 같은 publisher가 `leave.getPrimaryApprover()`·`getSubApprover()`·`getDates()`를 읽는다.
  LAZY라면 신청·승인마다 쿼리가 몇 개 늘어나는가.
- `EmailHistoryRepository.findTop100...`이 `idx_email_history_retry (status, retry_count, id)`의
  왼쪽 접두를 쓰는가.

이미 `docs/10 D-2`로 처리된 N+1은 다시 보고하지 마라. **오늘 새로 생긴 것만.**
