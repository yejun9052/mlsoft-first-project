# 작업: 관리자가 설정할 수 있어야 하는 값 전수 조사

사용자 요구: **"상한을 관리자가 설정하게 해줘. 그런 설정들 모두 관리자가 설정할 수 있게."**

지금은 `leave_policy_config` 테이블에 문자열 key-value 3개만 있고(`advance_leave_enabled`,
`reminder_list_days`, `reminder_auto_cycle`), 나머지 정책값은 코드에 하드코딩돼 있다.

## 1. 하드코딩된 정책값 인벤토리

`backend/src/main`(+ `frontend/src`) 전체에서 **운영자가 바꾸고 싶어질 만한 값**을 찾아라.
단순 상수가 아니라 "정책"인 것만 — 배열 크기나 버퍼 길이 같은 구현 상수는 제외한다.

각 항목을 표로:

| # | 파일:줄 | 현재 값 | 무엇을 정하는 값인가 | 설정화 판정 | 근거 문서 |

"설정화 판정"은 셋 중 하나로만:
- `필요` — 회사 정책에 따라 달라질 값
- `불필요` — 법정 기준이거나 코드 구조상 고정돼야 하는 값
- `보류` — 해당 기능이 아직 구현되지 않아 판단 유보

특히 다음을 확인해라 (있으면 표에 포함, 없으면 "미발견"이라고 써라):
- 당겨쓰기 상한 (docs/02 메모 11, docs/09 §3의 `advance_max_days` = 5) — **코드에 있는가?**
- 보너스 이월 여부 (docs/02 메모 10, `bonus_carry_over_enabled`)
- 신청 1건당 날짜 개수 상한 (리뷰 I-3이 `LeaveCreateRequest`에 `@Size`가 없다고 지적)
- 월차 적립 상한 11일 (갭분석 B-1)
- 연차 법정 상한 25일 / `MIN(15 + (년차−1)/2, 25)` (`DataInitializer`)
- 주말·과거 날짜 거부 규칙 (`LeaveService.validateDates`)
- 데이터 보존 기간 3년 (docs/01 2-9)
- 반차 단가 0.5 (`LeaveType`)
- 소급 취소 판정 기준(과거 날짜 포함 여부)

## 2. 현재 설정 읽기 경로의 파싱 실패 위험

`leave_policy_config`의 값은 문자열이고 `PUT /api/admin/configs`는 `@NotBlank`만 검증한다.
**즉 관리자가 아무 문자열이나 저장할 수 있다.**

`src/main`에서 config 값을 읽어 파싱하는 코드를 전부 찾고, 각각 **잘못된 값이 저장됐을 때
어디서 어떻게 터지는지** 판정해라. 표로:

| # | 읽는 위치 파일:줄 | 키 | 파싱 방식 | 잘못된 값 저장 시 결과 | 누가 피해를 보는가 |

"누가 피해를 보는가"가 중요하다 — 관리자가 잘못 넣었는데 **사원의 연차 신청이 500으로 실패**하면
설정 시점에 막아야 한다는 근거가 된다.

## 3. 프론트엔드 메타데이터 하드코딩 확인

`frontend/src/pages/AdminPolicyPage.jsx`의 `CONFIG_META`를 읽어라.

1. 백엔드에 새 설정 키를 추가하고 프론트를 안 고치면 **관리자 화면에 그 설정이 보이는가?**
   `.filter(...)` 부분을 근거로 판정해라.
2. `ConfigControl`이 지원하는 타입은 무엇인가. 새 타입(예: 소수점 있는 일수)이 필요한가.

## 4. 답할 것

- 위 3개 표
- **설정 카탈로그를 서버가 정의하고 메타데이터까지 내려주는 구조로 바꿀 때, 지금 코드에서
  깨지는 곳**이 어디인가 (`GET /api/admin/configs` 응답 형태가 바뀐다)
- 기존 테스트 중 영향받는 것 (`LeavePolicyConfigServiceTest` 등) 파일:줄로

추측 금지. 확인한 파일:줄만 근거로 쓰고, 확인 못 한 건 "미확인"이라고 명시해라.
