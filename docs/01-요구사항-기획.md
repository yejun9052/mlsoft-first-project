# 01. 요구사항 & 기획

> 노션 기획 문서(2026-07 작성)를 정리한 것. MLsoft 휴가관리 시스템 재설계·재제작 기준 문서.

## 회고 (이전 프로젝트에서 얻은 교훈)

1. **AI 의존도가 너무 심했다** — 1달이라는 짧은 기간 탓에 AI에 의존. 이번엔 설계를 직접 주도한다.
2. **기능·DB 설계를 직접 하지 않았던 점이 후회됨** — 이번 프로젝트는 설계(요구사항/DB/API)를 먼저 직접 작성하고 구현에 들어간다.
3. 만들면서 "이런 부분이 있었으면" 했던 것들을 이번 설계에 반영 (이메일 알림, 퇴직자 보존, 서브 승인자 등).

> **작업 원칙**: AI는 보조 도구로 사용하되, 설계 결정과 세부 구현 이해는 본인이 주도한다.

## 요구사항 분석 (14개)

1. 로그인: OAuth 2.0, **@mlsoft.com만 허용**, 첫 로그인 시 자동 가입
2. 캘린더에서 공휴일·팀원 연차 조회
3. 연차 신청 시 사유 필수 (연차/반차 선택 가능)
4. 자신의 팀 정보 조회
5. 복리후생 페이지에서 연차 추가 신청
6. 총 연차 / 사용 개수 / 잔여 연차 조회
7. 신청 시 기본 승인자는 팀장, **서브 승인자 선택 가능**
8. 취소도 동일한 승인 구조
9. 신청 시 당사자·담당자에게 **메일 발송**
10. 승인 시 신청자·담당자·총관리자에게 메일 발송
11. 생일 반차 자동 추가 시 총관리자에게 메일
12. 30/60/90일·분기 단위로 기산일 임박 + 연차 잔여 사원에게 일괄 메일
13. 권한 체계: `SYSTEM_ADMIN`(총관리자) / `TEAM_LEADER`(팀장) / `EMPLOYEE`(사원)
14. 퇴직 사원 데이터 **3년 이상 보존** (근로기준법)

## 기능 명세

### 2-1 Google OAuth 2.0 로그인
- @mlsoft.com 계정만 로그인 가능, 첫 로그인 시 자동 가입 (권한 EMPLOYEE, 부서 미배정)
- **도메인 검증 3중 방어 (검증 R-2 — 명세만 확정, ⏳ 표시는 회사 계정 확보 후 적용)**
  - ① ⏳ Google Cloud OAuth 앱을 "내부(Internal)"로 설정 — **회사 Workspace 관리자 계정 확보 후 적용** (선결 조건, 그전까지 테스트 클라이언트 사용)
  - ② 서버에서 ID 토큰 `hd == "mlsoft.com"` + `email_verified == true` 검증 — 개발 중엔 이메일 도메인 검사로 대체하고, 운영 전환 시 hd 검증 활성화
  - ③ 퇴직자(is_active=false)는 OAuth 인증에 성공해도 토큰 발급 거부 → `/login?error=retired`
- **최초 관리자 부트스트랩 (검증 R-3)**: 환경변수 `ADMIN_EMAILS`에 지정된 이메일은 첫 로그인(자동 가입) 시 SYSTEM_ADMIN 부여 — 전원 EMPLOYEE로 시작하는 닭-달걀 문제 해결
- 최초 로그인 시 온보딩 페이지에서 **생일/입사일을 필수 입력하고 직급은 선택 입력** → 완료 후 메인 이동
- 직급·직책은 회사별 체계와 개인 사정에 따라 달라 선택 정보로 두며, 온보딩을 무겁게 만들지 않고 나중에 **내 정보**에서 언제든 바꿀 수 있게 한다.
- **연차(base_days)는 유저가 입력하지 않는다** — 입력된 입사일 기준으로 연차 정책이 자동 계산 (위조 방지, 갭분석 C-1 반영)
- **온보딩 미완료 유저 (검증 Y-2)**: `onboarding_status != COMPLETED`이면 온보딩 페이지 외 접근 차단, 연차 신청·스케줄러 대상에서 제외
  - 판별 기준을 `hire_date IS NULL`에서 바꾼 것은 **리뷰 S-1** 때문이다 — 자가 신고 입사일이 자동 승인 기간 밖이면 승인 대기 상태에서도 `hire_date`가 채워져 옛 기준이 미확정 사원을 통과시킨다
- 결과: JWT 토큰 발급 — 쿠키는 `HttpOnly + Secure + SameSite=Lax`, 운영은 HTTPS 필수. 401 응답 시 프론트는 로그인 페이지로 강제 리다이렉트 (검증 Y-5)

### 2-2 역할별 권한
- `SYSTEM_ADMIN`: 모든 권한 + 관리자 화면
- `TEAM_LEADER`: 팀원 연차 관리 + 자신을 서브 승인자로 지정한 신청 관리
- `EMPLOYEE`: 연차·반차·복리후생 신청/조회
- 권한 밖 페이지 접근 차단 (라우트 가드)

### 2-3 연차·반차 신청
- `ANNUAL`(1.0) / `HALF_AM` / `HALF_PM`(0.5) 선택, 날짜는 리스트로 저장
- 캘린더 날짜칸 클릭으로 선택
- 사유 필수
- **승인자 구조 (갭분석 B-3 반영)**
  - **기본 승인자(primary)는 가까운 곳부터 위로 올라가며 정한다** (2026-08-16 개정 — 아래 §2-3(a) 참조)
  - **서브 승인자(sub) = 신청자가 재직 중(is_active=true)인 TEAM_LEADER·SYSTEM_ADMIN 중에서 직접 선택** (선택 사항 — 일반 EMPLOYEE는 후보 제외, 권한표와 일치)
  - 처리 방식은 **병렬 선착순**: primary/sub 중 먼저 처리한 1명의 결정으로 종료 (순차 결재 아님 — 팀장 부재 대비 목적)

#### 2-3(a) 기본 승인자 결정 규칙 (2026-08-16 확정)

구현: `ApproverResolver.resolvePrimary` — **연차·복리후생이 이 한 메서드를 함께 쓴다.**

```
⓪ 신청자가 SYSTEM_ADMIN       → 본인                ← 2026-08-19 추가
① 소속 부서의 팀장            자격 O → 확정
② 상위 부서(parent_id)의 팀장  자격 O → 확정      ← 2026-08-16 추가
   └ 그 위에 또 상위가 있으면 계속 (현재 계층은 2단계라 실제로는 한 번만 올라간다)
③ SYSTEM_ADMIN 중 id가 가장 작은 계정 (신청자 본인 제외)
④ 그마저 없으면 INVALID_APPROVER
```

**⓪을 넣은 이유 (2026-08-19)**: 총관리자 위에는 결재선이 없다. 2026-08-17에 "본인 신청은
본인이 결재할 수 없다"를 총관리자까지 적용했더니, ③이 **본인을 제외**하므로 총관리자가
한 명뿐인 조직에서는 승인자를 찾지 못해 **연차 신청 자체가 `INVALID_APPROVER`로 막혔다.**
①에서 부서 팀장이 잡히는 경우도 문제였다 — 부하가 상급자의 연차를 심사하는 모양이 된다.

**"마지막 수단"이 아니라 맨 앞에 둔 이유**: 부서에 팀장이 있느냐 없느냐에 따라 총관리자의
결재선이 달라지면 "왜 이 사람이 승인자인지"를 설명할 수 없다. 총관리자의 결재선은 항상 본인이다.

**푸는 것은 "자기 것"뿐이다** — `validateApprover`의 primary/sub 검사는 그대로다.
총관리자라도 **자기가 승인자로 지정되지 않은 남의 건**은 결재하지 못한다.

**"자격"의 정의는 한 곳뿐이다** (`isEligibleFor`) — 네 조건을 모두 만족해야 한다:
재직 중 · 역할이 TEAM_LEADER 또는 SYSTEM_ADMIN · 온보딩 완료(`COMPLETED`) · **신청자 본인이 아닐 것**.
단계마다 기준이 다르면 "왜 이 사람이 승인자인지" 설명할 수 없게 된다. 셀프 결재 배제는
①②③ 모든 단계에 적용된다 — 본부장이 자기 신청을 올리면 ②를 건너뛰고 ③으로 간다.
**단 신청자가 SYSTEM_ADMIN이면 ⓪에서 끝나 이 탐색에 들어오지 않는다.**

**②를 넣은 이유**: 예전에는 자기 부서 팀장이 없으면 곧바로 ③으로 갔다. 그래서
`개발본부(팀장 있음) → 개발 1팀(공석)` 구조에서 개발 1팀 신청이 **바로 위 본부장을 건너뛰고**
총관리자에게 갔다. 조직도상 결재선이 있는데 시스템만 몰랐던 것이다.

**팀장이 지정돼 있는데 자격이 없으면** (강등·퇴직·온보딩 미완료) 조용히 넘어가지 않고
`WARN [승인자] 부서 팀장이 결재 불가 상태라 상위 부서로 올라간다`를 남긴 뒤 위로 올라간다.
로그가 없으면 관리자는 그 부서 결재선이 비어 있다는 것을 영원히 모른다.
②로 결정됐을 때도 `INFO [승인자] 하위 부서 팀장이 없어 상위 부서 팀장으로 결정`이 남는다 —
나중에 "왜 이 사람이 승인자였나"를 설명할 수 있어야 한다.

**부서 계층에 순환이 있으면** (A→B→A, DB를 직접 고쳐야 만들 수 있다) 방문한 부서를 기억해
탐색을 멈추고 ③으로 간다. 무한 루프에 빠지면 신청 한 건이 스레드를 물고 늘어진다.

**연동 규칙**: `department.leader_id`는 `users.role`을 따라온다 — 구성원 관리에서 역할을
`TEAM_LEADER`로 올리면 그 사람의 소속 부서 팀장 자리까지 함께 채워진다. 자세한 것은 §2-9(b).
- **동시성 방지 (검증 R-5)**: users 낙관적 락(@Version)으로 동시 신청에 의한 잔여 초과 차단, 승인·취소 처리는 status 조건부 갱신(`WHERE status='PENDING'`)으로 이중 처리 차단 (실패 시 ALREADY_PROCESSED)
- **잔여 검증 (갭분석 A-3 반영)**: 잔여 < 신청 일수면 거부가 기본. 단 시스템 설정 `advance_leave_enabled=true`면 당겨쓰기로 접수 (`users.advance_days` 누적, 다음 기산일에 정산)
- **기산일을 넘어가는 연차 신청은 다음 기산일에서 계산**
- 신청 시 당사자 + primary·sub 승인자에게 이메일
- 결과: `leave_requests`에 PENDING 저장 (**선차감**: use_days에 즉시 반영), 승인 권한자에게 요청 표시

### 2-3(b) 연차·반차 취소 (갭분석 A-2 반영)
- PENDING 상태: 날짜 무관 즉시 CANCELLED + 선차감분 복구
- APPROVED 상태:
  - **미래 날짜만 포함** → 즉시 CANCELLED + use_days 복구
  - **과거 날짜 포함(소급 취소)** → CANCEL_PENDING 전환, 승인자 승인 필요 (승인 시 CANCELLED+복구 / 거부 시 APPROVED 복원)
- 취소 사유는 `cancel_reason`에 저장, 처리 이력은 action_history에 기록

### 2-4 복리후생 신청·안내
- 기본 복리후생 안내 (페이지네이션)
- 안내 객체(행) 클릭 → 신청 폼에 자동 입력
- 승인 구조·이메일은 연차와 동일, `welfare_requests`에 저장

### 2-5 잔여 연차 확인 (연차 Status)
- 총 연차 / 사용 개수 / 잔여(총-사용) / 다음 기산일 차감 예정 표시
- 기산일은 **입사일 기준**
- **대기 중 연차도 use_days에 선차감, 거부되면 복구** ← 이전 프로젝트(승인 시 차감)와 다른 정책

### 2-5(b) 캘린더
- 공휴일 + 팀원 일정 + 전체 연차 표시, 월 이동 가능
- 날짜칸 클릭으로 연차 신청
- **사유 마스킹 (검증 Y-4, 🔴 확정)**: 타인의 연차는 이름·기간·종류만 표시. 사유는 **본인·해당 건 승인자·SYSTEM_ADMIN만 조회 가능** — 병가·경조 사유는 민감 개인정보

### 2-6 생일 반차
- 매일 자정 스케줄러가 생일인 유저 검색 → 0.5일 지급
- 지급 시 담당자와 당사자에게 메일

### 2-7 기산일 스케줄러
- 매일 자정 실행. **대상 검색은 "오늘이 입사일"이 아니라 `last_reset_date + 1년 <= 오늘`인 유저 (검증 Y-1)** — 자정에 서버가 꺼져 있던 날이 있어도 재기동 후 첫 실행에서 자동 소급(catch-up). 정책에 따라 총 연차 재지급
- 월차 적립·생일 반차도 동일 원리(마지막 지급 기록 기준)로 미실행분 자동 복구
- 기산일 기준 미래에 사용한 연차 → 사용 연차에 포함해서 계산
- **당겨쓴 연차(advance_days) 정산**: 새 base_days에서 차감 후 advance_days 초기화 (갭분석 A-1 반영)
- 기산일 이전 사용 신청은 새 총 연차/사용 연차에 영향 없음
- **1년 미만 신입 월차 적립 (갭분석 B-1 반영, 근로기준법 §60)**: 입사 1년 미만 유저는 매월 입사일(같은 날)마다 1일 적립, 최대 11일. 1주년 도래 시 월차 적립 중단 + 정책 연차로 전환
- **미사용 연차 소멸 (갭분석 B-2 반영)**: 기산일 리셋 시 남은 연차는 이월 없이 소멸. 리셋 전 상태(prev_base/prev_used/expired_days)는 `leave_reset_history`에 기록 — 디자인의 "소멸 예정 N일" 표시는 다음 기산일까지 남은 잔여를 의미

### 2-8 이메일 일괄 전송 (관리자)
- 기산일 임박 + 연차 잔여 사원 리스트 조회 (며칠 전부터 띄울지 설정 가능)
- 관리자가 메일 양식 직접 작성, 체크박스로 일부만 선택 발송 가능
- 30/60/90일·분기 기준 자동 발송 설정 가능
- 발송 내역 보존 (`email_history`)

**온보딩 승인 알림 (2026-09-05 확정)** — 입사일 자가 신고가 자동 승인 범위 밖이면 승인 대기가 되는데, 지금은 총관리자가 화면에 들어와야만 그 사실을 안다. 대기 발생은 재직 SYSTEM_ADMIN 전원에게, 승인·반려 결과는 대상 사원 본인에게 메일로 알린다 (설계: `docs/설계-초안/연차-소진-안내-메일-설계-2026-08-28.md` §10)

**이메일 공통 처리 규칙 (검증 R-4 — 신청/승인/생일/리마인더 등 모든 발송에 적용)**
- 발송은 업무 트랜잭션과 분리: 커밋 후 비동기 발송 (`@Async` + `@TransactionalEventListener(AFTER_COMMIT)`) — **메일 서버 장애가 승인·신청 처리를 실패시키지 않는다**
- 모든 발송은 `email_history`에 기록: status `PENDING → SENT/FAILED`, 실패 시 error_message
- FAILED 건은 스케줄러 재시도(최대 3회) + 관리자 화면 수동 재발송
- 발송 계정: **개인 Gmail 발신 전용 계정 + 앱 비밀번호** (2026-08-12 확정). Workspace 계정을 못 받아 대체한 방식이고,
  회사 계정을 받으면 **환경변수만 교체**하면 된다 — 코드는 안 바뀐다.
  - 앱 비밀번호는 **2단계 인증을 켜야** 발급된다. 계정 로그인 비밀번호로는 인증되지 않는다(2022-05 차단)
  - **From 주소를 바꿀 수 없다** — 계정 주소로 강제되고 표시 이름(`MLsoft 연차관리`)만 지정 가능.
    회신 주소는 `MAIL_REPLY_TO`(Reply-To 헤더)로만 분리한다
  - **한도: 개인 Gmail 일 500건** / Workspace 일 2,000건. 건별 알림 + 승인마다 SYSTEM_ADMIN 참조가 곱해지므로
    일괄 리마인더(§2-8)를 붙일 때 이 한도를 먼저 계산할 것

### 2-9 퇴직자 데이터 보존
- 퇴직 상태 변경은 SYSTEM_ADMIN만 가능
- 3년 이상 보존 후 처분 권한은 SYSTEM_ADMIN에게
- 퇴직자 별도 목록 조회
- **팀장 퇴직 시 결재 이관 (갭분석 B-4 반영)**: 해당 부서 `leader_id` 해제(null) → 후임 지정 전까지 기본 승인자는 **상위 부서 팀장 → 없으면 SYSTEM_ADMIN**으로 이어진다(§2-3(a)). 퇴직 팀장 앞으로 걸려 있던 PENDING/CANCEL_PENDING 건도 동일하게 이관
- 퇴직자는 서브 승인자 선택 후보에서 제외 (is_active=true만 후보)
- **퇴직 복구 (2026-08-16)**: `POST /api/users/{id}/restore`로 재직 상태로 되돌린다. **퇴직의 완전한 역연산이 아니다** — `is_active`·`retired_at` 두 플래그만 되돌리고, 해제된 팀장직과 이관된 결재는 그대로 둔다(그사이 다른 사람이 팀장이 됐거나 결재가 이미 처리됐을 수 있다). 팀장은 관리자가 다시 지정한다

### 2-9(b) 역할과 부서 팀장의 관계 (2026-08-16 확정)

**"팀장"이라는 말이 두 곳에 있고, 둘은 항상 붙어 다녀야 한다.**

| 값 | 화면 | 뜻 |
|---|---|---|
| `users.role = TEAM_LEADER` | 구성원 관리 | **권한** — 결재할 수 있는 자격 |
| `department.leader_id` | 부서 관리 | **결재선** — 그 부서의 기본 승인자 |

예전에는 둘이 따로 놀았다. 구성원 관리에서 역할만 팀장으로 올리면 **권한만 생기고 결재선에는
들어가지 않아** 부서 관리에는 "공석"으로 보였고, 그 부서 신청의 승인자가 SYSTEM_ADMIN으로 갔다.
같은 부서 사람 둘을 팀장으로 올리면 "팀장 2명"도 만들어졌다.

**지금 규칙 — 역할이 단일 출처다** (`UserService.changeRole` · `assignDepartmentLeader`):

- 역할을 `TEAM_LEADER`로 올리면 → **소속 부서의 `leader_id`에 함께 앉힌다**
- **소속 부서가 없으면 승격 자체를 거부**한다 (`DEPARTMENT_REQUIRED_FOR_LEADER`) — 앉힐 자리가 없다
- 그 부서에 이미 팀장이 있으면 → **기존 팀장을 사원으로 내리고** 교체하며, 그 사람 앞으로 걸린
  대기 결재를 이관한다. 자리에서만 빼고 역할을 남기면 "그 부서에 역할이 팀장인 사람 2명"이 되어
  누가 실제 결재자인지 알 수 없다. 결재할 수 없는 사람이 승인자로 남으면 그 신청은
  선차감이 걸린 채 영구 PENDING이 된다(리뷰 I-5a)
- 역할을 `EMPLOYEE`로 내리면 → 팀장직 해제 + 대기 결재 이관 (기존 동작)
- **SYSTEM_ADMIN은 교체 대상이 아니다** — 팀장 자리에서만 빠지고 관리자 권한은 부서와 무관하다

**부서 관리에서 팀장을 바꿔도 같은 경로를 탄다.** 두 화면이 각자 구현하면 한쪽에서만 불변식이
깨진다 — `DepartmentService.update`가 `UserService.assignDepartmentLeader`를 호출한다.

**결과 불변식: 부서마다 팀장은 최대 1명이고, 그 사람의 역할은 항상 `TEAM_LEADER` 이상이다.**
