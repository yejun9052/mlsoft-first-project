## 점검 순서

**Codex → Claude Code → 사용자** 3단계다. 각 단계가 앞 단계를 검산한다.

| 단계 | 누가 | 무엇을 |
|---|---|---|
| 1 | Codex | 코드를 읽고 "자동 테스트가 못 덮는 것"을 추려 QA 후보를 만든다 |
| 2 | Claude Code | 그 후보의 **주장을 코드로 검증**하고, 틀린 절차·기대값을 고쳐 이 문서에 반영한다 |
| 3 | 사용자 | 브라우저에서 실제로 돌린다. 결과를 아래 "진행 기록"에 남긴다 |

2단계에서 실제로 걸러진 예 — 1단계는 "역할 변경 반영에 최대 60초"라고 했지만
**새로고침하면 즉시 반영된다**(`initialDataUpdatedAt: 0`이 저장값을 곧바로 stale로 만든다).
60초는 *같은 화면에 머무를 때*의 상한이다. 그대로 뒀으면 3단계에서 헛기다림이 됐다.

## 준비 — 시작 전에 읽을 것

기동: `/dev` 슬래시 커맨드 (백엔드 8080 · 프론트 5173).

**⚠️ 데모 계정 8명으로는 로그인할 수 없다.** `DemoDataInitializer`가 `@mlsoft.com` 주소로
DB 행만 만들 뿐, 로그인은 Google OAuth라 실제 구글 계정이 없으면 그 사람이 될 수 없다.
데모 데이터는 **화면을 채우고 결재 대상이 되어 주는 용도**다.

그래서 역할별 화면은 이렇게 확인한다:

```sql
-- 본인 계정의 역할을 바꾼 뒤 브라우저 새로고침 (재로그인 불필요)
UPDATE users SET role = 'TEAM_LEADER' WHERE email = '<내 계정>';
UPDATE users SET role = 'SYSTEM_ADMIN' WHERE email = '<내 계정>';
```

`OnboardingCheckInterceptor`가 매 요청 DB role로 권한을 재구성하므로 **새로고침만으로 바뀐다.**
이 동작 자체가 아래 J-2 항목이기도 하다 — 한 번은 의도적으로 확인할 것.

두 계정이 필요한 항목(J-2·K-1 등)은 **일반 창 + 시크릿 창**을 쓰거나, 구글 계정이 두 개면
브라우저 프로필을 나눈다.

설계상 **조회 실패를 예외로 만들지 않는다.** 키가 없거나 외부 API가 죽어도 빈 목록으로 내려가
공휴일 표시·검증만 빠지고 나머지는 계속 동작해야 한다.

- [ ] 🔴 **N-1** 키 없이도 캘린더가 정상 동작한다
  - 준비: `application-local.yml`의 `HOLIDAY_API_KEY`를 비우고 재기동 (또는 아직 적재 안 된 연도로 이동)
  - 절차: ① 캘린더 열기 → ② 월 이동 → ③ 날짜 클릭 → ④ 연차 신청
  - 기대: **공휴일 이름·빨간 표시만 없다.** 캘린더·연차·개인 일정·신청 패널은 전부 동작한다.
    공휴일 오류가 전체 페이지 오류 화면으로 번지면 실패
  - 실패하면: `HolidayService.java` · `useHolidays.js` · `CalendarPage.jsx`

- [ ] 🟡 **N-2** 키가 있으면 공휴일이 뜨고 그날은 연차 신청이 막힌다
  - 절차: ① 개발자도구 콘솔에서 `fetch('/api/holidays/sync?year=2026', {method:'POST', credentials:'include'})` (관리자 계정)
    — **화면에 버튼이 없다**(H절 참조) → ② 해당 연도 캘린더 → ③ 평일 공휴일 클릭 → ④ 연차 신청 시도
  - 기대: 공휴일명이 빨간 계열로 표시되고 그날은 연차 신청이 거부된다. **개인 일정 등록은 된다**

- [ ] 🟡 **N-3** 공휴일 자격 증명이 DB에 평문으로 남지 않는다
  - 준비: `HOLIDAY_API_KEY`와 별도 `HOLIDAY_CREDENTIAL_ENCRYPTION_KEY`를 주입하고, 최초 시드 때만 `HOLIDAY_CREDENTIAL_SEED=true`로 앱을 한 번 기동한 뒤 플래그를 끈다
  - 절차: `holiday_api_credentials`와 `holidays`를 각각 조회한다
  - 기대: credential 행에는 복호화 불가능한 암호문만 있고, `holidays`에는 날짜·명칭만 있다. API 키가 날짜별 행에 반복되지 않는다

- [ ] 🟡 **N-4** 공휴일이 하나의 일정으로 동작한다
  - 절차: 공휴일 하루에 개인 일정·연차 표시 데이터를 2건 이상 준비하고 데스크톱/모바일 캘린더를 확인한다
  - 기대: 데스크톱 `...더보기` 개수에 공휴일이 포함되고 상세 모달에 같은 목록으로 표시된다. 모바일은 빨간 점과 선택일 하단 공휴일 행을 표시하며 `...더보기`는 없다

- [ ] 🟡 **N-5** 공휴일이 네 화면에 같은 내용으로 표시된다
  - 절차: 공휴일이 적재된 연도로 이동해 `Calendar`·`Dashboard`·`MyInfo`·`Team` 화면을 차례로 연다
  - 기대: 네 화면 모두 같은 공휴일 날짜와 이름을 표시하고, 한 화면의 조회 실패가 다른 화면 전체 오류로 번지지 않는다

- [ ] 🔴 **N-6** 공휴일 날짜의 연차 신청이 차단된다
  - 절차: 공휴일 날짜를 연차 신청 날짜로 선택하고 제출한다
  - 기대: `공휴일은 연차로 신청할 수 없습니다.` 오류가 표시되고 신청이 생성되지 않는다. 개인 일정 등록은 허용된다

- [ ] 🔴 **N-7** 미적재 연도에서는 degrade 정책대로 연차 신청이 통과한다
  - 준비: 공휴일을 아직 동기화하지 않은 연도의 평일을 선택한다
  - 절차: 해당 날짜로 연차를 신청한다
  - 기대: 공휴일 조회 실패가 신청을 막지 않고, 주말·과거 날짜 등 다른 규칙에 걸리지 않으면 신청이 정상 접수된다 (통과 유지 확정, 2026-09-05)

- [ ] 🟡 **N-8** 관리자 수동 동기화가 선택 연도와 건수를 표시한다
  - 절차: 관리자 → 연차 정책 → 공휴일에서 전년 또는 다음해를 선택하고 `동기화`를 누른다
  - 기대: 선택한 연도의 API가 호출되고 완료 후 `N건 적재`가 표시되며, 현재 적재 건수도 갱신된다

- [ ] 🟡 **N-9** 새해 공휴일 자동 적재 잡이 정해진 시각에 실행된다
  - 절차: 1월 1일 00:05 KST 기동 로그 또는 스케줄러 실행 로그를 확인한다
  - 기대: `LeaveScheduler.syncHolidaysForNewYear`가 해당 연도를 동기화하고, 이후 캘린더에서 새해 공휴일을 조회할 수 있다

## P. 이메일 건별 알림 — 2026-08-12 신규, **실제 메일이 나간다**

발송 계정은 **개인 Gmail + 앱 비밀번호**다(`application-local.yml`의 `spring.mail`).
Workspace가 아니므로 **From 주소는 계정 주소로 고정**되고 표시 이름만 바뀐다. 회신 주소는
`MAIL_REPLY_TO`로 분리한다. **한도가 일 500건**이니 반복 테스트 시 유의할 것.

발송 구조는 **아웃박스**다 — 업무 트랜잭션 안에서 `email_history` 행(PENDING)을 먼저 만들고,
커밋 후 비동기로 발송한다. **그래서 "메일이 안 왔다"와 "이력조차 없다"는 원인이 다르다.**

```sql
-- 매 항목 후 이걸로 확인한다
SELECT id, recipient_id, email_type, status, retry_count, error_message, sent_at
  FROM email_history ORDER BY id DESC LIMIT 20;
```

| 상태 | 뜻 |
|---|---|
| `SENT` | 정상 |
| `PENDING`이 10분 넘게 유지 | 발송이 안 붙었다. 재시도 스케줄러(15분)가 회수해야 한다 |
| 행 자체가 없음 | 발행 자체가 안 됐다 — 트랜잭션·publisher 문제 |

| # | 🔴 | 절차 | 기대 결과 | 결과 |
|---|---|---|---|---|
| P-1 | 🔴 | 연차 신청 1건 (1차·2차 승인자 지정) | **3통**이 각각 나간다 — 신청자·1차·2차. `email_history` 3행 `SENT` | ⬜ |
| P-2 | 🔴 | 그 건을 승인 | 신청자·승인자 2명 + **재직 중인 SYSTEM_ADMIN 전원**에게 간다 (참조 성격) | ⬜ |
| P-3 | 🔴 | 받은 메일의 발신자 확인 | 표시 이름은 **MLsoft**, 주소는 **계정 주소 그대로**. 회신 누르면 `MAIL_REPLY_TO`로 간다 | ⬜ |
| P-4 | 🔴 | 메일 본문의 연차 사유 | 신청 사유가 보인다 (수신자 전원이 열람 권한자다 — 마스킹 대상 아님) | ⬜ |
| P-5 | 🔴 | 반려 · 취소 · 소급 취소 승인을 각각 1건 | 4종 템플릿이 서로 다른 제목·본문으로 온다 | ⬜ |
| P-6 | 🔴 | 복리후생 신청 → 승인 | 연차와 같은 규칙으로 발송된다 (`email_type = WELFARE`) | ⬜ |
| P-7 | 🟡 | 같은 사람이 신청자이면서 승인자·관리자인 경우 | **한 통만** 온다 (수신자 중복 병합) | ⬜ |
| P-8 | 🔴 | 퇴직 처리된 사원이 승인자인 건을 처리 | 그 사람에게는 **안 간다**. 이력 행도 안 생긴다 | ⬜ |
| P-9 | 🟡 | 앱 비밀번호를 틀리게 바꾸고 재기동 → 연차 신청 | **기동은 정상.** 신청도 정상 접수된다. 이력만 `FAILED` + `error_message`에 인증 실패 | ⬜ |
| P-10 | 🟡 | P-9 상태로 15분 이상 대기 | `retry_count`가 오르다 **3에서 멈춘다** (무한 재시도 아님) | ⬜ |

📌 **P-9가 이 절에서 가장 중요하다.** 설계상 이메일 실패가 업무를 막으면 안 된다 —
메일이 안 나갔다고 연차 신청이 실패하면 그게 결함이다. 공휴일 API degrade(N절)와 같은 기준.

📌 생일 반차 알림은 스케줄러 경로라 **손으로 확인할 방법이 없다**(O절과 같은 이유).
자동 테스트가 덮고 있으니 여기서 시도하지 말 것.

연차 정책 화면의 **시스템 설정**은 토글·입력을 바꾼 뒤 카드 맨 아래 오른쪽 **"설정 저장"을 따로

모르고 메뉴를 옮겼다 — 그러면 값이 조용히 사라지고 다음 접속에 "껐는데 켜져 있다"로 보인다.
그래서 **① 화면에 미저장 배지**를 띄우고 **② 떠나려 할 때 붙잡는다**.

**브라우저 뒤로가기는 의도적으로 막지 않았다** (S-5 참고). 앱이 `BrowserRouter`라 `useBlocker`를
못 쓰고, 우회책은 저장한 뒤에도 뒤로가기를 한 번 먹통으로 만든다 — 조용히 고장 난 뒤로가기가
잃은 설정 한 건보다 나쁘다고 봤다.
