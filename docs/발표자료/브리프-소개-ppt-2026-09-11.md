## 2. 산출물 요구

- **형식**: `.pptx`, 16:9, 한국어. `python-pptx 1.0.2`가 설치돼 있다(`python -c "import pptx"`로 확인).
  Node가 필요하면 `pptxgenjs`도 가능하지만 python-pptx를 우선한다.
- **플로우 차트와 아키텍처 다이어그램은 PPT 네이티브 도형(사각형·마름모·화살표 커넥터)으로 그린다.**
  이미지로 박아 넣지 않는다 — 받는 쪽이 파워포인트에서 글자를 고칠 수 있어야 한다.
  단, 네이티브로 도저히 안 되는 것(예: 복잡한 ERD)은 SVG→PNG로 넣되 그 사실을 보고에 적는다.
- **분량**: 18~25장. 너무 길면 안 읽는다.
- **디자인**: 발표용답게. 어두운 배경이든 밝은 배경이든 일관되게. 한 장에 한 메시지.
  글자 크기 최소 11pt. 겹침·잘림이 없어야 한다 — 만든 뒤 PowerPoint로 PNG 내보내기 해서
  **직접 눈으로 전 장 확인**하고, 확인했다고 보고에 적어라.
  PowerPoint COM으로 내보내는 방법:
  ```powershell
  $app = New-Object -ComObject PowerPoint.Application
  $p = $app.Presentations.Open("<절대경로>.pptx", $true, $false, $false)
  $p.Export("<출력폴더>", "png", 1600, 900); $p.Close(); $app.Quit()
  ```
- **다시 만들 수 있게** 생성 스크립트를 남긴다. 장표를 손으로 고치면 다음 갱신 때 덮어써지므로 원본은 스크립트다.

### B. 큰 기능 — "~한다" 한 줄씩 (2~3장)
읽는 사람이 개발자가 아니어도 되게, 이 톤으로:
- 사원이 캘린더에서 날짜를 골라 연차를 신청한다
- 팀장이 결재함에서 승인·반려한다
- 복리후생(경조사 등)을 신청하면 승인 시 보너스 연차로 쌓인다
- 외근·출장·재택·교육은 결재 없이 일정으로 기록한다
- 관리자가 조직·구성원·정책을 화면에서 관리한다
- 연차 부여·월차 적립·생일 반차·소진 안내·퇴직자 파기를 매일 새벽 자동으로 처리한다
- 신청·결재·온보딩 결과가 관련자에게 이메일로 간다
- 관리자가 이메일 양식을 고치고 일괄 발송할 수 있다
- 퇴직자를 처리하고, 보존 기간이 지나면 개인정보를 파기하며, 재입사도 처리한다

### C. 세세한 동작 — **플로우 차트** (8~10장, 이 장들이 핵심)
한 장에 흐름 하나. 사각형=단계, 마름모=판단, 화살표에 조건 표기. 아래 흐름은 **코드에서 확인된 사실**이다.

**C-1. 연차 신청 → 결재 → 메일**
```
사원: 캘린더에서 날짜 선택 → 종일/오전반차/오후반차 선택 → 승인자(기본·서브) 확인 → 신청
  ↓ 검증: 주말? 공휴일? 지난 날짜? 이미 신청된 날짜? 잔여 부족?
  ↓ (통과) 잔액 선차감(PENDING 상태) + 메일 발송
      → 메일 수신: 신청자 본인 + 기본 승인자 + 서브 승인자
팀장: 결재함에서 승인 / 반려(사유)
  ↓ 승인: APPROVED, 잔액 유지         ↓ 반려: REJECTED, 잔액 복구
  → 메일 수신: 신청자 + 승인자들 + 총관리자 전원
```
**C-2. 연차 취소** (2026-09-11 코드 대조로 정정 — 처음 적은 "승인 후는 전부 취소 결재"는 틀렸다)
```
승인 전(PENDING): 사원이 취소 → 즉시 CANCELLED, 잔액 복구 → 메일(신청자·승인자)
승인 후(APPROVED) + 날짜가 전부 오늘·미래: 즉시 CANCELLED, 잔액 복구 → 메일(신청자·승인자)
승인 후(APPROVED) + 지난 날짜 포함: 취소 요청 → CANCEL_PENDING → 팀장이 취소 승인/거부
   승인 → CANCELLED, 잔액 복구 / 거부 → APPROVED 유지 → 메일(신청자·승인자·총관리자)
```
**C-3. 연차 잔액이 계산되는 방식**
```
잔여 = 부여(base) + 보너스(bonus) − 사용(use)
신청한 날짜가 [기산일, 기산일+1년) 안이면 → 지금 잔액에서 차감
다음 기산일 이후 날짜면 → 지금 잔액은 그대로, "다음 회차 예약"으로만 집계 (다음 1회차까지만 허용)
잔여 부족 + 당겨쓰기 허용 → 부족분을 advance_days로 기록 → 다음 기산일에 새 연차에서 상환
```
**C-4. 온보딩 (첫 로그인)**
```
Google 로그인 → 회사 도메인 확인 → 자동 가입 → 생일·입사일·직급 입력
  ↓ 입사일이 최근 90일 이내? (관리자 설정 가능)
  예 → 즉시 완료, 연차 산정        아니오 → 관리자 승인 대기 (연차 0) → 총관리자 전원에게 메일
                                           → 승인: 연차 산정 + 본인 메일 / 반려: 본인 메일(반려된 입사일 포함)
                                           → 대기 중 1회 스스로 입사일 수정 가능 → 총관리자에게 메일
온보딩 끝나기 전엔 다른 화면 전부 차단
```
**C-5. 복리후생 신청 → 결재**
```
정책 선택(경조·포상 등) → 사유·기간 입력 → 신청 → 메일(신청자·승인자)
→ 승인: bonus_days에 가산 / 반려 → 메일(신청자·승인자·총관리자)
```
**C-6. 매일 00:10 자동 처리 (순서 고정)**
```
① 기산일 리셋(1주년마다 연차 새로 부여, 당겨쓴 빚 상환)
→ ② 월차 적립(1년 미만, 입사일+N개월마다 1일)
→ ③ 생일 반차(0.5일 가산 → 본인·총관리자 메일)
→ ④ 연차 소진 안내(설정된 주기에 잔여 남은 사원에게 메일, 같은 주기 중복 방지)
→ ⑤ 퇴직자 파기(자동 모드일 때만: 3년 경과 → 30일 전 예고 메일 → 파기 → 결과 메일)
사원 1명 = 1트랜잭션. 순서를 바꾸면 값이 어긋나므로 고정.
```
**C-7. 이메일이 나가는 경로**
```
사건 발생(신청·결재·온보딩·생일·안내·파기) → 발송 큐에 PENDING으로 적재
→ 발송 계정 결정: 관리자 화면에 저장된 SMTP 계정 → 없으면 서버 환경변수 계정
→ SENDING 선점 → 발송 → SENT / 실패 시 FAILED(최대 3회 자동 재시도, 이후 관리자 수동 재발송)
관리자: 양식(제목·본문·변수) 수정, 대상 골라 일괄 발송, 이력 조회
```
**C-8. 퇴직 → 파기 → 재입사**
```
퇴직 처리 → 즉시 로그인 차단 (본인 계정은 불가, 되돌리기 가능)
→ 보존 기간(기본 3년, 근로기준법) 경과 → 수동 파기 or 자동 파기(30일 예고)
→ 파기 = 행 삭제가 아니라 익명화: 이름 "퇴직사원#id", 이메일 무효화, 사유 본문 삭제. 감사 로그는 남김(이름 없이)
→ 파기 보류 가능(감사·분쟁 중)
재입사 → 파기 전 계정만 가능(파기된 계정은 신규 가입) · 이전 근속을 별도 구간으로 보존, 연차는 새 입사일 기준으로 새로 시작
```
**C-9. 권한과 접근 제어**
```
역할 3개: 사원 / 팀장 / 총관리자
매 요청마다 서버가 DB를 다시 확인: 퇴직자? 역할 바뀜? 온보딩 미완료? → 즉시 반영
본인 건은 본인이 결재 못 함 — 단 총관리자는 예외(위에 결재선이 없어 막으면 자기 연차를 처리할 사람이 없음, 2026-08-19)
마지막 총관리자는 강등 불가 · 본인 계정 퇴직 처리 불가
```

- 존재하지 않는 기능을 넣지 않는다. 확신 없으면 코드로 확인하고, 그래도 모르면 보고에 질문으로 남긴다.
- 기존 개발자용 장표를 그대로 복사하지 않는다.
- git commit/push 하지 않는다.
