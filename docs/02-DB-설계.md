# 02. DATABASE 설계

> 노션 설계 원문은 13개 테이블에서 시작했다. 스케줄러·리셋 이력·감사 로그가 추가된 현재
> `db/schema.sql` 기준은 20개 테이블이며, 이 문서는 핵심 설계 원문과 변경 근거를 보존한다.
> 현재 구현 상태와 운영 반영 순서는 [docs/12-남은-작업](12-남은-작업.md)을 함께 확인한다.
> DB 네이밍: 테이블/컬럼 `snake_case`, JPA 필드는 `camelCase`.
> **일수(연차) 컬럼은 전부 `DECIMAL(4,1)` / JPA는 `BigDecimal`** — 부동소수점 오차 방지 (검증 R-1, 2026-07-02 확정).

## ERD 관계 요약

```
departments ─┬─< users (department_id)
             └── leader_id → users (팀장 명시)

users ─< leave_requests ─< leave_dates
                        └─< leave_action_history
users ─< welfare_requests (policy_id → welfare_policies)
                        └─< welfare_action_history
users ─< email_history (수신자/발신자)
users ─< leave_reminder_dispatch >─ email_history (자동 발송 중복 방지·아웃박스 연결)

leave_policy (근속년수별 연차), holidays (공휴일) : 독립 테이블
mail_credentials (메일 발신 계정 암호문), email_templates (메일 양식) : 독립 테이블
```

## 3-4 leave_dates

| NAME | TYPE | NULL | DEFAULT | 제약 | 설명 |
|---|---|---|---|---|---|
| leave_requests_id | BIGINT | NOT | | FK(leave_requests) | |
| day | DATE | NOT | | UNIQUE(leave_requests_id, day) | 날짜 |

> **설계-코드 불일치 해소 (리뷰 D-6, 2026-08-10) — 문서를 코드에 맞췄다.**
>
> 원안은 `id` PK를 가진 독립 테이블이었지만, 구현은 `@ElementCollection` +
> `@CollectionTable(name = "leave_dates")`이다. 그래서 **대리키가 없고**
> `(leave_requests_id, day)`가 실질 키다(중복 날짜를 DB가 막는다).
>
> **코드를 문서에 맞추지 않고 문서를 고친 이유**: 날짜는 신청에 완전히 종속된
> 값 목록이다 — 독립적인 생명주기도, 자기만의 식별자로 참조될 일도 없다.
> `@ElementCollection`이 그 관계를 정확히 표현하고, 신청을 지우면 날짜가 함께 사라진다.
> 독립 엔티티로 쪼개면 얻는 것은 쓰이지 않는 `id` 하나이고, 대신 저장소·연관 관리 코드가
> 늘어난다. 현재 구조는 `@BatchSize(50)`·인덱스(`idx_leave_dates_day`)까지 붙어 정상 동작 중이다.
>
> `schedule_dates`(3-4(c))도 같은 패턴이며, 그쪽은 처음부터 이렇게 설계했다.

## 3-4(b) schedule_entries — 개인 일정 (2026-08-07 신규)

외근·출장·재택근무·교육. **연차 잔액과 무관하다** — `days`도 `status`도 `approver`도 없다.
결재를 거치지 않으므로 상태 전이가 없고, 차감하지 않으므로 일수를 저장할 이유가 없다
(필요하면 `schedule_dates` 행 수로 센다). 필드를 두고 안 쓰면 나중에 누군가 채운다.

### 카탈로그는 코드가 정의한다 (2026-08-06)

**이 테이블은 값만 들고 있다.** 어떤 키가 존재하고 그 타입·기본값·허용 범위·라벨이 무엇인지는
`PolicyConfigKey` enum(`domain/policy/entity/`)이 정의한다. 값 검증도 그쪽 책임이다.

정의를 코드로 옮긴 이유 — 이전에는 키·기본값이 `DataInitializer`, 읽는 쪽 키 상수가 각 서비스,
라벨·타입·설명이 프론트 `CONFIG_META`에 흩어져 있었다. 설정 하나를 추가하려면 세 곳을 고쳐야 했고,
프론트를 빼먹으면 **관리자 화면에서 그 설정이 조용히 사라졌다**(메타데이터 없는 키를 필터로 걸러냈다).

지금은 enum에 상수 한 줄을 넣으면 시딩·저장 검증·화면 렌더가 모두 따라온다.
`GET /api/admin/configs`가 값과 함께 메타데이터를 내려주므로 프론트는 키 이름을 모른다 (docs/03).

**값 검증은 저장 시점에 한다.** 이전에는 `@NotBlank`만 걸려 있어 관리자가 아무 문자열이나 저장할 수
있었고, 문제는 **값을 읽는 시점**에 드러났다 — `advance_leave_enabled`에 `"ture"`를 넣으면
`Boolean.parseBoolean`이 예외 없이 `false`를 돌려주므로 당겨쓰기가 조용히 꺼지고, 사원은
잔여가 부족할 때 이유 모를 거부를 받는다. 읽기 쪽은 2차 방어선으로 기본값 fallback + WARN 로그다.

**카탈로그 (9키)** — 단일 정의처는 `PolicyConfigKey` enum이다. 이 표는 그 사본이므로
enum을 고치면 여기도 함께 고친다 (2026-08-16 기준으로 동기화했다).

|---|---|---|---|---|---|
