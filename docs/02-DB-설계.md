# 02. DATABASE 설계

> 노션 설계 원문 기준. 13개 테이블. DB 네이밍: 테이블/컬럼 `snake_case`, JPA 필드는 `camelCase`.
> **일수(연차) 컬럼은 전부 `DECIMAL(4,1)` / JPA는 `BigDecimal`** — 부동소수점 오차 방지 (검증 R-1, 2026-07-02 확정).

## ERD 관계 요약

```
departments ─┬─< users (department_id)
             └── leader_id → users (팀장 명시)

users ─< leave_requests ─< leave_dates
                        └─< leave_action_history
users ─< welfare_requests (policy_id → welfare_policies)
                        └─< welfare_action_history
users ─< email_history (수신자/발신자)

leave_policy (근속년수별 연차), holidays (공휴일) : 독립 테이블
```

### 카탈로그는 코드가 정의한다 (2026-08-06)

**이 테이블은 값만 들고 있다.** 어떤 키가 존재하고 그 타입·기본값·허용 범위·라벨이 무엇인지는
`PolicyConfigKey` enum(`domain/policy/entity/`)이 정의한다. 값 검증도 그쪽 책임이다.

정의를 코드로 옮긴 이유 — 이전에는 키·기본값이 `DataInitializer`, 읽는 쪽 키 상수가 각 서비스,
라벨·타입·설명이 프론트 `CONFIG_META`에 흩어져 있었다. 설정 하나를 추가하려면 세 곳을 고쳐야 했고,
프론트를 빼먹으면 **관리자 화면에서 그 설정이 조용히 사라졌다**(메타데이터 없는 키를 필터로 걸러냈다).

지금은 enum에 상수 한 줄을 넣으면 시딩·저장 검증·화면 렌더가 모두 따라온다.
`GET /api/admin/configs`가 값과 함께 메타데이터를 내려주므로 프론트는 키 이름을 모른다 (docs/03).

**값 검증은 저장 시점에 한다.** 이전에는 `@NotBlank`만 걸려 있어 관리자가 아무 문자열이나 저장할 수
있었고, 문제는 **값을 읽는 시점**에 드러났다 — `advance_leave_enabled`에 `"ture"`를 넣으면
`Boolean.parseBoolean`이 예외 없이 `false`를 돌려주므로 당겨쓰기가 조용히 꺼지고, 사원은
잔여가 부족할 때 이유 모를 거부를 받는다. 읽기 쪽은 2차 방어선으로 기본값 fallback + WARN 로그다.

**카탈로그 (7키)**

| 키 | 타입 | 기본값 | 허용 범위 | 동작 | 설명 |
|---|---|---|---|---|---|
| advance_leave_enabled | BOOLEAN | false | — | ✅ | 당겨쓰기 허용 여부 (잔여 부족 시 신청 접수 가능) |
| advance_max_days | DECIMAL | 5.0 | 0 ~ 25.0 | ✅ | **당겨쓰기 누적 상한 — 초과 시 ADVANCE_LIMIT_EXCEEDED (메모 11, 리뷰 I-3)** |
| leave_max_dates_per_request | INTEGER | 30 | 1 ~ 366 | ✅ | 신청 1건당 날짜 개수 상한 (리뷰 I-3) |
| bonus_carry_over_enabled | BOOLEAN | false | — | ⏳ | **기산일 리셋 시 보너스 연차 이월 여부 — false면 소멸 (메모 10)** |
| monthly_leave_max_days | INTEGER | 11 | 0 ~ 12 | ⏳ | 1년 미만 월차 적립 상한 (갭분석 B-1) |
| reminder_list_days | INTEGER | 30 | 0 ~ 365 | ⏳ | 소진 안내 대상을 기산일 며칠 전부터 표시할지 |

⏳ = `PENDING_FEATURE`. 값은 저장되지만 이를 읽는 기능(스케줄러·이메일)이 아직 없다.
관리자 화면에 **"미동작" 배지로 구분 표시**한다 — 설정처럼 보이는데 아무 일도 일어나지 않는 것이
기존 소진 안내 2키의 문제였다(docs/11 "⚠️ 반쪽"). 기능을 구현하면 `ACTIVE`로 바꾸는 것이 마지막 단계다.

## 구현 시 검토할 점 (설계 리뷰 메모)

1. ~~created_at/update_at 타입~~ → **DATETIME(LocalDateTime) 확정** (2026-07-02 구현 반영, 감사 목적)
2. ~~users.role에 RETIRED 포함 vs is_active로 판별~~ → **is_active=false + retired_at로 판별 확정, role에서 RETIRED 제외** (2026-07-02 구현 반영 — 퇴직 전 직급 이력 보존, 로그인 차단은 is_active 검사)
3. **대기 중 선차감 정책**: use_days에 PENDING 포함 → 화면 표시는 "사용(확정)"과 "대기"를 분리해서 보여줘야 혼란 없음.
4. **history의 user_id(신청자) 중복 보관**: 조인 없이 로그 조회하기 위한 반정규화 — 유지.
5. **인덱스**: users.email(UK), leave_dates.day, leave_requests.status, *_history.created_at, holidays.date — 전달받은참고자료의 인덱스 전략 참고.
6. **FK 삭제 정책**: 퇴직자 3년 보존 요구 때문에 CASCADE 금지, 사용자 삭제 대신 비활성화(소프트 삭제)로 통일.
7. ~~welfare_requests에 부여 일수 스냅샷 없음~~ → **`add_days` 신청 시점 스냅샷 확정** (2026-07-06): 신청 생성 시 policy.default_days를 복사하고, 승인 시 이 값으로 bonus_days를 가산 — 정책 변경 후에도 부여 근거 보존, 승인 취소·정정 시 회수 근거로 사용 (3-7 반영, 연차의 advance_used_days 스냅샷과 같은 원리).
8. **users에 월차 지급 이력 필드 없음** (인증 리뷰에서 발견): 1년 미만 월차 스케줄러가 "마지막 지급 기록 기준 catch-up"(01 §2-7)을 구현하려면 `last_monthly_grant_date DATE` 컬럼이 필요 — base_days 역산은 관리자 직접 설정과 충돌. 연차 코어(3단계) 착수 시 추가할 것.
