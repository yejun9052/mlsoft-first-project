## 1. 잡 구성과 실행 순서

매일 **00:10 KST** 단일 진입점에서 아래 순서로 실행한다.

```
① 기산일 리셋  →  ② 월차 적립  →  ③ 생일 반차
```

**순서가 고정인 이유** — 우연이 아니라 데이터 의존성이다.

- **① → ②**: 1주년 당일에 두 잡이 겹친다. 리셋이 먼저 돌면 `hire_date + 1년 <= 오늘`이 되어 월차 잡의 "1년 미만" 조건에서 자연히 빠진다. 반대 순서면 11일째 월차를 적립한 직후 리셋이 그걸 소멸시켜, 하루짜리 유령 적립이 이력에 남는다.
- **① → ③**: 생일 반차는 `bonus_days` 가산인데 리셋은 `bonus_days`를 0으로 만든다. **생일과 기산일이 같은 날인 사원**은 순서가 뒤바뀌면 그 해 생일 반차가 지급 즉시 증발한다.

## 2. 대상 조회 조건

모든 잡에 공통으로 적용하는 가드:

- `is_active = true` — 퇴직자 제외
- `hire_date IS NOT NULL` — 온보딩 미완료자 제외 (검증 Y-2)

잡별 조건:

| 잡 | 조건 |
|---|---|
| ① 기산일 리셋 | `last_reset_date + 1년 <= 오늘` (검증 Y-1 — "오늘이 입사일" 금지) |
| ② 월차 적립 | `hire_date + 1년 > 오늘` **AND** `last_monthly_grant_date + 1개월 <= 오늘` **AND** 누적 적립 < 11 |
| ③ 생일 반차 | 올해 생일 `<= 오늘` **AND** `last_birthday_grant_year < 올해` **AND** 올해 생일 `>= hire_date` |

③의 마지막 조건이 없으면 **입사 전에 지나간 생일까지 소급 지급된다** (3월 생일·7월 입사자가 입사 당일 0.5일을 받음).

## 3. 스키마 변경

`ddl-auto: update`라 컬럼 추가는 자동 반영된다. **기존 행은 전부 null이 되므로 폴백 규칙이 설계의 일부다.**

| 대상 | 컬럼 | 근거 | 기존 행 폴백 |
|---|---|---|---|
| `users` | `last_monthly_grant_date DATE` | docs/02 메모 8 | null이면 `hire_date` 기준으로 계산 |
| `users` | `last_birthday_grant_year INT` | 신규 (중복 지급 방지) | null이면 미지급 — §2의 `>= hire_date` 조건이 소급을 막음 |
| `leave_reset_history` | `carried_bonus_days DECIMAL(4,1)` | docs/02 메모 10 (미결 → 확정) | 기본 0 |

`base_days` 역산으로 월차 적립 횟수를 알아내는 방법은 **쓰지 않는다** — 관리자가 `PATCH /api/users/{id}/base-days`로 연차를 직접 설정할 수 있어 역산값이 오염된다 (docs/02 메모 8이 지적한 그대로).

|---|---|---|
| `advance_max_days` | 5 | docs/02 메모 11 |

## 4. 기산일 리셋 — 계산 순서

리셋은 네 가지를 한 번에 처리하므로 순서를 고정한다.

```
1. 새 정책 연차 산정      newBase = calculateAnnualLeaveDays(만 근속년수)
2. 미래 승인분 재차감      newUse  = Σ(기산일 이후 날짜 × 단가)      ← §5
3. 보너스 이월 판정        newBonus = config on ? max(0, bonus − max(0, use − base)) : 0
4. 잔존 신청 스냅샷 정리    PENDING·CANCEL_PENDING 건의 advance_used_days = 0  ← 아래
5. 이력 기록 후 상태 전이   leave_reset_history 저장 → user.resetAnnualLeave(...)
```

**4단계를 빠뜨리면 리셋 후 반려가 음수를 만든다** (리뷰 I-4). `resetAnnualLeave`가 `advance_days`를 0으로 정산하는데 잔존 신청은 여전히 "내가 advance를 N일 썼다"는 스냅샷을 들고 있다. 리셋 뒤 그 건이 반려되면 `restoreLeave(days, N)`이 이미 0인 `advance_days`에서 N을 또 빼 **음수**가 된다. 리셋 시점에 살아 있는 선차감 건(`PENDING`·`CANCEL_PENDING`)의 스냅샷을 0으로 재기록해야 한다 — 그 건들의 차감분은 2단계에서 이미 새 `use_days`에 반영됐으므로 당겨쓰기 근거가 소멸한 상태다.

**이력을 먼저 쓴다.** `LeaveResetHistory.create()`가 리셋 *직전* 상태(`prev_base`·`prev_use`·`expired`·`advance_settled`)를 스냅샷하기 때문에, 상태를 먼저 바꾸면 기록할 원본이 사라진다.

`User.resetAnnualLeave`는 현재 `useDays`/`bonusDays`를 **무조건 0으로 밀고 있어 시그니처 변경이 필요하다**:

```java
// 현재 — 미래 승인분과 이월 보너스가 증발
resetAnnualLeave(BigDecimal newBaseDays, LocalDate resetDate)

// 변경
resetAnnualLeave(BigDecimal newBaseDays, BigDecimal carriedUseDays,
                 BigDecimal carriedBonusDays, LocalDate resetDate)
```

`AuthService.completeOnboarding`의 호출부 2곳도 함께 수정한다(둘 다 `ZERO, ZERO` 전달 — 온보딩 시점엔 이월할 것이 없다).

### 보너스 이월 공식 (메모 10)

```
이월분 = max(0, bonus − max(0, use − base))
```

`use`가 `base`를 초과한 만큼이 보너스에서 쓴 분량이다. 리셋 때 `use`가 0이 되므로, **이 보정 없이 `bonus`를 그대로 넘기면 이미 써버린 보너스가 부활한다.**

## 5. 미래 승인분 재차감 (결정 1)

### 왜 필요한가

```
기산일 3/1인 사원
 2/20  "3/10 연차" 신청·승인   →  use_days += 1  (선차감)
 3/1   리셋                    →  use_days = 0   ← 차감분 증발
 3/10  실제로 휴가 사용         →  아무 데도 반영 안 됨
결과: 새 연도 잔액 1일 과다 — 연차를 공짜로 한 번 더 받는다
```

docs/01 §2-7의 *"기산일 기준 미래에 사용한 연차 → 사용 연차에 포함해서 계산"*이 이것이고, docs/06이 v1에서 재사용 가치가 높다고 꼽은 `resetAndApplyPolicy`의 "미래 승인분 재차감"이 이것이다. 현재 코드에는 없다.

### 계산 규칙

**날짜 단위**로 집계한다 (신청 단위가 아니다).

```
newUseDays = Σ  단가(leave_type)
             where leave_date.day >= 기산일
               and status in (APPROVED, PENDING, CANCEL_PENDING)

단가: ANNUAL = 1.0,  HALF_AM = 0.5,  HALF_PM = 0.5
```

신청 단위로 하면 `2/28~3/2` 같이 기산일을 걸친 신청에서 **이전 연도에 이미 쓴 2/28까지 새 연도에 다시 차감**되어 사원이 손해를 본다. docs/01 §2-3의 *"기산일을 넘어가는 연차 신청은 다음 기산일에서 계산"*과도 날짜 단위 해석이 맞다.

대상 상태에 `PENDING`·`CANCEL_PENDING`을 포함하는 이유: 둘 다 **선차감이 유지되고 있는** 상태다 (`CANCELLED`·`REJECTED`는 이미 복구됨).

### 엣지 — 재차감 후 잔여 음수

`newBase − advance` 에서 다시 `newUse`를 빼면 음수가 될 수 있다. 이미 승인된 건이므로 **되돌리지 않고 음수를 허용**하되 `WARN` 로그를 남긴다. 여기서 다시 `advance_days`를 쌓으면 "다음 기산일에 또 정산"이 재귀적으로 이어져 추적이 불가능해진다. 메모 11의 `advance_max_days` 상한이 이 음수 폭을 실질적으로 제한한다.

## 6. catch-up 반복 (검증 Y-1)

서버가 며칠 꺼져 있어도 재기동 후 첫 실행에서 밀린 분을 소급 처리한다.

- **리셋**: `last_reset_date + 1년 <= 오늘`이 유지되는 동안 **while 루프로 반복**한다. 회차마다 `leave_reset_history`를 남겨 몇 년치가 소급됐는지 감사 가능하게 한다. (최근 기산일로 한 번에 점프하면 중간 연도 이력이 통째로 비어 검증이 불가능해진다.)
- **월차**: `last_monthly_grant_date`부터 경과한 만 개월 수만큼 반복 적립하되 누적 11일에서 멈춘다.
- **생일**: 연 1회라 반복이 없다. `last_birthday_grant_year`로 멱등성을 확보한다.

말일 처리는 `LocalDate.plusMonths`에 맡긴다 (1/31 → 2/28 자동 클램프). 2/29 생일은 `withYear`가 평년에 2/28로 조정한다.

## 7. 트랜잭션 경계

**유저 1명당 1트랜잭션** (`REQUIRES_NEW`). 진입점 스케줄러 메서드에는 `@Transactional`을 걸지 않는다.

`User`에 `@Version` 낙관적 락이 걸려 있어(검증 R-5), 배치가 도는 중 사원이 연차를 신청하면 충돌한다. 전체를 한 트랜잭션으로 묶으면 **수백 명 중 1명의 충돌로 전원이 롤백**된다. 유저별로 끊으면 실패자만 건너뛰고, 그 사원은 다음 실행에서도 catch-up 조건에 그대로 걸리므로 **자동으로 복구된다** — 별도 재시도 큐가 필요 없다.

실패는 삼키지 말고 `ERROR` 로그에 `userId`를 남긴다.

## 8. 테스트 가능성 — Clock 주입

스케줄러는 "1년 뒤"를 시뮬레이션해야 검증할 수 있는데 `LocalDate.now(KST)`가 하드코딩되면 불가능하다. docs/02 3-11(b)가 *"이전 프로젝트에서 스케줄러 검증을 못 했던 문제"*를 명시적으로 지적하고 있으므로, 같은 실수를 반복하지 않는다.

`Clock` Bean을 주입하고 테스트에서 `Clock.fixed()`로 날짜를 고정한다. **적용 범위는 스케줄러 관련 서비스로 한정**한다 — 기존 `AuthService` 등은 건드리지 않고, 필요해지면 그때 확산한다.

```java
@Bean
public Clock clock() {
    return Clock.system(ZoneId.of("Asia/Seoul"));
}
```

### 필수 테스트 시나리오

| # | 시나리오 | 검증 대상 |
|---|---|---|
| 1 | 2년 밀린 리셋 | catch-up 반복 + 이력 2건 |
| 2 | 기산일을 걸친 신청(2/28~3/2) | 날짜 단위 재차감 — 새 use = 2.0 |
| 3 | 같은 날 두 번 실행 | 생일 반차 멱등성 |
| 4 | 생일 == 기산일 | 잡 실행 순서 (반차가 살아남는지) |
| 5 | 3개월 밀린 월차 | 반복 적립 + 11일 상한 |
| 6 | 입사 전 생일 | 소급 지급 차단 |
| 7 | `bonus_carry_over_enabled` on/off | 이월 공식 (이미 쓴 보너스가 부활하지 않는지) |

## 9. 패키지 구조

```
domain/leave/scheduler/
  LeaveScheduler.java              @Scheduled 진입점 (트리거 전용, 로직 없음)
domain/leave/service/
  AnnualLeaveResetService.java     ① 기산일 리셋
  MonthlyLeaveGrantService.java    ② 월차 적립
  BirthdayLeaveGrantService.java   ③ 생일 반차
config/
  SchedulingConfig.java            @EnableScheduling + Clock Bean
```

잡별로 서비스를 나누는 이유는 테스트 격리다. 한 클래스에 세 잡을 넣으면 `Clock`·config·리포지토리 의존이 뒤섞여 단위 테스트가 통합 테스트가 된다.

**`SchedulingConfig`는 `@Profile("!test")`로 막는다** — H2 테스트 실행 중 스케줄러가 실제로 돌면 테스트가 서로를 오염시킨다.

## 10. 이메일 연동

이메일 발송 인프라가 아직 없으므로(코드 0건) 스케줄러는 **`// TODO(email)` 시밍만 남긴다**. 연차·복리후생 서비스가 이미 쓰고 있는 패턴과 동일하게 간다.

- 생일 반차 지급 → 당사자 + SYSTEM_ADMIN (요구사항 11)
- 기산일 리셋 → 요구사항에 없음. 소진 안내는 별도 리마인더(docs/01 §2-8) 소관이다.

## 11. 구현 순서

0. **선행 — `advance_days` 재계산 방식 전환** (리뷰 I-1·I-2). 현재 `restoreLeave`/`addBonusDays`가 스냅샷 차감이라 **신청 2건 이상이 얽히면 `advance_days`가 실제와 어긋난다.** 틀린 값 위에서 리셋이 돌면 오차가 그대로 확정되므로 스케줄러보다 먼저 고친다. `max(0, use − base − bonus)` 재계산으로 바꾸면 순서 의존성이 사라진다. 기존 74건이 이 케이스를 안 덮으므로(리뷰 T-2) **2건 시나리오 테스트를 먼저 추가**할 것.
1. 스키마 3건 + config 2키 + `ErrorCode` (§3)
2. `advance_max_days` 상한 검증 — `deductLeave` 경로 (메모 11 / 리뷰 I-3). `LeaveCreateRequest`에 `@Size` 상한도 함께
3. `resetAnnualLeave` 시그니처 변경 + `AuthService` 호출부 2곳 (§4)
4. 미래 승인분 재차감 쿼리 + 잔존 스냅샷 정리 — `LeaveRequestRepository` (§4·§5)
5. `Clock` Bean + `SchedulingConfig` (§8)
6. 잡 3개 서비스 + 테스트 7종 (§9)
7. `LeaveScheduler` 진입점 연결 — **마지막**. 로직이 검증되기 전에 크론을 붙이면 실 DB에서 사고가 난다.
