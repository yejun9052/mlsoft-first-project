## 1. 잡 구성과 실행 순서

매일 **00:10 KST** 단일 진입점에서 아래 순서로 실행한다.

```
① 기산일 리셋  →  ② 월차 적립  →  ③ 생일 반차
```

**순서가 고정인 이유** — 우연이 아니라 데이터 의존성이다.

- **① → ②**: 1주년 당일에 두 잡이 겹친다. 리셋이 먼저 돌면 `hire_date + 1년 <= 오늘`이 되어 월차 잡의 "1년 미만" 조건에서 자연히 빠진다. 반대 순서면 11일째 월차를 적립한 직후 리셋이 그걸 소멸시켜, 하루짜리 유령 적립이 이력에 남는다.
- **① → ③**: 생일 반차는 `bonus_days` 가산인데 리셋은 `bonus_days`를 0으로 만든다. **생일과 기산일이 같은 날인 사원**은 순서가 뒤바뀌면 그 해 생일 반차가 지급 즉시 증발한다.

## 2. 대상 조회 조건

모든 잡에 공통으로 적용하는 가드:

- `is_active = true` — 퇴직자 제외
- `hire_date IS NOT NULL` — 온보딩 미완료자 제외 (검증 Y-2)

잡별 조건:

| 잡 | 조건 |
|---|---|
| ① 기산일 리셋 | `last_reset_date + 1년 <= 오늘` (검증 Y-1 — "오늘이 입사일" 금지) |
| ② 월차 적립 | `hire_date + 1년 > 오늘` **AND** `last_monthly_grant_date + 1개월 <= 오늘` **AND** 누적 적립 < 11 |
| ③ 생일 반차 | 올해 생일 `<= 오늘` **AND** `last_birthday_grant_year < 올해` **AND** 올해 생일 `>= hire_date` |

③의 마지막 조건이 없으면 **입사 전에 지나간 생일까지 소급 지급된다** (3월 생일·7월 입사자가 입사 당일 0.5일을 받음).

## 3. 스키마 변경

`ddl-auto: update`라 컬럼 추가는 자동 반영된다. **기존 행은 전부 null이 되므로 폴백 규칙이 설계의 일부다.**

| 대상 | 컬럼 | 근거 | 기존 행 폴백 |
|---|---|---|---|
| `users` | `monthly_granted_count INT NOT NULL DEFAULT 0` | docs/02 메모 8 (아래 정정) | 0 + backfill SQL |
| `users` | `last_birthday_grant_year INT` | 신규 (중복 지급 방지) | null이면 미지급 — §2의 `>= hire_date` 조건이 소급을 막음 |
| `leave_reset_history` | `carried_bonus_days DECIMAL(4,1)` | docs/02 메모 10 (미결 → 확정) | 기본 0 |

`base_days` 역산으로 월차 적립 횟수를 알아내는 방법은 **쓰지 않는다** — 관리자가 `PATCH /api/users/{id}/base-days`로 연차를 직접 설정할 수 있어 역산값이 오염된다 (docs/02 메모 8이 지적한 그대로).

> **정정 (2026-08-08) — `last_monthly_grant_date DATE`가 아니라 `monthly_granted_count INT`다.**
>
> 원래는 마지막 지급 **날짜**를 저장하고 거기서 적립 횟수를 역산할 계획이었다(`MONTHS.between(hire_date, last_monthly_grant_date)`).
> **말일 클램프에서 이 역산이 깨진다:**
>
> ```
> 1/31 입사 → 1회차 지급일 = 1/31.plusMonths(1) = 2/28   (2/31이 없어 클램프)
> MONTHS.between(1/31, 2/28) = 0                          ← 지급했는데 0회로 읽힌다
> ```
>
> 역산이 0을 주므로 다음 실행이 1회차를 **다시** 지급하고, 그게 매달 반복된다.
> 그래서 횟수를 직접 센다. 날짜는 `hire_date + 횟수개월`로 언제든 되살릴 수 있으니
> 저장할 이유가 없다 — 파생값을 따로 들고 있다가 어긋나는 것이 리뷰 I-1의 원인이었다.
>
> 지급일을 **직전 지급일이 아니라 `hire_date`에서 매번 다시 더하는** 이유도 같은 클램프다.
> 직전 지급일 기준이면 `1/31 → 2/28 → 3/28 → 4/28`로 밀려 원래 날짜를 영영 회복하지 못한다.
> `hire_date` 기준이면 `2/28 → 3/31 → 4/30`으로 제자리를 찾는다.
>
> 기존 행은 `db/backfill-2026-08-08-scheduler.sql`이 채운다 — 온보딩 소급분(`base_days`)을
> 근거로 횟수를 복원하고, 올해 생일이 지난 사원은 지급 완료로 표시해 첫 실행의 전사 소급 지급을 막는다.
>
> 발견: Codex(leave-invariant-auditor) 착수 전 설계 감사 §5.

### config 키 — ✅ 2026-08-06 완료 (스케줄러 착수 전 선행 조건이었다)

설정 카탈로그가 코드(`PolicyConfigKey` enum)로 옮겨졌고 시딩·검증·화면이 거기서 파생된다 (docs/02 3-11).

|---|---|---|---|

**상한 판정 기준**: 이번 신청분이 아니라 **누적 당겨쓰기 총량**이다 —

얼마든지 누적되던 것이 I-3의 실제 결함이었다. 상한이 걸리므로 §5의 "재차감 후 잔여 음수" 폭도
실질적으로 `advance_max_days` 이내로 제한된다.

## 4. 기산일 리셋 — 계산 순서

리셋은 네 가지를 한 번에 처리하므로 순서를 고정한다.

```
1. 새 정책 연차 산정      newBase = calculateAnnualLeaveDays(만 근속년수)
2. 미래 승인분 재차감      newUse  = Σ(기산일 이후 날짜 × 단가)      ← §5
3. 보너스 이월 판정        newBonus = config on ? max(0, bonus − max(0, use − base)) : 0
4. 이력 기록 후 상태 전이   leave_reset_history 저장 → user.resetAnnualLeave(...)
```

> **~~4. 잔존 신청 스냅샷 정리 (advance_used_days = 0)~~ — 2026-08-06 폐기, 넣지 말 것.**
>
> 원래 이 단계가 필요했던 이유는 `restoreLeave`가 신청별 `advance_used_days` 스냅샷을 직접 빼서,
> 리셋으로 이미 0이 된 `advance_days`에서 또 빼면 음수가 됐기 때문이다(리뷰 I-4).
>
> 리뷰 I-1 수정으로 `advance_days`가 **파생값**이 됐다 — `User.syncAdvanceDays()`가
> `max(0, use − base − bonus)`로 매번 재계산하므로 스냅샷을 빼는 코드가 아예 없다.
> 따라서 이 단계는 불필요하고, 넣으면 감사 기록(`advance_used_days`)만 지운다.
>
> **대신 §5에 남는 다른 문제가 있다 → 리뷰 I-10.** 기산일을 걸친 신청은 2단계에서 기산일 이후
> 날짜만 새 `use_days`에 들어가는데, 복구는 `fresh.getDays()`로 신청 전체를 되돌린다.
> `2/28~3/2` 3일 신청이 리셋 후 취소되면 `use_days`가 −1이 되어 연차 1일이 공짜로 생긴다.
> **§5 구현과 같은 커밋에서** 복구량을 "기산일 이후 날짜의 일수"로 좁혀야 한다.

**이력을 먼저 쓴다.** `LeaveResetHistory.create()`가 리셋 *직전* 상태(`prev_base`·`prev_use`·`expired`·`advance_settled`)를 스냅샷하기 때문에, 상태를 먼저 바꾸면 기록할 원본이 사라진다.

`User.resetAnnualLeave`는 현재 `useDays`/`bonusDays`를 **무조건 0으로 밀고 있어 시그니처 변경이 필요하다**:

```java
// 현재 — 미래 승인분과 이월 보너스가 증발
resetAnnualLeave(BigDecimal newBaseDays, LocalDate resetDate)

// 변경
resetAnnualLeave(BigDecimal newBaseDays, BigDecimal carriedUseDays,
                 BigDecimal carriedBonusDays, LocalDate resetDate)
```

`AuthService.completeOnboarding`의 호출부 2곳도 함께 수정한다(둘 다 `ZERO, ZERO` 전달 — 온보딩 시점엔 이월할 것이 없다).

### 보너스 이월 공식 (메모 10)

```
이월분 = max(0, bonus − max(0, use − base))
```

`use`가 `base`를 초과한 만큼이 보너스에서 쓴 분량이다. 리셋 때 `use`가 0이 되므로, **이 보정 없이 `bonus`를 그대로 넘기면 이미 써버린 보너스가 부활한다.**

## 5. 미래 승인분 재차감 (결정 1)

### 왜 필요한가

```
기산일 3/1인 사원
 2/20  "3/10 연차" 신청·승인   →  use_days += 1  (선차감)
 3/1   리셋                    →  use_days = 0   ← 차감분 증발
 3/10  실제로 휴가 사용         →  아무 데도 반영 안 됨
결과: 새 연도 잔액 1일 과다 — 연차를 공짜로 한 번 더 받는다
```

docs/01 §2-7의 *"기산일 기준 미래에 사용한 연차 → 사용 연차에 포함해서 계산"*이 이것이고, docs/06이 v1에서 재사용 가치가 높다고 꼽은 `resetAndApplyPolicy`의 "미래 승인분 재차감"이 이것이다. 현재 코드에는 없다.

### 계산 규칙

**날짜 단위**로 집계한다 (신청 단위가 아니다).

```
newUseDays = Σ  단가(leave_type)
             where leave_date.day >= 기산일
               and status in (APPROVED, PENDING, CANCEL_PENDING)

단가: ANNUAL = 1.0,  HALF_AM = 0.5,  HALF_PM = 0.5
```

신청 단위로 하면 `2/28~3/2` 같이 기산일을 걸친 신청에서 **이전 연도에 이미 쓴 2/28까지 새 연도에 다시 차감**되어 사원이 손해를 본다. docs/01 §2-3의 *"기산일을 넘어가는 연차 신청은 다음 기산일에서 계산"*과도 날짜 단위 해석이 맞다.

대상 상태에 `PENDING`·`CANCEL_PENDING`을 포함하는 이유: 둘 다 **선차감이 유지되고 있는** 상태다 (`CANCELLED`·`REJECTED`는 이미 복구됨).

### 엣지 — 재차감 후 잔여 음수

`newBase − advance` 에서 다시 `newUse`를 빼면 음수가 될 수 있다. 이미 승인된 건이므로 **되돌리지 않고 음수를 허용**하되 `WARN` 로그를 남긴다. 메모 11의 `advance_max_days` 상한이 이 음수 폭을 실질적으로 제한한다.

> **정정 (2026-08-06).** 원래 이 자리에 *"여기서 다시 `advance_days`를 쌓으면 '다음 기산일에 또 정산'이 재귀적으로 이어져 추적이 불가능해진다"* 고 적혀 있었다. **다년 검산 결과 이 서술이 틀렸고, 반대로 advance로 이어받지 않으면 빚이 면제된다.**
>
> 근거는 리셋이 base를 **덮어쓴다**는 것이다 — `base = newBase − advance`는 가감이 아니다. 따라서 음수 base는 다음 리셋에서 그냥 버려진다.
>
> ```
> Y1  부여 15 · 사용 35            → advance 20
> 리셋  base = 15 − 20 = −5
>       advance를 0으로 닫으면       advance 0
>       재계산하면                   advance 5
> Y2  활동 없음
> 리셋  advance 0이었으면  base = 15 − 0  = 15   ← 5일 과다
>       advance 5였으면    base = 15 − 5  = 10
> 검산  Σ부여 45 − Σ사용 35 = 10                 ← 재계산 쪽이 정답
> ```
>
> 재귀도 일어나지 않는다. advance는 리셋마다 새 정책 연차만큼 줄어들어 **단조 감소**한다 (50 → 35 → 20 → 5 → 0, 4회에 종료).
>
> 미래 승인분(`newUse`)이 만드는 음수도 이중 차감이 아니다. 그 일수는 새 연도의 `use_days`에 **한 번만** 들어가고, 다음 리셓에서 `use`가 0으로 초기화되므로 초과분만 advance로 한 번 넘어간다.
>
> 따라서 `User.resetAnnualLeave`는 **다른 도메인 메서드와 똑같이 `syncAdvanceDays()`를 호출한다** — 잔액 불변식에 예외는 없다. 회귀 테스트 4건으로 고정했다 (`UserTest.resetAnnualLeave_*`). 상세는 docs/10 "1순위 수정 결과".
>
> ### ⚠️ 단, `carriedUse`가 들어오면 이 재계산만으로는 부족하다 (리뷰 I-11)
>
> 위 검산은 **현재 2인자 시그니처**(`newBase`, `resetDate`) 기준이다. §4대로 `carriedUse`를 넘기기 시작하면 **기존 `advance`와 `carriedUse`가 같은 신청에서 유래해 이중 반영될 수 있다.**
>
> ```
> 리셋 전  base=15, use=20, advance=5   (20일 전부 새 연도 날짜의 승인분)
> 리셋     base = 15 − advance 5 = 10
>          use  = carriedUse 20
>          재계산 → advance = 20 − 10 = 10
> 경제적 초과분은 5일인데 10일로 잡힌다 — 같은 20일을 두 번 센 것이다
> ```
>
> **✅ 결정 (2026-08-08) — ①안 채택, 아래 식으로 확정.**
>
> 채무를 `advance` 컬럼에서 읽지 않고 **"이전 연도에 귀속되는 사용분"에서 다시 구한다.**
> 이월되는 날짜는 새 연도에서 다시 차감되므로, 이전 연도 채무 계산에서 빼야 한다.
>
> ```
> oldYearUse  = use − carriedUse
> oldYearDebt = max(0, oldYearUse − base − bonus)
> newBase     = 정책연차 − oldYearDebt
> newUse      = carriedUse
> newBonus    = carriedBonus
> → syncAdvanceDays() 가 advance 재계산 (writer는 여전히 하나)
> ```
>
> | 시나리오 | 옛 방식(advance 직접 차감) | 새 식 | 정답 |
> |---|---|---|---|
> | base15·use20, 20일 전부 이월 | base 10 · advance **10** | 채무 0 → base 15 · advance **5** | 5 |
> | Y1 부여15·사용35, 이월 0 | base −5 · advance 5 | 채무 20 → base **−5** · advance 5 | −5 |
> | Y2 무활동 리셋 | base 10 | 채무 5 → base **10** | Σ부여45−Σ사용35 = **10** |
>
> `carriedUse = 0`이면 `oldYearDebt = max(0, use − base − bonus) = advance`라 **기존 2인자
> 리셋과 결과가 완전히 같다** — 회귀가 없다는 뜻이고, 테스트로 고정했다.
> `base`가 음수(=남은 빚)여도 식이 그대로 성립한다(Y2가 그 경우다).
>
> 부수 효과 — 채무를 잔액 3필드에서 유도하므로 **`advance`가 잔액과 어긋난 상태를 더 이상
> 받아들이지 않는다.** 기존 테스트 픽스처 3개가 실제로 불가능한 상태(`use=0`인데 `advance=3` 등)를
> 쓰고 있었고 이 변경으로 드러났다. 실제 데이터에서는 `syncAdvanceDays`가 유일한 writer라
> 발생할 수 없는 조합이다.
>
> <details><summary>검토했으나 채택하지 않은 나머지 2안</summary>

> 1. **(채택)** 리셋에서 차감할 `advance` 중 `carriedUse`와 겹치는 몫을 제외한다

> 3. 기존 채무와 미래 사용분을 **한 번씩만** 반영하는 통합 전이식을 세운다

## 6. catch-up 반복 (검증 Y-1)

서버가 며칠 꺼져 있어도 재기동 후 첫 실행에서 밀린 분을 소급 처리한다.

- **리셋**: `last_reset_date + 1년 <= 오늘`이 유지되는 동안 **while 루프로 반복**한다. 회차마다 `leave_reset_history`를 남겨 몇 년치가 소급됐는지 감사 가능하게 한다. (최근 기산일로 한 번에 점프하면 중간 연도 이력이 통째로 비어 검증이 불가능해진다.)
- **월차**: `last_monthly_grant_date`부터 경과한 만 개월 수만큼 반복 적립하되 누적 11일에서 멈춘다.
- **생일**: 연 1회라 반복이 없다. `last_birthday_grant_year`로 멱등성을 확보한다.

말일 처리는 `LocalDate.plusMonths`에 맡긴다 (1/31 → 2/28 자동 클램프). 2/29 생일은 `withYear`가 평년에 2/28로 조정한다.

## 7. 트랜잭션 경계

**유저 1명당 1트랜잭션** (`REQUIRES_NEW`). 진입점 스케줄러 메서드에는 `@Transactional`을 걸지 않는다.

`User`에 `@Version` 낙관적 락이 걸려 있어(검증 R-5), 배치가 도는 중 사원이 연차를 신청하면 충돌한다. 전체를 한 트랜잭션으로 묶으면 **수백 명 중 1명의 충돌로 전원이 롤백**된다. 유저별로 끊으면 실패자만 건너뛰고, 그 사원은 다음 실행에서도 catch-up 조건에 그대로 걸리므로 **자동으로 복구된다** — 별도 재시도 큐가 필요 없다.

실패는 삼키지 말고 `ERROR` 로그에 `userId`를 남긴다.

## 8. 테스트 가능성 — Clock 주입

스케줄러는 "1년 뒤"를 시뮬레이션해야 검증할 수 있는데 `LocalDate.now(KST)`가 하드코딩되면 불가능하다. docs/02 3-11(b)가 *"이전 프로젝트에서 스케줄러 검증을 못 했던 문제"*를 명시적으로 지적하고 있으므로, 같은 실수를 반복하지 않는다.

`Clock` Bean을 주입하고 테스트에서 `Clock.fixed()`로 날짜를 고정한다. **적용 범위는 스케줄러 관련 서비스로 한정**한다 — 기존 `AuthService` 등은 건드리지 않고, 필요해지면 그때 확산한다.

```java
@Bean
public Clock clock() {
    return Clock.system(ZoneId.of("Asia/Seoul"));
}
```

## 9. 패키지 구조

```
domain/leave/scheduler/
  LeaveScheduler.java              @Scheduled 진입점 (트리거 전용, 로직 없음)
domain/leave/service/
  AnnualLeaveResetService.java     ① 기산일 리셋
  MonthlyLeaveGrantService.java    ② 월차 적립
  BirthdayLeaveGrantService.java   ③ 생일 반차
config/
  SchedulingConfig.java            @EnableScheduling + Clock Bean
```

잡별로 서비스를 나누는 이유는 테스트 격리다. 한 클래스에 세 잡을 넣으면 `Clock`·config·리포지토리 의존이 뒤섞여 단위 테스트가 통합 테스트가 된다.

> **구현 시 정정 2건 (2026-08-08).**
>
> 1. **프로필 가드는 `SchedulingConfig`가 아니라 `LeaveScheduler`에 붙였다.**
>    `SchedulingConfig`를 통째로 막으면 테스트 컨텍스트에서 `Clock` 빈이 사라져 기동이 깨진다.
>    막아야 하는 것은 크론 트리거지 시계가 아니다.
> 2. **사원별 루프는 서비스가 아니라 `LeaveScheduler`에 있다** — §9의 "로직 없음"에서 이 부분만 벗어난다.
>    Spring AOP는 자기 호출에 프록시를 적용하지 않으므로, 서비스가 자기 `reset()`을 루프로 부르면
>    §7이 요구하는 **사원 1명당 `REQUIRES_NEW` 트랜잭션이 걸리지 않는다.** 외부(스케줄러)에서
>    빈을 거쳐 호출해야 경계가 실제로 생긴다. 잡별 규칙 자체는 전부 서비스에 있다.
>
> `Clock` 주입 범위도 진입점 하나로 좁혔다. 잡 서비스는 `Clock`이 아니라 계산된 `today`를 인자로 받는다 —
> 단위 테스트가 시계를 흉내 낼 필요 없이 날짜만 넘기면 된다.

**`LeaveScheduler`는 `@Profile("!test")`로 막는다** — H2 테스트 실행 중 스케줄러가 실제로 돌면 테스트가 서로를 오염시킨다.

`syncHolidaysForNewYear`(매년 1/1 00:05)도 같은 진입점에 있다 — docs/12 ②가 남겨 둔 "매년 자동 동기화"다.

## 10. 이메일 연동

이메일 발송 인프라가 아직 없으므로(코드 0건) 스케줄러는 **`// TODO(email)` 시밍만 남긴다**. 연차·복리후생 서비스가 이미 쓰고 있는 패턴과 동일하게 간다.

- 생일 반차 지급 → 당사자 + SYSTEM_ADMIN (요구사항 11)
- 기산일 리셋 → 요구사항에 없음. 소진 안내는 별도 리마인더(docs/01 §2-8) 소관이다.

## 11. 구현 순서

0. **선행 — `advance_days` 재계산 방식 전환** (리뷰 I-1·I-2). 현재 `restoreLeave`/`addBonusDays`가 스냅샷 차감이라 **신청 2건 이상이 얽히면 `advance_days`가 실제와 어긋난다.** 틀린 값 위에서 리셋이 돌면 오차가 그대로 확정되므로 스케줄러보다 먼저 고친다. `max(0, use − base − bonus)` 재계산으로 바꾸면 순서 의존성이 사라진다. 기존 74건이 이 케이스를 안 덮으므로(리뷰 T-2) **2건 시나리오 테스트를 먼저 추가**할 것.
1. 스키마 3건 + config 2키 + `ErrorCode` (§3)
2. `advance_max_days` 상한 검증 — `deductLeave` 경로 (메모 11 / 리뷰 I-3). `LeaveCreateRequest`에 `@Size` 상한도 함께
3. `resetAnnualLeave` 시그니처 변경 + `AuthService` 호출부 2곳 (§4)
4. 미래 승인분 재차감 쿼리 + 잔존 스냅샷 정리 — `LeaveRequestRepository` (§4·§5)
