# 퇴직자 데이터 파기 설계 (2026-09-07)

> 대상: `docs/08` **검증 Y-4**의 "퇴직자 3년 후 파기 절차 미구현", `docs/01 §2-9` 퇴직자 데이터 보존.
> 현재 상태·우선순위의 단일 원본은 `docs/12`다. 이 문서는 착수 전 설계와 결정 근거를 보존한다.
>
> **사용자 결정 (2026-09-07)**
> 1. 파기 방식을 **정책으로 뺀다** — 자동 삭제 / 수동 삭제 중 택1. 자동일 때만 "몇 년 이상" 옵션을 보여준다
> 2. 파기 범위는 **익명화 + 자유 텍스트 본문까지 파기**
> 3. 알림 메일은 **자동 삭제 모드에서만** 보낸다

## 1. 지금 상태와 두 법의 상충

`retired_at`과 `is_active`만 있고 **파기 관련 코드는 하나도 없다.** 화면·API·스케줄러 모두 없다.
퇴직자는 영구히 남는다.

두 법이 서로 반대 방향으로 민다.

| 법 | 요구 |
|---|---|
| 근로기준법 제42조 | 근로자 명부·임금대장 등 **3년 보존** |
| 개인정보보호법 제21조 | 보유 목적이 끝나면 **지체 없이 파기** |

그래서 **3년은 하한이지 파기 시점이 아니다.** 3년이 지나면 보존 의무가 풀리고 파기 의무가 켜진다.
`docs/01 §2-9`가 "3년 이상 보존 후 처분 권한은 SYSTEM_ADMIN에게"라고 적은 것이 이 뜻이다 —
**원안부터 자동 삭제가 아니라 사람이 정하는 구조였다.**

**3년 하한은 정책 값이 아니라 상수다.** 법이 정한 것이라 관리자가 2년으로 낮출 수 있으면 안 된다.
정책으로 여는 것은 "3년 이상 중 언제"다.

## 2. 정책 키 2개

| 키 | 타입 | 기본 | 범위 | 설명 |
|---|---|---|---|---|
| `retiree_purge_mode` | ENUM | `MANUAL` | `MANUAL`/`AUTO` | 퇴직자 개인정보 파기 방식. `MANUAL`은 관리자가 목록에서 직접 파기, `AUTO`는 기간이 지나면 스케줄러가 파기 |
| `retiree_purge_years` | INTEGER | `3` | `3 ~ 10` | **`AUTO`일 때만 쓴다.** 퇴직 후 몇 년이 지나면 자동 파기할지. 하한 3은 근로기준법 보존 의무라 더 낮출 수 없다 |

**기본값을 `MANUAL`로 두는 이유**: 파기는 되돌릴 수 없고, 이 시스템은 아직 운영 전이다.
관리자가 의식적으로 `AUTO`를 켜기 전까지는 아무것도 사라지지 않아야 한다.

### 조건부 노출 — 카탈로그에 없던 개념 하나가 필요하다

사용자 요구는 "`AUTO`일 때만 연수 옵션을 보여 달라"다. 그런데 지금 `PolicyConfigKey`에는
**키 사이의 의존 관계를 표현할 방법이 없다.** 프론트에 `if (key === 'retiree_purge_years')`를
쓰면 CLAUDE.md가 금지한 **키 이름 하드코딩**이 된다.

그러므로 카탈로그에 메타데이터를 하나 더한다.

```java
// PolicyConfigKey — 선택 필드. 없으면 항상 보인다.
visibleWhen = new VisibleWhen("retiree_purge_mode", "AUTO")
```

`GET /api/admin/configs`가 이 정보를 함께 내려주고, 관리자 화면은 **키 이름을 모른 채**
"의존 키의 현재 값이 조건과 다르면 숨긴다"는 규칙 하나로 렌더한다. 다음에 같은 요구가 와도
enum 한 줄로 끝난다 — 정책 카탈로그를 만든 이유가 그것이었다.

**숨김은 표시 규칙이지 검증이 아니다.** 서버는 `MANUAL`일 때도 `retiree_purge_years` 값을 저장·검증한다
(모드를 다시 `AUTO`로 켰을 때 값이 살아 있어야 한다).

## 3. 대상 판정 — 모드마다 다르다

| 모드 | 목록에 보이는 사람 | 파기 실행 |
|---|---|---|
| `MANUAL` | **퇴직자 전원** (경과 연수를 함께 표시) | 관리자가 행마다 실행. **3년 미만은 버튼이 잠긴다** |
| `AUTO` | 퇴직 후 `retiree_purge_years`년 경과자 | 스케줄러가 실행 |

수동 모드에 별도 임계값을 두지 않는 이유: 관리자가 "3년 2개월 지난 사람"을 보고 판단하는 것이
이 모드의 목적이다. 임계값으로 걸러 버리면 판단할 대상 자체가 안 보인다.

공통 제외 조건:

- **이미 파기된 사람** (`purged_at != null`) — 재파기는 의미가 없다
- **보류된 사람** (`purge_hold_reason != null`) — 진행 중인 분쟁·미지급 정산·재입사 예정처럼
  보존 사유가 남은 경우. 보류는 **사유를 반드시 적게** 한다. 사유 없는 보류는 잊혀진 데이터가 된다
- **재직자** (`is_active = true`) — 퇴직 복구된 사람은 대상에서 빠진다

## 4. 파기 범위 — 익명화 + 본문까지

행을 지우지 않는다. **누가**를 지우고 **무엇을**은 남긴다.

| 대상 | 처리 | 이유 |
|---|---|---|
| `users.name` | `퇴직사원#{id}` | 화면·이력이 이름을 참조하므로 NULL이면 렌더가 깨진다 |
| `users.email` | `deleted-{id}@invalid` | UNIQUE 제약이 있어 NULL로 못 둔다. `.invalid`는 예약 TLD라 실제로 도달하지 않는다 |
| `users.birth_day` · `hire_date` · `position` | `NULL` | 생일·입사일·직책은 식별정보다 |
| `users.department_id` | **유지** | 부서는 개인정보가 아니고 부서별 통계의 축이다 |
| `users.role` · 잔액 4필드 | **유지** | 통계와 과거 정산 검증에 쓰인다 |
| `leave_requests.reason` | `NULL` | "어머니 병원 동행" 같은 사생활이 그대로 남는다 |
| `welfare_requests.reason` | `NULL` | 같은 이유 |
| `leave_action_history` · `welfare_action_history`의 사유·코멘트 | `NULL` | 반려 사유에 개인 사정이 적힌다 |
| `email_history.title` · `content` | `NULL` | 본문에 이름·날짜·사유가 전부 들어 있다 (docs/08 Y-4가 지적한 자리) |
| `admin_audit_log` | **행·값 모두 유지** | 감사 기록이다. "누가 이 사람을 퇴직시켰나"가 사라지면 감사가 성립하지 않는다. 보존 근거가 개인정보 보호보다 우선하는 예외이며, 이 판단을 문서에 남긴다 |

`users.purged_at`에 파기 시각을 남긴다. 이 컬럼이 **재파기 방지이자 파기 증적**이다.

### 파기 뒤 그 사람이 다시 로그인하면

이메일이 바뀌었으므로 **신규 가입자로 들어온다.** 과거 이력과 연결되지 않는다.
그것이 파기의 정의이고, 의도된 동작이다. 재입사 예정자는 §3의 **보류**로 막아야 한다.

### 상태 전이는 도메인 메서드 하나로

`User.purge(LocalDateTime at)` 하나가 `users`의 모든 필드를 바꾼다. Setter를 쓰지 않는다.
이력 테이블 쪽은 리포지터리의 벌크 UPDATE로 처리하되 **한 트랜잭션 안**에서 끝낸다 —
사원 정보만 익명화되고 메일 본문이 남는 중간 상태가 커밋되면 안 된다.

## 5. 자동 모드 — 스케줄러 ⑤

`LeaveScheduler`의 일일 잡에 **다섯 번째로, 맨 뒤에** 붙인다.

```
① 기산일 리셋 → ② 월차 적립 → ③ 생일 반차 → ④ 연차 소진 안내 → ⑤ 퇴직자 파기
```

- **맨 뒤인 이유**: 앞 네 잡은 재직자 잔액을 다루고 ⑤는 퇴직자를 다룬다. 의존은 없지만,
  파기가 앞 잡의 입력(사원 목록)을 바꾸므로 같은 날 실행 순서가 뒤바뀌면 로그 해석이 어려워진다
- **사원 1명 = 1트랜잭션** (`REQUIRES_NEW`). 한 명의 실패가 전원을 롤백시키면 안 된다.
  루프는 진입점에 둔다 — 서비스가 자기 메서드를 부르면 프록시를 안 타 경계가 생기지 않는다
- `retiree_purge_mode != AUTO`면 **아무것도 하지 않고 즉시 끝낸다**

### 예고 후 파기

자동 모드는 사람이 누르지 않는데 결과가 되돌릴 수 없다. 그래서 **30일 예고**를 둔다.

```
D-30  예고 메일 — "N명이 30일 뒤 파기됩니다" + 대상 목록 + 보류 방법
D-0   파기 실행 → 결과 메일 — 몇 명이 파기됐는지
```

예고 기간은 상수로 둔다(정책 키를 늘리지 않는다). 예고를 받고 30일 안에 보류를 걸면 대상에서 빠진다.

수신자는 **재직 중인 SYSTEM_ADMIN 전원**이다. `EmailType.NOTICE`를 재사용하므로 ENUM 확장이 없다.
중복 발송 방지는 리마인더(④)가 쓰는 방식과 같은 모양으로 — 사원·기간 키 UNIQUE로 막는다.

**수동 모드는 메일을 보내지 않는다** (사용자 결정 3). 대신 관리자 화면에 **대상 건수 배지**를
띄운다. 아무도 보지 않는 채로 개인정보가 남는 것을 막는 최소 장치다.

## 6. API

| Method | URL | 설명 | 권한 |
|---|---|---|---|
| GET | `/api/users/retired` | **기존 확장** — 경과 연수·파기 가능 여부·보류 사유·`purged_at`을 함께 내려준다 | SA |
| POST | `/api/users/{id}/purge` | 수동 파기 실행 | SA |
| POST | `/api/users/{id}/purge-hold` | 보류 설정 (사유 필수) | SA |
| DELETE | `/api/users/{id}/purge-hold` | 보류 해제 | SA |

새 컨트롤러를 만들지 않는다 — 퇴직·복구가 이미 `UserController`에 있고 파기는 그 연장선이다.

에러 코드 신규 3개:

- `PURGE_RETENTION_NOT_MET`(400) — 3년 미만. "퇴직 후 3년이 지나야 파기할 수 있습니다."
- `PURGE_ON_HOLD`(400) — 보류된 사원. 사유를 함께 보여준다
- `ALREADY_PURGED`(400) — 이미 파기됨

**본인 파기는 막는다** — 자기 퇴직 금지(`CANNOT_RETIRE_SELF`)와 같은 계열이고, 퇴직자만 대상이므로
관리자가 자기를 파기하려면 먼저 퇴직해야 해서 자연히 걸리지만, 서버에서 한 번 더 막는다.

## 7. 화면

`AdminMembersPage` **퇴직 탭**을 확장한다. 새 화면을 만들지 않는다.

- 행마다 **퇴직 후 경과 연수** 표시 (`2년 4개월`)
- **파기** 버튼 — 3년 미만이면 비활성 + 사유 툴팁("퇴직 후 3년이 지나야 파기할 수 있습니다")
- **보류/해제** — 보류된 행은 사유를 함께 보여준다
- 이미 파기된 행은 `퇴직사원#42`로 보이고 파기 버튼이 사라진다
- 탭 라벨에 **파기 대상 건수 배지** (수동 모드에서 특히 중요)

### 확인 모달 — 되돌릴 수 없으므로 한 단계 더

파기 버튼은 바로 실행하지 않는다. 모달에서 **사원 이름을 직접 입력**해야 실행된다.
퇴직·복구는 확인만으로 되지만 그건 되돌릴 수 있고, 파기는 아니다.
모달에 **무엇이 사라지고 무엇이 남는지**를 그대로 적는다 — §4 표의 요약.

## 8. 스키마 변경

**엔티티를 바꾸면 두 가지를 함께** (CLAUDE.md 배포 절차).

`users` 신규 컬럼 2개:

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `purged_at` | `datetime(6) NULL` | 파기 시각. 재파기 방지이자 증적 |
| `purge_hold_reason` | `varchar(255) NULL` | 보류 사유. NULL이면 보류 아님 |

`AdminAction`에 **`USER_PURGED`** 추가 — **이것도 스키마 변경이다.** `admin_audit_log.action`이
MySQL `ENUM(...)`이라 값 목록을 넓히지 않으면 첫 파기에서 `Data truncated`로 터진다.
`ddl-auto: validate`는 ENUM 값 목록까지 보지 않아 **기동은 정상이고 실행 시점에 500이 난다.**

그래서 backfill에 `ALTER TABLE ... ADD COLUMN` 2건과 `MODIFY COLUMN` 1건을 함께 넣는다.
`SchemaEnumConsistencyTest`가 `schema.sql` 쪽 누락은 잡아 주지만 **backfill의 `MODIFY COLUMN`은
검사하지 못하므로** 사람이 확인한다.

## 9. 감사와 되돌릴 수 없음

- 파기 1건마다 `admin_audit_log`에 `USER_PURGED` 기록. 자동 모드는 actor를 시스템으로 남긴다
- 감사 로그의 `before` 값에 **이름을 남기지 않는다** — 파기해 놓고 로그에 이름을 적으면 파기가 아니다.
  대상은 `user_id`로만 식별한다
- **복구 기능을 만들지 않는다.** 만들 수 있는 것이 없다 — 원본이 사라졌다

## 10. 범위 밖 (이 설계가 다루지 않는 것)

- **재직자의 `email_history` 보존 기간** — `docs/08` Y-4가 함께 지적했지만 다른 주제다.
  퇴직자 메일 본문은 이 설계로 닫히고, 재직자 메일을 몇 년 두는지는 별도로 정한다
- **DB 백업 안의 개인정보** — 파기 후에도 백업에는 남는다. 백업 보존 주기와 함께 다룰 문제다.
  이 설계는 운영 DB만 책임진다. **운영 문서에 명시해야 한다**
- **퇴직자 본인의 열람·삭제 요구권 대응** — 절차 문서의 영역이지 코드가 아니다

## 11. 테스트 계획

1. 3년 미만 파기 시도 → `PURGE_RETENTION_NOT_MET`, 데이터 그대로
2. 보류된 사원 파기 시도 → `PURGE_ON_HOLD`
3. 이미 파기된 사원 재파기 → `ALREADY_PURGED`
4. 파기 성공 → §4 표의 필드가 전부 바뀌었는지 **한 건씩** 확인 (사원·연차 사유·복리 사유·이력 코멘트·메일 본문)
5. 파기해도 `admin_audit_log` 행과 값이 남는지
6. 파기 후 연차 사용 통계 조회가 여전히 동작하는지 (FK 무결성)
7. 자동 모드: `MANUAL`이면 스케줄러가 아무것도 하지 않는다
8. 자동 모드: 경과자만 파기하고 보류자는 건너뛴다
9. 자동 모드: 한 명이 실패해도 나머지가 파기된다 (트랜잭션 경계)
10. 예고 메일이 30일 전에 한 번만 나가는지
11. 수동 모드에서는 메일이 나가지 않는지
12. 정책 화면: `MANUAL`이면 연수 옵션이 **숨겨지고**, `AUTO`로 바꾸면 나타난다
13. 화면: 3년 미만 행의 파기 버튼 비활성 + 사유 표시
14. 화면: 확인 모달에서 이름을 정확히 입력해야 실행된다

## 12. 구현 순서

1. **W1 정책·스키마** — 정책 키 2개와 `visibleWhen` 메타데이터, `users` 컬럼 2개, `AdminAction` 확장,
   `schema.sql`·backfill. 관리자 설정 화면의 조건부 노출까지
2. **W2 파기 도메인** — `User.purge()`, 이력·메일 본문 벌크 파기, 대상 판정, 감사 기록. 테스트 1~6
3. **W3 API·화면** — 엔드포인트 4개, 퇴직 탭 확장, 확인 모달, 배지. 테스트 13~14
4. **W4 자동 모드** — 스케줄러 ⑤, 예고·결과 메일, 중복 방지. 테스트 7~11

W1을 먼저 독립적으로 넣는 이유는 **`AUTO`를 켤 수단이 없는 동안에는 아무것도 파기되지 않기** 때문이다.
기본값이 `MANUAL`이므로 W4가 들어오기 전까지 이 기능은 조용히 잠겨 있다.

## 13. 이 설계가 정한 것 (바꾸려면 여기부터)

1. 3년은 **상수**, 정책으로 여는 것은 "3년 이상 중 언제" (§1)
2. 기본 모드는 **`MANUAL`** — 의식적으로 켜기 전에는 아무것도 사라지지 않는다 (§2)
3. 수동 모드는 **퇴직자 전원**을 보여주고 3년 미만만 버튼을 잠근다 (§3)
4. 파기 = **익명화 + 자유 텍스트 본문 파기**, `admin_audit_log`는 예외로 보존 (§4)
5. 자동 모드는 **30일 예고 후** 실행하고, 메일은 자동 모드에서만 (§5)
6. 확인 모달에서 **이름 직접 입력** (§7)
7. **복구 기능은 만들지 않는다** (§9)
