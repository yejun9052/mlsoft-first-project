# 미래 차감 연차 분리 설계 (2026-09-07)

> 대상: `docs/12` ⑨절 **B-1 미래 차감 연차 분리** (별칭 `USER-1`).
> 사용자 결정: **다음 기산일 이후 날짜의 연차는 현재 회차에서 빼지 않고 따로 뺀다.**
> 현재 상태·우선순위의 단일 원본은 `docs/12`다. 이 문서는 착수 전 설계와 검산을 보존한다.

## 1. 왜 지금 문제인가

`LeaveService.apply()`는 날짜를 `단가 × 날짜 수` 한 덩어리로 만들어 `User.deductLeave()`에 넘긴다.
주말·과거·공휴일만 보고 **기산일이라는 개념이 없다** (`LeaveService.java:110-134`).

그래서 셋이 따라온다.

1. 내년 3월 연차를 예약하면 **올해 잔액을 먹는다** — 잔여 3일로 내년 3월 3일을 예약하면 올해 12월에 쓸 연차가 0이 된다
2. 잔여가 0이면 **내년 연차를 아예 예약할 수 없다** — 아직 부여되지도 않은 배정인데 `INSUFFICIENT_LEAVE_BALANCE`로 막히거나 당겨쓰기 상한을 먹는다
3. **얼마나 먼 미래까지 낼 수 있는지 제한이 없다** — 2030년 날짜를 넣으면 잔액이 4년간 묶인다

**반대쪽은 이미 되어 있다.** 리셋 잡은 회차마다 `leave_dates.day >= resetDate`를 날짜 단위로 다시 세어
새 회차 `use_days`로 넘긴다(`AnnualLeaveResetService.applyOneRound`, docs/09 §5). 복구도 날짜를 본다 —
`restoreCurrentYearPortion()`이 `leave.daysOnOrAfter(user.lastResetDate)`만 되돌린다
(`LeaveService.java:427-446`). **비어 있는 것은 신청 시점 하나다.**

## 2. 핵심 규칙 — 회차 창(cycle window) 하나로 통일

회차는 `[lastResetDate, lastResetDate + 1년)` 반열린 구간이다. 잔액을 건드리는 **세 지점이 같은 창을 쓴다.**

```
현재 회차분  =  Σ 단가(leaveType)   where  lastResetDate <= day < lastResetDate + 1년
다음 회차분  =  Σ 단가(leaveType)   where  nextResetDate <= day < nextResetDate + 1년
                                          (nextResetDate = lastResetDate + 1년)
```

| 지점 | 지금 | 바뀐 뒤 |
|---|---|---|
| 신청 차감 | 전체 날짜 | **현재 회차분만** `use_days`에 더한다 |
| 취소·반려 복구 | `day >= lastResetDate` 전부 | **현재 회차분만** 되돌린다 (상한이 생긴다) |
| 리셋 이월(`carriedUse`) | `day >= resetDate` (상한 없음) | 그 회차 창 `[resetDate, resetDate+1년)`으로 **상한을 준다** |

불변식은 한 줄로 말할 수 있게 된다.

> **`use_days` = 살아 있는 신청(APPROVED·PENDING·CANCEL_PENDING) 중 현재 회차 창 안에 있는 날짜의 합.**

지금은 이 문장이 참이 아니다 — 미래 회차 날짜가 섞여 있다.

### 필드를 만들지 않는다

`future_use_days` 같은 컬럼을 두지 않는다. **파생값을 필드로 두면 `advance_days`에서 겪은 것과 같은
함정이 생긴다**(리뷰 I-1·I-2·I-8) — 잔액을 바꾸는 도메인 메서드마다 재계산을 붙여야 하고 하나라도
빠지면 조용히 어긋난다. 다음 회차 예약분은 **필요할 때 `leave_dates`에서 집계한다.** 집계 쿼리는
리셋이 이미 쓰는 것과 같은 모양이라 새 개념이 아니다.

## 3. 리셋 식 재유도 — 여기가 이 설계의 위험 지점이다

`docs/12`가 경고한 자리다. 리셋은 검산이 끝나 있으므로 **왜 바꿔도 되는지**를 먼저 적는다.

현재 채무 식은 이렇다 (`User.carryOverDebt`, `User.java:391-405`).

```java
debt = max(0, useDays − carriedUse − baseDays − bonusDays)
```

`useDays`에 미래 회차 날짜가 섞여 있으니 `carriedUse`를 **빼서** 지난 회차 몫만 남기는 식이다.
새 모델에서는 미래 회차 날짜가 애초에 `useDays`에 들어가지 않는다. 그러므로 `carriedUse`를 빼면
**두 번 빼는 것**이 된다. 식은 이렇게 줄어든다.

```java
debt = max(0, useDays − baseDays − bonusDays)     // == 리셋 직전의 advance_days
```

즉 **채무는 리셋 직전 `advance_days` 그 자체**가 된다. 파생 필드와 채무 계산이 같은 식으로 수렴하므로
계산 경로가 하나 줄어든다.

같은 뺄셈이 **세 곳**에 있다. 셋 다 같은 이유로 `useDays` 하나로 줄어든다.

| 위치 | 지금 | 바뀐 뒤 |
|---|---|---|
| `User.carryOverDebt(carriedUse)` | `max(0, use − carriedUse − base − bonus)` | `max(0, use − base − bonus)` |
| `LeaveResetHistory.create()`의 `oldYearUse` | `use − carriedUse` | `use` |
| `AnnualLeaveResetService.carriedBonus()`의 `oldYearUse` | `use − carriedUse` | `use` |

**셋을 함께 바꿔야 한다.** 하나만 고치면 이월 보너스와 소멸 일수가 채무와 어긋난 기준으로 계산된다.

### 검산 — 경계에서 결과가 달라지지 않는다

**① 채무 없음**: `base 15`, 현재 회차 사용 10, 다음 회차 예약 3

```
지금    use=13(전부 선차감), carriedUse=3 → debt = max(0, 13−3−15) = 0
        newBase = 15−0 = 15, newUse = 3        → 잔여 12
바꾼 뒤 use=10(다음 회차 미차감), carriedUse=3 → debt = max(0, 10−15) = 0
        newBase = 15−0 = 15, newUse = 3        → 잔여 12   ✅ 동일
```

**② 당겨쓰기 5일**: `base 15`, 현재 회차 사용 20, 다음 회차 예약 3

```
지금    use=23, carriedUse=3 → debt = max(0, 23−3−15) = 5
        newBase = 10, newUse = 3               → 잔여 7
바꾼 뒤 use=20, carriedUse=3 → debt = max(0, 20−15) = 5
        newBase = 10, newUse = 3               → 잔여 7    ✅ 동일
```

**③ docs/09 §5 정정 블록의 다년 검산**(미래 예약 0건): `carriedUse = 0`이라 두 식이 글자 그대로 같다.
그 블록의 결론(**리셋도 `syncAdvanceDays()`를 예외 없이 호출한다**)은 그대로 유효하다.

**④ 여러 회차 catch-up**: 서버가 여러 해 꺼져 있던 경우, 지금은 1회차 집계가 `day >= R1` 무제한이라
**2회차 이후에 속한 날짜까지 1회차 `use`로 잡힌다.** 최종 상태는 다음 회차가 덮어써서 같아지지만
`leave_reset_history`의 중간 행은 사실과 다르게 남는다. 창으로 상한을 주면 회차별 이력이 맞는다 —
**이 변경은 이력 정확도를 높이는 쪽이다.**

## 4. 다음 회차 예약의 한도

아직 부여되지 않은 배정이므로 "잔여"가 없다. 무제한으로 두면 기산일에 이월된 순간 `use > base`가 되어
**당겨쓰기 상한(`advance_max_days`)을 신청 시점에 한 번도 통과하지 않고** 빚이 생긴다.

예상 가용량을 보수적으로 계산해 그 안에서만 받는다.

```
nextCycleAllowance = max(0, policyDays(다음 회차 근속년수) − 현재 advance_days)
검증               : 이미 예약한 다음 회차분 + 이번 신청의 다음 회차분 <= nextCycleAllowance
```

- `policyDays`는 리셋이 쓰는 것과 **같은 계산**이다 — `YEARS.between(hireDate, nextResetDate)`로 근속년수를
  구해 정책 표를 본다(`AnnualLeaveResetService.applyOneRound`). 지금은 리셋 안에 묻혀 있으므로
  **공용 메서드로 빼내 신청 경로와 공유한다.** 두 벌로 계산하면 정책이 바뀔 때 한쪽만 따라간다
- `advance_days`를 미리 빼는 이유: 리셋이 `newBase = policyDays − debt`로 부여하므로, 지금 빚이 있으면
  다음 회차 배정이 그만큼 줄어든다. 예상치는 **낙관적이면 안 된다**
- 생일 반차 같은 `bonus`는 예측하지 않는다 (그날 재직 중일지 모른다)
- **다음 회차에는 당겨쓰기를 적용하지 않는다.** 당겨쓰기는 "이번 회차 배정을 넘겨 쓰는 것"이고,
  다음 회차 예약은 이미 다음 배정을 쓰는 행위다. 겹쳐 쓰면 2회차 앞선 빚이 된다

넘으면 새 에러 코드 `NEXT_CYCLE_RESERVATION_EXCEEDED`(400)로 거부한다.

## 5. 예약 가능 범위 — 다음 1회차까지

**다음 회차 창을 넘어가는 날짜(`day >= nextResetDate + 1년`)는 거부한다.** 새 에러 코드
`LEAVE_DATE_TOO_FAR`(400).

- 회차 버킷이 **현재·다음 둘로 고정**되어 집계·검증·표시가 각각 한 벌로 끝난다. 3회차 이상을 허용하면
  회차마다 예상 배정을 추정해야 하는데, 그 시점의 정책·근속년수·빚을 지금 알 수 없다
- 2030년 날짜로 잔액을 묶는 문제(§1-3)가 같이 닫힌다
- 끄고 싶을 때를 위해 정책 키 하나를 둔다

## 6. 정책 키 (신규 1개)

`PolicyConfigKey`에 상수 한 줄을 넣으면 시딩·검증·관리자 화면 렌더가 따라온다.

| 키 | 타입 | 기본 | 설명 |
|---|---|---|---|
| `next_cycle_reservation_enabled` | BOOLEAN | `true` | 다음 기산일 이후 날짜의 연차 신청 허용 여부. `false`면 현재 회차 안에서만 신청할 수 있다 |

`false`일 때는 §5의 거부를 다음 회차 시작일부터 적용한다(=`day >= nextResetDate` 거부).
**읽는 곳이 생기므로 `ACTIVE`로 넣는다** — `PENDING_FEATURE`로 두면 안 된다.

## 7. 응답과 화면

`LeaveSummaryResponse`에 다음 회차 블록을 더한다 (`nextResetDate`는 이미 있다).

```java
public record LeaveSummaryResponse(
    BigDecimal baseDays, BigDecimal bonusDays, BigDecimal useDays,
    BigDecimal remainingDays, BigDecimal pendingDays, BigDecimal advanceDays,
    LocalDate nextResetDate,
    // 신규
    BigDecimal nextCycleReservedDays,   // 다음 회차 창에 예약된 일수
    BigDecimal nextCycleAllowanceDays,  // §4의 예상 가용량
    boolean nextCycleReservationEnabled // 정책 키 값 — 화면이 입력을 막는 근거
) {}
```

**현재 잔여 숫자는 바뀌지 않는다.** 다음 회차 예약분이 빠지므로 오히려 사원이 기대하는 값이 된다.
표시는 잔여 옆에 한 줄을 덧붙이는 방식으로 통일한다 — `잔여 12일 · 다음 회차 예약 3일`.

같은 요약을 읽는 화면 5곳이 같은 문구를 써야 한다(QA 7-7).

신청 패널이 가장 중요하다. 지금은 선택 날짜 전부를 잔여에서 빼서 보여주므로 **화면과 서버의 계산이
어긋나게 된다.**

## 8. 기존 데이터 보정

이미 선차감된 미래 회차분이 `use_days`에 남아 있다. 배포 시 1회 보정한다.

`db/backfill-<날짜>-future-leave-split.sql`:

1. 사원별로 `use_days`를 **현재 회차 창 안의 살아 있는 날짜 합**으로 다시 계산해 대입
   (상태 `APPROVED`·`PENDING`·`CANCEL_PENDING`, `last_reset_date <= day < last_reset_date + 1년`)
2. `advance_days = GREATEST(0, use_days − base_days − COALESCE(bonus_days,0))` 재계산
3. 보정 전후를 세는 검증 쿼리를 같은 파일에 남긴다 — **몇 명의 `use_days`가 얼마나 줄었는지**

재계산이라 자연히 멱등이다(여러 번 돌려도 같은 값으로 수렴한다).
**운영 데이터가 아직 없으므로 지금이 가장 싼 시점이다.**

## 9. 엣지

- **기산일을 걸친 신청**(2/28~3/2, 기산일 3/1): 날짜 단위라 2/28은 현재 회차, 3/1~3/2는 다음 회차로 쪼개진다. `leave_dates` 구조라 그대로 된다
- **`lastResetDate == null`**: 온보딩 미확정이라 `OnboardingCheckInterceptor`가 신청을 막는다. 방어적으로 전체를 현재 회차로 본다(기존 `daysOnOrAfter` 동작과 같다)
- **윤년**: `plusYears(1)`이 2/29를 2/28로 클램프한다. 기존 리셋·리마인더와 같은 규칙을 쓰므로 새 불일치는 생기지 않는다
- **리셋 직후 취소**: 복구는 항상 **그때의** 창으로 다시 계산한다. 리셋 전에 다음 회차였던 날짜는 리셋 후 현재 회차가 되어 있고, 그 사이 리셋이 `use_days`에 넣었으므로 되돌릴 대상이 맞다
- **지난 회차 날짜만 있는 소급 취소**: 창 밖이라 복구량 0. 리셋이 이미 그 회차 `use`를 지웠으므로 옳다 (현재 동작과 동일)
- **월차 대상(1년 미만)**: 다음 회차 = 입사 1주년이고 그 회차 배정은 정책 연차다. 월차 적립은 현재 회차에만 붙으므로 예상 가용량 계산에 넣지 않는다
- **소진 안내 ④잡**: 잔여 식이 그대로라 영향 없다. 안내 메일에 다음 회차 예약을 적을지는 후속 판단

## 11. 테스트 계획

**기존 회귀가 먼저다** — 리셋 검산 테스트(`UserTest.resetAnnualLeave_*`, `AnnualLeaveResetServiceTest`)가
식 변경 뒤에도 같은 값을 내야 한다. §3의 검산 ①②를 그대로 테스트로 옮긴다.

새로 고정할 것:

1. 다음 회차 날짜만 있는 신청 → `use_days` 불변, 다음 회차 예약분만 증가
2. 기산일을 걸친 신청 → 현재 회차분만 차감 (경계 당일 포함)
3. 잔여 0인 사원이 다음 회차 날짜를 신청 → 통과 (지금은 실패한다)
4. 다음 회차 예약이 예상 가용량을 넘으면 `NEXT_CYCLE_RESERVATION_EXCEEDED`
5. 다음 회차 창을 넘는 날짜 → `LEAVE_DATE_TOO_FAR`
6. 정책 키 `false` → 다음 회차 날짜 자체를 거부
7. 신청 → 리셋 → 취소 순서에서 복구량이 정확히 그 회차분
8. catch-up 2회차 이상에서 회차별 `leave_reset_history`가 창 기준으로 맞음
9. 요약 응답의 다음 회차 3필드
10. 프론트: 신청 패널이 현재/다음 회차를 나눠 표시

## 12. 구현 순서

1. **W1 도메인·집계** — `daysWithin`, 창 기반 리포지터리 쿼리, `carryOverDebt`·`oldYearUse` 식 정정 + §3 검산 테스트
2. **W2 신청 경로** — 회차 분리 차감, §4 한도, §5 범위, 정책 키, 에러 코드, 복구 교체
3. **W3 응답·화면** — 요약 3필드와 화면 5곳(신청 패널 포함)
4. **W4 보정·문서** — backfill과 검증 쿼리, docs 갱신

W1을 먼저 독립적으로 넣는 이유는, 리셋 식 변경이 **기존 테스트로 즉시 검증되는 유일한 부분**이기 때문이다.
여기서 값이 흔들리면 그다음을 쌓지 않는다.

## 13. 이 설계가 정한 것 (바꾸려면 여기부터)

1. 다음 회차 예약분을 **필드가 아니라 날짜 집계**로 다룬다 (§2)
2. 채무 식에서 `carriedUse`를 뺀다 — 새 모델에서는 이중 차감이다 (§3)
3. 다음 회차 한도는 **정책 연차 − 현재 빚**, 당겨쓰기는 적용하지 않는다 (§4)
4. 예약은 **다음 1회차까지만** (§5)
5. 잔여 숫자는 그대로 두고 **"다음 회차 예약 N일"을 옆에 붙인다** (§7)
