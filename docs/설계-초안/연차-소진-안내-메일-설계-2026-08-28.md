## 1. 결론

현재 이메일은 연차 신청·승인·취소·생일 반차 같은 건별 알림과 실패 재시도까지만 구현되어 있다. `REMINDER` 메일 타입과 `reminder_list_days`, `reminder_auto_cycle` 설정값은 존재하지만 모두 `PENDING_FEATURE`라서 자동 대상 조회와 발송은 아직 미구현이다.

1차 구현은 **다음 기산일까지 남은 일수와 잔여 연차를 함께 판단하는 개인별 리마인더**로 한다.

- 대상: 재직 중이며 온보딩이 완료되고, 잔여 연차가 0일보다 큰 사원
- 기준: `nextResetDate = lastResetDate + 1년`
- 방식: 관리자가 `D30`, `D60`, `D90`, `QUARTER` 중 하나를 선택
- 발송: 수신자 본인에게만 발송하고, 기존 `email_history` 아웃박스·비동기 발송·3회 재시도를 재사용
- 중복: 같은 사원·같은 주기·같은 기산일(또는 분기)에 한 번만 큐에 넣음
- 기본값: `NONE`이므로 구현 완료와 운영 설정 전에는 메일이 나가지 않음

여기서 “연차를 사용하지 않고 남아 있음”은 연차 신청이 한 번도 없다는 뜻이 아니라 **현재 잔여일이 남아 있음**이라는 뜻으로 정의한다. 일부 사용한 사원도 잔여일이 있으면 대상이다.

## 2. 주기와 대상 판정

`daysUntilReset = today`와 `nextResetDate` 사이의 날짜 수로 계산한다. 기존 현황 API와 동일하게 잔여일은 `baseDays + bonusDays - useDays`를 사용하며, `useDays`에는 대기 중 선차감도 포함한다. 반려·취소된 신청은 잔여일 계산에 남지 않는다.

| 설정값 | 실행 기준 | 대상 범위 | 중복 기준 키 |
|---|---|---|---|
| `NONE` | 실행하지 않음 | 없음 | - |
| `D30` | 매일, `0 <= daysUntilReset <= 30`에 처음 진입했을 때 | 잔여일 `> 0` | `D30:{nextResetDate}` |
| `D60` | 매일, `0 <= daysUntilReset <= 60`에 처음 진입했을 때 | 잔여일 `> 0` | `D60:{nextResetDate}` |
| `D90` | 매일, `0 <= daysUntilReset <= 90`에 처음 진입했을 때 | 잔여일 `> 0` | `D90:{nextResetDate}` |
| `QUARTER` | 1·4·7·10월 1일. 장애 시 7일 이내 catch-up | `daysUntilReset <= reminder_list_days`이고 잔여일 `> 0` | `QUARTER:{연도-Q분기}` |

D30·D60·D90은 “30일마다 반복”이 아니라 **다음 기산일까지 30·60·90일 남은 구간에 한 번** 보내는 의미로 한다. 서버가 해당 날짜에 꺼져 있어도 다음 실행에서 구간 안이면 발송한다. 현재 설정 enum이 하나의 값을 저장하므로 v1에서는 세 시점을 동시에 보내지 않는다. 90·60·30일 세 번 모두 보내려면 후속 버전에서 다중 선택 설정으로 확장한다.

`reminder_list_days`는 관리자 대상 목록과 분기 발송의 조회 범위로 유지한다. D 주기를 선택할 때는 선택한 일수 이상으로 설정하도록 두 설정의 교차 검증을 추가한다. 예를 들어 `D90`인데 `reminder_list_days=30`이면 저장을 거부하거나 자동 발송을 안전하게 중지하고 관리자에게 설정 오류를 표시한다.

대상 공통 조건은 다음과 같다.

- `is_active = true`, `onboarding_status = COMPLETED`, `last_reset_date IS NOT NULL`
- 이메일 주소가 공백이 아님
- `remainingDays > 0`
- `0 <= daysUntilReset <= 선택된 범위`
- 팀장·관리자에게 참조(CC)하지 않고 대상 사원 본인에게만 발송

기산일 리셋이 실패해 `nextResetDate`가 이미 지난 사용자는 메일을 보내지 않고 리셋 실패 로그를 우선 남긴다. 리셋 후 새 잔여일을 계산해야 하기 때문이다.

## 3. 처리 흐름과 저장 구조

기존 `LeaveScheduler`의 기산일 리셋·월차·생일 반차 처리 **뒤**에 리마인더 실행을 배치한다. 별도 진입점으로 분리할 경우에도 같은 순서가 보장되는 실행 시각 또는 완료 신호가 필요하다. `Clock`을 주입하고 테스트 프로필에서는 크론을 막는다.

```text
정책 읽기(NONE이면 종료)
  → 대상 ID를 안정적인 id 순서로 조회
  → 사원별 REQUIRES_NEW 트랜잭션
      → 최신 잔여일·다음 기산일 재확인
      → 중복 키 선점(이미 있으면 종료)
      → 템플릿 렌더링 및 email_history(PENDING) 생성
  → 커밋 후 EmailDispatchEvent
  → 기존 SMTP 발송 / 실패 재시도
```

`email_history`는 발송 아웃박스이므로 그대로 사용하되, 중복 방지를 위해 별도 업무 이력 테이블을 추가한다.

```text
leave_reminder_dispatch
- id
- user_id (FK users)
- cycle (D30/D60/D90/QUARTER)
- period_key (예: D30:2027-08-28, QUARTER:2026-Q3)
- reference_date (기준일)
- next_reset_date
- remaining_days_snapshot
- email_history_id (FK email_history)
- result (QUEUED / SKIPPED_NO_EMAIL)
- created_at, updated_at

UNIQUE (user_id, cycle, period_key)
```

선점과 `email_history` 생성을 같은 트랜잭션에서 처리한다. 두 스케줄러 인스턴스가 동시에 들어와도 unique 제약으로 한 건만 남기고, unique 충돌은 정상적인 “이미 처리됨”으로 기록한다. 템플릿이 변경되어도 `email_history.content`에는 발송 당시 HTML이 보존된다.

현재 이메일 재시도 구현에는 다중 인스턴스에서 같은 이력을 동시에 보낼 수 있는 보류 항목이 있다. 자동 발송을 운영에 켜기 전 `PENDING/FAILED → SENDING` 원자적 선점과 `@Version` 또는 조건부 UPDATE를 추가하고, 오래된 `SENDING`을 재시도하는 규칙을 확정한다. 업무 이력의 unique 키만으로는 SMTP 중복 발송까지 막을 수 없다.

## 4. 이메일 양식

`EmailTemplateData`는 신청 정보 중심이므로 리마인더에는 별도 스냅샷 DTO를 사용한다. 새 `EmailTemplateKind.LEAVE_BALANCE_REMINDER`를 추가하고 `EmailTemplateFactory`에서 동일한 HTML escaping·버튼·푸터 규칙을 적용한다.

기본 양식의 변수는 다음으로 제한한다.

`{name}`, `{remainingDays}`, `{nextResetDate}`, `{daysUntilReset}`, `{serviceUrl}`

예시:

```text
제목: [연차 소진 안내] {name}님, 잔여 연차가 {remainingDays}일 있습니다.

{name}님, 현재 사용 가능한 연차가 {remainingDays}일 남아 있습니다.
다음 기산일은 {nextResetDate}이며 {daysUntilReset}일 후입니다.
기산일에 적용되는 이월·소멸 정책은 서비스의 연차 정책을 확인해 주세요.
```

관리자 양식 수정은 `leave_policy_config.value`에 본문을 넣지 않는다. 해당 컬럼은 길이가 짧고 정책 값과 콘텐츠를 섞게 된다. `email_templates` 테이블(`template_key`, `subject_template`, `body_template`, `version`, `updated_by`, timestamps)을 별도로 두고, v1 편집기는 평문을 저장한 뒤 서버에서 HTML escaping과 줄바꿈 변환을 한다. HTML 직접 입력은 허용 목록 sanitizing을 추가한 뒤 별도 범위로 둔다.

## 5. 관리자 기능과 API 초안

기존 문서의 `/api/emails/reminder-targets`, `/api/emails/bulk`, `/api/emails`, `/api/emails/{id}/resend` 계약을 유지하면서 다음 동작을 명확히 한다.

| 기능 | 동작 |
|---|---|
| 대상 미리보기 | 주기·기준일을 받아 이름, 부서, 잔여일, 다음 기산일, 발송 가능 여부를 반환. 실제 발송하지 않음 |
| 자동 설정 | 정책 화면에서 `reminder_list_days`와 `reminder_auto_cycle`을 저장. 교차 검증 실패 시 저장하지 않음 |
| 양식 관리 | 시스템 관리자만 기본 양식 조회·수정·미리보기 |
| 수동 일괄 발송 | 자동 대상 또는 체크한 대상만 선택해 큐에 넣음. 자동 발송 ledger와 구분하고 발송자·대상을 감사 로그에 남김 |
| 발송 이력 | `REMINDER`·상태·기간·실패 사유 필터와 수동 재발송 제공 |

대상 미리보기 응답에는 수신자의 원문 메일 주소나 다른 사람의 연차 사유를 불필요하게 포함하지 않는다. 자동 스케줄러는 HTTP API를 자기 호출하지 않고 동일한 도메인 서비스를 직접 사용한다.

SENDING 복구는 `email_history`에 `updated_at`이 없어 `created_at` 기준 10분이다 — 다중 인스턴스에서 오래된 행을 재시도 중 복구가 겹칠 수 있으므로 단일 인스턴스 전제. 컬럼을 더하려면 backfill이 필요하다.

## 6. 보안·운영 제한

- 모든 관리자 API는 `SYSTEM_ADMIN`만 접근한다.
- 메일 본문은 수신자 본인의 잔여일만 포함한다. 부서 전체 잔여일, 다른 사원의 이름·사유·신청일은 넣지 않는다.
- 이름과 관리자 입력 양식은 템플릿 변수 치환 전에 escaping한다.
- SMTP 계정·앱 비밀번호·공공 API 키는 Git, 정책 테이블, 응답 JSON에 저장하지 않는다. 환경변수나 암호화된 secret 저장소를 사용한다.
- 스케줄러 한 번에 큐에 넣는 건수에 상한을 두고, 개인 Gmail 일 500건 한도와 건별 알림 사용량을 합산해 초과하지 않도록 한다. 초과 대상은 다음 실행에서 안정적인 id 순서로 이어서 처리한다.
- 설정이 없거나 잘못되면 `NONE`으로 안전하게 동작하고 WARN 로그를 남긴다. 설정 키의 `ACTIVE` 전환은 구현·마이그레이션·QA가 끝난 뒤 마지막에 한다.
- 수동 발송·양식 변경·강제 재발송은 `admin_audit_log`에 행위자, 대상 수, 기간, 양식 버전을 기록한다.

## 7. 구현 전 검증 항목

1. `NONE`에서는 scheduler가 대상 조회·이력 생성·이벤트 발행을 모두 하지 않는지 확인한다.
2. 31·30·29일 경계와 0일, 윤년·말일 기산일을 검증한다.
3. 잔여 0·음수, 퇴직자, 온보딩 미완료, 이메일 공백, 기산일 누락을 제외한다.
4. 대기·승인·반려·취소 상태가 기존 잔여일 계산과 일치하는지 검증한다.
5. 분기 첫날·catch-up 7일·분기 중복 발송을 검증한다.
6. 같은 사원에 대한 동시 실행에서 `leave_reminder_dispatch`와 `email_history`가 한 건만 생성되는지 검증한다.
7. SMTP 실패는 기존 최대 3회 재시도로 이어지고, 실패 이력 수동 재발송이 자동 주기를 중복 생성하지 않는지 확인한다.
8. 템플릿의 `<`, `>`, `&`와 URL이 그대로 HTML을 깨뜨리지 않는지, 관리자 외 API가 차단되는지 확인한다.

## 8. 권장 구현 순서와 결정이 필요한 항목

1. 이 문서의 주기 의미와 `QUARTER` 기준일을 확정한다.
2. `leave_reminder_dispatch` 및 이메일 선점 마이그레이션을 추가한다.
3. 잔여일 대상 조회·리마인더 서비스·템플릿·기존 아웃박스 연결을 구현한다.
4. 단위·통합·동시성·보안 테스트를 작성한다.
5. 관리자 대상 미리보기·양식·수동 일괄 발송 화면을 구현한다.
6. 사용자 QA 후에만 두 정책 키를 `ACTIVE`로 전환한다.

현재 권장안은 **D30/D60/D90 중 하나를 선택**, **분기는 분기 첫날**, **대기 중 선차감은 잔여일에 포함**, **자동 발송과 일반 수동 일괄 발송을 별도 기능으로 분리**하는 것이다. 이 네 가지가 확정되면 백엔드 구현을 시작할 수 있다.

|---|---|---|
| ① | 발신 계정(SMTP 사용자·앱 비밀번호)은 **DB에 암호화 저장**하고 환경변수는 fallback으로 남긴다 | 회사 계정을 받으면 화면에서 갈아 끼울 수 있어야 한다는 것이 `USER-4`(구 B-4)의 요구다. env fallback까지 지우면 자격 증명이 아직 없는 새 환경에서 메일 경로가 통째로 죽는다 |
| ② | 관리자 화면은 **신규 2페이지** — `/admin/integrations`(공휴일 키·메일 계정 회전·테스트 발송), `/admin/emails`(대상 목록·양식·일괄 발송·이력·재발송) | `AdminPolicyPage`에 연차 정책·시스템 설정·소멸 이력·공휴일이 이미 붙어 있어 한 화면에 더 얹을 자리가 없다 |
| ③ | 재발송은 **`FAILED`만** 허용한다 | `SENT` 재발송은 수신자에게 중복 수신이고, 자동 발송 ledger의 "한 번만" 규칙과도 충돌한다 |
| ④ | 일괄 발송 상한은 **회당 100건 · 일 400건** | 개인 Gmail 일 500건 한도(docs/01 §2-8)에 건별 알림 몫 100건을 남긴다 |
| ⑤ | 대상 필터는 **§2의 설계 그대로** (재직 · 온보딩 완료 · `last_reset_date` 있음 · 잔여일 > 0 · 기산일 임박) | v1에서 부서·역할 필터를 얹으면 대상 판정과 중복 키가 함께 복잡해진다 |
| ⑥ | 온보딩 승인 대기 알림을 **포함**한다 (§10) | 트리거가 네 곳뿐이고 `EmailType.NOTICE`를 재사용해 ENUM 확장이 없다 |

## 10. 온보딩 승인 알림

입사일이 자동 승인 범위 밖이면 승인 대기로 들어가는데(§`ONBOARDING_AUTO_APPROVE_DAYS`), 지금은 총관리자가 화면에 들어와야만 그 사실을 안다. 대기 발생과 처리 결과를 메일로 알린다.

| 트리거 | 코드 위치 | 수신자 |
|---|---|---|
| 대기 발생 | `AuthService.processOnboarding`의 `user.requestOnboardingApproval(...)` 직후 (`AuthService:138`) | 재직 `SYSTEM_ADMIN` 전원 |
| 승인 | `OnboardingApprovalService.approve` (`:55`) | 대상 사원 본인 |
| 반려 | `OnboardingApprovalService.reject` (`:74`) | 대상 사원 본인 |
| 1회 수정 | `AuthService.reviseOnboarding` (`:87`) → `processOnboarding(revision=true)` (`:103`) | 재직 `SYSTEM_ADMIN` 전원 |

- 수신자 결정은 `EmailNotificationPublisher.addSystemAdmins`(`:245`, `findByRoleAndIsActiveTrue(SYSTEM_ADMIN)`)를 **그대로 재사용**한다. 승인 알림에 이미 쓰이는 경로라 새로 만들 이유가 없다.
- **반려 메일은 `user.rejectOnboarding()`이 `hire_date`를 지우기 전에 입사일을 담아야 한다.** `User.rejectOnboarding`(`User:218~219`)이 `hireDate = null`로 되돌리므로, 지운 뒤에 읽으면 메일의 입사일이 빈칸으로 나간다. 서비스는 같은 이유로 이미 `LocalDate rejected = user.getHireDate();`를 먼저 잡아 두고 있으니(`OnboardingApprovalService:76`) 메일 페이로드도 그 값을 쓴다.
- 1회 수정은 수정 결과가 자동 승인 범위 **안**이면 그 자리에서 확정되므로(`AuthService:137` 분기), "대기 재발생"과 "수정 후 확정"의 문구를 나눈다.
- 타입은 기존 `EmailType.NOTICE`를 재사용한다 — **ENUM 확장이 없으므로 `email_history.email_type`의 `MODIFY COLUMN` backfill도 필요 없다.**
- 문구는 `EmailTemplateKind`에 상수 네 개(`ONBOARDING_PENDING`·`ONBOARDING_APPROVED`·`ONBOARDING_REJECTED`·`ONBOARDING_REVISED`)를 더해 `EmailTemplateFactory`가 만든다. 자바 enum이고 컬럼이 아니라 DB 영향은 없다.
- 발송 구조는 건별 알림 7종과 **같은 아웃박스**를 탄다 — 업무 트랜잭션 안에서 `email_history`(PENDING) 생성 → 커밋 후 `EmailDispatchEvent` → 비동기 발송 → 실패 시 `EmailRetryScheduler` 재시도.

## 11. 외부 연동 설정 (`/admin/integrations`)

- **`mail_credentials` 신설** — `provider`(UNIQUE) · `username` · `encrypted_secret` · `active`. 공휴일의 `holiday_api_credentials`와 **한 테이블로 합치지 않는다**: 그쪽은 staging 시드 절차가 이미 문서로 확정돼 있어 스키마를 바꾸면 그 절차가 무효가 되고, SMTP는 계정 ID 컬럼이 더 필요해 통합이 어색해진다.
- **`HolidaySecretCipher` → `com.mlsoft.backend.domain.credential.SecretCipher`로 일반화**한다. 알고리즘(AES-GCM · 32바이트 키 · IV 12바이트 · 태그 128비트)은 그대로 두고 주입받는 키 이름만 바꾼다.
- **암호화 키 환경변수는 `APP_CREDENTIAL_ENCRYPTION_KEY`**. 값이 비면 옛 `HOLIDAY_CREDENTIAL_ENCRYPTION_KEY`를 fallback으로 읽어, 이미 시드된 staging이 이름 변경만으로 복호화에 실패하지 않게 한다.

| Method | URL | 설명 | 권한 |
|---|---|---|---|
| GET | `/api/admin/integrations` | 마스킹 조회 — 비밀번호·API 키는 `••••`와 끝 4자만 | SA |
| PUT | `/api/admin/integrations/{provider}` | 저장·회전 (쓰기 전용 필드) | SA |
| POST | `/api/admin/integrations/mail/test` | 테스트 발송 — 요청한 관리자 본인에게만 | SA |
| POST | `/api/admin/integrations/holiday/verify` | 키 검증 — 저장하지 않고 응답 코드만 확인 | SA |

- **비밀번호·키는 응답에 싣지 않는다.** 평문을 내려주면 관리자 화면을 여는 것만으로 유출 경로가 생긴다 (docs/12 `B-4` 별항).
- **`PolicyConfigKey` 카탈로그에 넣지 않는다** — 그 테이블은 값을 평문으로 두고 관리자 화면이 값을 그대로 렌더한다. 시크릿용이 아니다.
- 화면에는 Google 앱 비밀번호 발급 절차(2단계 인증 선행)를 함께 안내한다.
- 저장·회전·테스트 발송은 `admin_audit_log`에 남긴다. **`AdminAction`에 상수를 더하는 순간 `admin_audit_log.action`의 `MODIFY COLUMN` backfill이 따라온다** — 그 컬럼이 MySQL `ENUM(...)`이고 `ddl-auto: validate`는 값 목록까지 검사하지 않아, 기동은 멀쩡히 통과하고 **그 값을 처음 저장하는 요청에서 500**이 난다(`USER_RESTORED` 전례, CLAUDE.md 배포 절).
