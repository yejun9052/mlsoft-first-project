## 2. 요구사항과 어긋나는 지점

### 기존 갭분석에 이미 기록된 항목

다음은 `docs/07-기능-갭분석.md`의 항목 번호만 참조한다.

- 대시보드 명세: 갭분석 A-7
- 복리후생 취소 규칙: 갭분석 A-9
- 휴일·중복 신청 검증 명세: 갭분석 A-10
- 1년 미만 월차: 갭분석 B-1

- 온보딩 연차 자동 산정: 갭분석 C-1

문서의 2026-08-07 구현 상태는 현재 코드보다 오래됐다. 예를 들어 월차·공휴일 검증·스케줄러는 현재 구현돼 있으므로 과거의 “미구현” 표를 현행 결함으로 사용하면 안 된다.

### 추가로 확인된 불일치

1. 이메일 요구사항은 미구현이다.

   `docs/01-요구사항-기획.md:84, 97, 122-131`은 신청·결재·생일·리마인더 이메일과 발송 이력·재시도를 요구한다. 현재는 `TODO(email)`만 있으며 사용자 지시에 따라 이번 QA 결함 대상에서는 제외한다.

2. Google Workspace `hd` claim 검증은 미구현이다.

   `docs/01-요구사항-기획.md:54-59`가 운영 전 `hd == "mlsoft.com"` 및 `email_verified` 검증을 요구하지만 현재 개발 단계는 이메일 도메인 검사다. 이번 QA 결함 대상에서는 제외한다.

3. “매일 자정”과 실제 실행 시각이 다르다.

   요구사항은 `docs/01-요구사항-기획.md:109-115`에서 자정 실행으로 표현하지만 실제 일일 잡은 `LeaveScheduler.java:53`의 KST 00:10이다. 이는 `docs/09-스케줄러-설계.md`에서 공휴일 동기화(00:05) 이후 순서를 보장하려고 구체화한 설계이므로 결함으로 보지 않는다.

4. 퇴직자 3년 보존 후 처분 기능은 확인하지 못했다.

   `docs/01-요구사항-기획.md:134-138`은 SYSTEM_ADMIN의 3년 경과 데이터 처분 권한을 적고 있으나, 사용자 삭제·익명화 엔드포인트는 확인하지 못했다. 기존 갭분석 번호로 직접 대응되는 항목도 찾지 못했다. 다만 이번 지시의 중점 기능이 아니며 존재하지 않는 기능을 수동 QA로 올리지 않는다.

5. 관리자 감사 로그는 요구사항 문서보다 구현 범위가 구체적이다.

   코드상 7종은 `AdminAction.java:21-27`의 권한 변경, 부서 변경, 연차 직접 설정, 퇴직, 온보딩 승인, 온보딩 반려, 시스템 설정 변경이다. 부서 자체 CRUD와 연차 정책표·복리후생 정책 CRUD는 이 감사 로그에 포함되지 않는다. “관리자 조작 전부”를 기록한다고 확대 해석하면 안 된다.

## 3. QA 항목 (영역별)

### 온보딩 승인

- [ ] 🔴 자동 승인 기간 밖 입사일이 연차 0인 승인 대기 상태로 이어지는지 확인한다.
  - 준비: 온보딩 전 신규 계정 1개, `ONBOARDING_AUTO_APPROVE_DAYS`보다 오래된 입사일
  - 절차: 1. 신규 계정으로 로그인한다. 2. 생일과 오래된 입사일을 입력한다. 3. 제출한다. 4. 새로고침한다. 5. 대시보드 URL을 직접 입력한다.
  - 기대: 승인 대기 안내만 보이고 연차는 부여되지 않는다. 새로고침 후에도 안내가 유지되며 대시보드에는 진입하지 못한다. 로그아웃은 가능하다.
  - 실패하면: `frontend/src/pages/OnboardingPage.jsx`, `frontend/src/components/RequireAuth.jsx`, `backend/.../AuthService.java`, `backend/.../OnboardingCheckInterceptor.java`

- [ ] 🔴 관리자가 온보딩을 승인하면 계정이 즉시 정상 사용 상태가 되는지 확인한다.
  - 준비: 위 승인 대기 계정, SYSTEM_ADMIN 계정
  - 절차: 1. 관리자로 로그인한다. 2. 구성원 관리에서 온보딩 승인 대기 탭을 연다. 3. 대상 계정의 승인 버튼을 누른다. 4. 확인창에서 승인한다. 5. 대상 계정 탭에서 새로고침한다.
  - 기대: 관리자 목록과 탭 배지에서 대상이 사라진다. 대상 계정은 대시보드로 진입하며 입사일 기준 연차가 표시된다.

  - 준비: 별도의 승인 대기 계정, SYSTEM_ADMIN 계정
  - 절차: 1. 관리자가 승인 대기 탭에서 반려를 누른다. 2. 확인창에서 반려한다. 3. 대상 계정 화면을 새로고침한다. 4. 온보딩 정보를 다시 입력한다.

  - 절차: 1. 해당 관리자로 구성원 관리에 들어간다. 2. 본인 역할을 EMPLOYEE로 변경한다. 3. 실패 메시지와 목록을 확인한다. 4. 이어서 본인 퇴직 처리를 시도한다.
  - 기대: 두 작업 모두 실패하고 관리자 역할과 재직 상태가 유지된다. 성공 토스트나 일시적인 목록 제거가 나타나지 않는다.

  - 기대: B는 로그아웃·재로그인 없이 최신 역할에 맞는 메뉴와 라우트 권한을 얻거나 잃는다. 이전 역할 메뉴가 계속 작동하지 않는다.

## 4. 시간·외부 의존 때문에 확인이 어려운 것 + 확인 가능하게 만드는 방법

### 현재 확인 수단

일일 잡과 연간 잡 모두 수동 트리거 엔드포인트가 없다.

- 일일 잡: `LeaveScheduler.java:53-66`
- 연간 공휴일 잡: `LeaveScheduler.java:73-81`
- 공휴일만 별도로 동기화: `POST /api/holidays/sync` 존재

DB 날짜를 조작해도 실행 트리거 자체가 00:10에 고정돼 있어 즉시 결과를 볼 수 없다. 서버 재기동도 잡을 실행하지 않는다. 따라서 “DB 날짜 조작 후 기다리지 않고 브라우저 확인”은 현재 구조로 불가능하다.

또한 운영 DB 접속 방식과 스키마 변경 도구는 이번 범위에서 확인하지 않았으므로, 실데이터 DB를 직접 수정하는 절차는 제안하지 않는다.

### 권장 확인 가능화 방식

프로덕션에 공개 API를 추가하지 말고, `local` 전용 수동 트리거를 추가하는 것이 가장 안전하다.

- `@Profile("local")` 컨트롤러
- SYSTEM_ADMIN 전용
- `POST /api/admin/jobs/daily?date=YYYY-MM-DD`
- `POST /api/admin/jobs/holidays?year=YYYY`
- 날짜를 서버 현재 시각에 묶지 않고 명시적으로 전달
- 실행 결과로 잡별 대상·성공·실패 건수 반환
- 운영 프로필에는 빈 자체가 등록되지 않도록 제한
- 실행 사실은 관리자 감사 로그에 기록

다만 현재 `LeaveScheduler.runDailyJobs()`는 내부에서 주입된 `Clock`의 오늘을 직접 읽는다. 단순히 컨트롤러에서 이 메서드를 호출하면 임의 날짜 검증이 안 된다. 수동 검증을 지원하려면 스케줄러와 수동 트리거가 공통 오케스트레이터의 `runDailyJobs(LocalDate 기준일)`을 호출하도록 최소 분리해야 한다.

이 변경은 이번 과제의 “코드를 고치지 말라”는 범위를 벗어나므로 구현하지 않는다.
