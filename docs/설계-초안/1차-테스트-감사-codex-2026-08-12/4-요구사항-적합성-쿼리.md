정적 코드 기준 감사 결과입니다. 운영 SQL 로그나 Hibernate statistics를 실행하지 않았으므로 실제 쿼리 횟수는 코드 경로로 산정했습니다.

- 페이지 목록의 to-one 연관: `@EntityGraph`
- `dates` 컬렉션: `@BatchSize(50)`
- 컬렉션 fetch와 `Pageable` 결합: 없음
- `HHH90003004` 발생 구조: 발견되지 않음
- 남은 명확한 반복 조회: 이메일 비동기 리스너의 수신자별 `findById`
- 신규 필수 인덱스: 없음. 기존 backfill이 주요 조회를 커버함

## 2. 페이징 + 컬렉션 fetch 위험

위험 없음.

페이지 반환 메서드의 `@EntityGraph`에는 모두 to-one 연관만 들어 있습니다.

- 연차 목록: user, department, primary/sub approver
- 복리후생 목록: user, department, policy
- 처리 이력: actor, user, department, request
- 사용자·감사·리셋 이력: 단일 to-one 연관

`LeaveRequest.dates`와 `ScheduleEntry.dates`는 컬렉션 fetch join이나 EntityGraph에 넣지 않고 `@BatchSize(50)`로 분리되어 있습니다. 따라서 컬렉션 조인 때문에 Hibernate가 메모리 페이징으로 후퇴하는 `HHH90003004` 발생 조건이 없습니다.

페이지 크기 20 기준 연차 목록은 통상 다음 형태입니다.

1. count 쿼리
2. 본문 + to-one join 쿼리
3. `dates` 배치 쿼리 1회

즉 컬렉션 때문에 행이 증폭되거나 DB 페이징이 무력화되지는 않습니다.

## 5. 결론

페이지 크기 20에서 과거처럼 연차·복리후생 목록마다 `20`, `40`, `60`개의 추가 쿼리가 붙는 구조는 제거됐습니다. 현재 목록 계층의 최대 추가 조회는 `dates` 배치 1회이며, 이는 의도된 방식입니다.

우선순위는 다음 두 가지입니다.

1. `EmailNotificationListener`의 수신자별 `findById`를 벌크 조회로 변경
2. 운영 DB에서 세 backfill 인덱스의 실제 적용 여부 확인

그 외에는 새로운 `@EntityGraph`, fetch join, `@BatchSize`, 신규 인덱스를 추가할 근거가 없습니다. 특히 소규모 마스터 테이블에 “일단 인덱스”를 추가하는 것은 권하지 않습니다.
