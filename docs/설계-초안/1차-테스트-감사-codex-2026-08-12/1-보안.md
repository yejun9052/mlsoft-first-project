## 발견

### [중간] JWT 쿠키 인증에서 CSRF 보호가 전면 비활성화됨

- 위치: [SecurityConfig.java](C:/Users/User/Desktop/myproject/mlsoft-leave-system/backend/src/main/java/com/mlsoft/backend/config/SecurityConfig.java:53), [TokenCookieFactory.java](C:/Users/User/Desktop/myproject/mlsoft-leave-system/backend/src/main/java/com/mlsoft/backend/security/TokenCookieFactory.java:36)
- 공격/악용 시나리오: 동일 사이트로 판정되는 하위 도메인이 탈취되거나 공격자 콘텐츠를 제공하면, 로그인 사용자의 `token` 쿠키가 위조 요청에 첨부될 수 있습니다. 특히 body가 필요 없는 `POST /api/auth/logout`, 관리자용 `POST /api/holidays/sync` 같은 요청은 브라우저 폼으로 실행할 수 있습니다.
- 왜 문제인가: 인증 수단이 자동 전송되는 쿠키인데 CSRF를 완전히 끄고 있습니다. `SameSite=Lax`는 일반적인 교차 사이트 POST를 줄이지만 동일 사이트 하위 도메인 공격까지 막지 못하며, CORS도 브라우저 폼 요청 자체를 차단하지 않습니다.
- 권장 수정: 쿠키 기반 CSRF 토큰을 활성화하고 프론트가 변경 요청마다 헤더로 전송하게 하십시오. 대안으로 모든 변경 API에 사용자 정의 요청 헤더를 강제하고, 서버에서 `Origin`도 허용된 프론트 오리진과 일치하는지 검증하십시오.

### [낮음] 새 키·인증서 파일이 저장소와 Docker 이미지에 포함될 수 있음

- 위치: [.gitignore](C:/Users/User/Desktop/myproject/mlsoft-leave-system/.gitignore:4), [.dockerignore](C:/Users/User/Desktop/myproject/mlsoft-leave-system/.dockerignore:15), [Dockerfile](C:/Users/User/Desktop/myproject/mlsoft-leave-system/Dockerfile:20)
- 공격/악용 시나리오: 향후 개발자가 `backend/` 아래에 TLS 개인키나 서비스 계정 키를 `*.key` 또는 `*.pem`으로 추가하면 무시 규칙에 걸리지 않습니다. Dockerfile은 `backend/` 전체를 복사하므로 해당 파일이 빌드 컨텍스트나 이미지 계층에 들어갈 수 있습니다.
- 왜 문제인가: 현재 규칙은 로컬 설정과 `*-secret.*`은 잘 차단하지만, 작업 규칙에서 시크릿으로 분류한 `*.key`, `*.pem` 패턴은 빠져 있습니다.
- 권장 수정: 루트 `.gitignore`와 `.dockerignore` 모두에 `*.key`, `*.pem`을 추가하고, 필요한 공개 인증서만 `!경로`로 개별 허용하십시오. CI에서 이미지·JAR 내부의 금지 파일명도 검사하는 것이 안전합니다.

## 권한매트릭스 검토 결과

- 관리자 전용 사용자·부서·정책·감사·온보딩 API에는 `hasRole('SYSTEM_ADMIN')`가 적용되어 있습니다.
- 결재 API는 `TEAM_LEADER`·`SYSTEM_ADMIN` 역할 게이트와 서비스 계층의 실제 승인자 검증을 함께 사용합니다.
- 본인 신청·프로필·일정 API는 요청 body의 `userId`가 아니라 `@AuthenticationPrincipal AuthUser`의 ID를 사용합니다.
- 일정 수정·삭제는 서비스에서 소유권을 검사하며, 캘린더 메모는 본인 또는 `SYSTEM_ADMIN`에게만 반환됩니다.
- 이메일 신청 사유는 신청자·지정 승인자·`SYSTEM_ADMIN`에게만 `reasonVisible=true`로 전달됩니다. 중복 수신자는 권한을 OR 병합하므로 마스킹이 잘못 풀리는 경로도 발견하지 못했습니다.
- 퇴직 여부·현재 역할·온보딩 상태는 JWT 값만 신뢰하지 않고 `/api/**` 요청마다 DB에서 재검증합니다.
- Google Workspace `hd` claim 미검증은 `docs/08 R-2`와 코드 TODO에 이미 기록된 알려진 미완료 항목이므로 신규 발견으로 중복 보고하지 않았습니다.
- SMTP 최하위 예외 메시지를 `email_history.error_message`에 저장하지만, 현재 코드에는 이를 반환하는 이메일 조회 컨트롤러·DTO가 없습니다. 현시점 외부 노출 취약점으로 분류하지 않았습니다. 추후 조회 API 구현 시에는 관리자 전용 권한과 메시지 정제 여부를 다시 확인해야 합니다.
