## 요약

🔴 2건 · 🟡 2건 · 🟢 1건  (메일 알림 유실·기록 불일치와 외부 호출 무제한 대기가 운영상 핵심 위험)

## 발견

### [🔴] 비동기 큐 포화 시 알림과 `email_history`가 함께 조용히 사라진다

- 위치: `backend/src/main/java/com/mlsoft/backend/config/EmailAsyncConfig.java:30`
- 터지는 조건: SMTP 장애·지연으로 실행 스레드 4개가 묶인 상태에서 커밋 후 이메일 작업이 100건을 초과해 큐에 들어온다.
- 결과: 101번째 이후 작업은 업무 요청을 성공시킨 채 폐기된다. `EmailNotificationListener`가 실행되기 전에 버리므로 `email_history`에는 `PENDING`이나 `FAILED`조차 남지 않고, 15분 재시도 스케줄러도 유실된 메일을 찾을 수 없다. WARN 로그가 사라지면 영구적으로 탐지할 방법이 없다.
- 근거:

```java
executor.setQueueCapacity(100);
executor.setRejectedExecutionHandler((task, pool) ->
        log.warn("[이메일] 비동기 큐 포화로 발송 작업을 폐기했습니다. ..."));
```

- 자동 테스트가 왜 못 잡는가: `EmailTransactionIntegrationTest`는 한 이벤트의 정상 큐 진입과 SMTP 실패만 검증한다. 실행기 4개 점유 + 큐 100개 포화 및 거부된 작업의 이력 존재 여부를 검증하지 않는다.

### [🔴] 여러 수신자를 한 트랜잭션에서 발송해 “메일은 갔지만 이력은 없는” 상태가 생긴다

- 위치: `backend/src/main/java/com/mlsoft/backend/domain/email/service/EmailNotificationListener.java:32`
- 터지는 조건: 한 이벤트에 수신자가 여러 명이고, 앞 수신자의 SMTP 발송은 성공한 뒤 뒤 수신자의 사용자 조회·템플릿 생성·DB 저장 또는 트랜잭션 최종 flush가 실패한다.
- 결과: 앞 수신자에게 보낸 SMTP 메일은 되돌릴 수 없지만, 리스너 전체의 `REQUIRES_NEW` 트랜잭션은 롤백된다. 앞 수신자의 `SENT` 이력이 사라지고 뒤 수신자는 발송되지 않는다. 실패 이력이 없으므로 자동 재시도도 불가능하다. 운영자가 이벤트를 수동 재처리하면 앞 수신자는 중복 메일을 받는다.
- 근거:

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void handle(EmailNotificationEvent event) {
    for (EmailRecipient recipientSnapshot : event.recipients()) {
        ...
        emailDeliveryService.createAndSend(recipient, event.emailType(), message);
    }
}
```

```java
emailHistoryRepository.save(...);
mailSender.send(mimeMessage); // 외부 부작용
history.markSent();           // 실제 DB commit은 리스너 종료 뒤
```

- 자동 테스트가 왜 못 잡는가: `EmailTransactionIntegrationTest`는 단일 수신자만 사용한다. “첫 수신자 SMTP 성공 후 두 번째 수신자 처리 예외”와 트랜잭션 롤백 뒤 실제 발송/이력 불일치를 검증하지 않는다.

### [🟡] SMTP 연결·읽기·쓰기 타임아웃이 없어 메일 작업이 무기한 점유될 수 있다

- 위치: `backend/src/main/resources/application.yml:48`
- 터지는 조건: SMTP 서버가 TCP 연결을 완성하지 않거나 연결 후 응답을 보내지 않는 반개방 상태가 된다.
- 결과: 메일 작업 스레드 최대 4개가 반환되지 않고 큐가 누적된다. 이후 큐 포화로 신규 알림이 위 첫 번째 발견처럼 영구 유실된다. `retry_count`도 `send()`가 반환하거나 예외를 던지기 전까지 증가하지 않는다.
- 근거:

```yaml
mail:
  smtp:
    auth: true
    starttls:
      enable: true
```

`mail.smtp.connectiontimeout`, `mail.smtp.timeout`, `mail.smtp.writetimeout` 설정이 없다.

- 자동 테스트가 왜 못 잡는가: 테스트 설정은 사용자명이 비어 있어 `mailSender.send()` 이전에 FAILED로 종료한다. 실제 소켓이 연결된 뒤 응답하지 않는 SMTP 경로는 실행되지 않는다.

### [🟡] 공휴일 API에 명시적 타임아웃이 없어 연차 검증 보완 작업이 장시간 멈출 수 있다

- 위치: `backend/src/main/java/com/mlsoft/backend/domain/holiday/client/HolidayApiClient.java:35`
- 터지는 조건: data.go.kr가 연결 또는 응답을 끝내지 않는 상태에서 새해 동기화나 캐시가 빈 연도의 조회 요청이 실행된다.
- 결과: 예외가 발생하면 빈 목록으로 degrade하지만, 예외가 발생하기 전까지의 대기 상한이 없다. 새해 스케줄러 실행이 오래 점유되고, HTTP 요청 경로의 `getByYear()`도 응답하지 않는다. 이 시간 동안 공휴일 데이터가 비어 있으면 연차 신청 검증은 공휴일을 평일로 허용한다.
- 근거:

```java
private final RestClient restClient = RestClient.create();

JsonNode root = restClient.get()
        .uri(uri)
        .retrieve()
        .body(JsonNode.class);
```

- 자동 테스트가 왜 못 잡는가: `HolidayServiceTest`는 API 목이 즉시 빈 목록을 반환하는 경우만 검증한다. 연결 성공 후 무응답·느린 응답은 검증하지 않는다.

### [🟢] 이메일 재시도는 단일 인스턴스 전제이며 다중 인스턴스에서는 중복 발송 가능성이 있다

- 위치: `backend/src/main/java/com/mlsoft/backend/domain/email/service/EmailDeliveryService.java:82`
- 터지는 조건: 애플리케이션 인스턴스가 둘 이상이고 두 재시도 스케줄러가 같은 FAILED 행을 동시에 조회한다.
- 결과: 양쪽 트랜잭션이 모두 FAILED 상태를 확인하고 같은 이메일을 발송할 수 있다. `EmailHistory`에는 `@Version`, 비관적 락 또는 FAILED→PROCESSING 선점 CAS가 없다.
- 근거:

```java
Optional<EmailHistory> optionalHistory = emailHistoryRepository.findById(historyId);
if (history.getStatus() != EmailStatus.FAILED
        || history.getRetryCount() >= MAX_ATTEMPTS) {
    return;
}
attempt(history);
```

- 자동 테스트가 왜 못 잡는가: 리포지토리 테스트는 재시도 상한 쿼리만 검증하며, 동시 트랜잭션 선점은 다루지 않는다. 현재 문서의 단일 인스턴스 운영 전제에서는 즉시 결함은 아니므로 개선 권고로 분류한다.

## 확인했으나 문제 없던 것

- 업무 트랜잭션 롤백 시 `AFTER_COMMIT` 리스너가 실행되지 않는 경계는 실제 통합 테스트로 검증돼 있다.
- 메일 발송 실패는 업무 트랜잭션을 롤백시키지 않고 `FAILED`와 실제 시도 횟수를 기록한다.
- `retry_count < 3` 조건은 실제 저장소 통합 테스트가 경계값 2 포함·3 제외를 검증해 무한 재시도를 막는다.
- 연차·복리후생 승인과 취소 상태 전이는 상태 조건부 갱신(CAS)을 사용하며, 연차 잔액·보너스 변경과 처리 이력은 같은 업무 트랜잭션 안에 있다.
- 연차 스케줄러는 리셋→월차→생일 순서를 지키고, 사원별 `REQUIRES_NEW` 호출을 프록시 밖 진입점에서 수행한다.
- 월차 catch-up, 1월 31일 말일 보정, 생일 2월 29일 평년 보정, 생일과 기산일 중복, 사원 한 명 실패 후 나머지 계속 처리는 자동 테스트가 덮는다.
- `BigDecimal` 일수 비교·합산에서 scale에 민감한 `equals` 대신 `compareTo` 또는 산술 연산을 사용한다.
- 연차 신청·취소의 오늘 기준은 KST로 고정돼 있다.

## 확인 못 한 것

- 실제 운영 SMTP 및 data.go.kr의 네트워크 타임아웃 동작은 외부 접속과 시크릿 설정이 필요해 실행 검증하지 않았다.
- 다중 애플리케이션 인스턴스 운영 여부는 배포 환경을 읽지 않아 코드와 문서의 단일 인스턴스 전제로만 판단했다.
- 요청에 따라 코드는 수정하지 않았고 테스트도 재실행하지 않았다. 기존 테스트 코드와 운영 코드를 읽기 전용으로 대조했다.
