## 3. 위험 변경점 권장 코드

현재 실행 경로의 수정 필요 코드는 **없음**이다.

선택적 예방 조치로는 클래스 수준 `@Builder`를 제거하고 생성용 정적 팩토리만 공개하는 방법이 가장 확실하다. 다만 현재 데모 초기화가 빌더를 사용하므로 함께 변경해야 하며, 이번 감사에서 발견된 운영 결함에 대한 필수 수정은 아니다.

`resetAnnualLeave`는 변경하면 안 된다. 현재 구현:

```java
public void resetAnnualLeave(
        BigDecimal newBaseDays,
        BigDecimal carriedUse,
        BigDecimal carriedBonus,
        LocalDate resetDate
) {
    this.baseDays = newBaseDays.subtract(carryOverDebt(carriedUse));
    this.useDays = carriedUse;
    this.bonusDays = carriedBonus;
    this.lastResetDate = resetDate;
    syncAdvanceDays();
}
```

이 수식과 호출 순서가 맞다. 특히 `carryOverDebt(carriedUse)`를 계산한 뒤 필드를 교체해야 하며, 교체 후 반드시 `syncAdvanceDays()`를 호출해야 한다.

## 4. 다년 부채 이월 검산

결론: `resetAnnualLeave`에서도 `(B)`를 재계산하는 현재 코드가 정확하다. “리셋에서는 `advance=0`으로 닫아야 한다”는 과거 설명이 틀렸다.

### `carriedUse`가 전부 새 연도 사용분인 경우

리셋 전:

```text
base=15, bonus=0, use=20, advance=5
carriedUse=20
정책 연차=15
```

계산:

```text
oldYearUse  = use − carriedUse = 20 − 20 = 0
oldYearDebt = max(0, 0 − 15 − 0) = 0

리셋 후:
base    = 15 − 0 = 15
use     = 20
bonus   = 0
advance = max(0, 20 − 15 − 0) = 5
```

경제적 초과분 5일과 일치한다. 기존 `advance=5`를 정책 연차에서 먼저 빼면 `base=10`, 재계산 후 `advance=10`이 되어 같은 신청을 이중 계산한다. 현재 `carryOverDebt(carriedUse)` 방식이 이 문제를 해결한다.

### 새 정책 연차보다 부채가 큰 경우

1년 차:

```text
부여 15, 사용 35
advance = 20
```

첫 리셋:

```text
oldYearDebt = 20
new base    = 15 − 20 = −5
use         = 0
advance     = max(0, 0 − (−5)) = 5
```

2년 차에 활동이 없고 다시 리셋:

```text
oldYearDebt = max(0, 0 − (−5)) = 5
new base    = 15 − 5 = 10
use         = 0
advance     = 0
```

총계 검산:

```text
총 부여 = 15 + 15 + 15 = 45
총 사용 = 35
잔액     = 10
```

정확하다. 첫 리셋에서 `advance=0`으로 닫으면 다음 리셋이 음수 `base`를 덮어써 `base=15`가 되고, 부채 5일이 면제된다.

따라서 [docs/09 §5](C:/Users/User/Desktop/myproject/mlsoft-leave-system/docs/09-스케줄러-설계.md:183)의 정정 내용과 현재 구현은 일치한다. `advance`는 재귀적으로 불어나는 값이 아니라 정책 연차만큼 `20 → 5 → 0`으로 감소한다.
