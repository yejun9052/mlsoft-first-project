## 2. 남은 P0

### P0-A. information_schema 컬럼 ↔ 파생 테이블 컬럼 비교의 collation 충돌 위험 — **실행 전 30초 안에 판별할 것**

**증상 시 결과**: `ERROR 1267 (HY000): Illegal mix of collations ... for operation '='`.
§1에서 터지면 `mysql <` 파이프가 즉시 중단되어 **preflight가 아무 결과도 내지 않는다.** 전부 아니면 전무다.

**왜 위험한가**: MySQL 8의 `information_schema` 이름 컬럼(`TABLE_NAME`, `COLUMN_NAME`, `INDEX_NAME`,
`CONSTRAINT_NAME`, `REFERENCED_*`)은 utf8mb3 계열 collation이고, `UNION ALL` 파생 테이블은 **병합되지 않고
구체화(materialize)** 되므로 그 컬럼은 연결 문자셋(보통 `utf8mb4_0900_ai_ci`)을 갖는다.
양쪽 모두 coercibility=IMPLICIT(2)라 MySQL이 어느 쪽으로 변환할지 결정하지 못하고 1267을 던진다.

**이 리포지터리에 선례가 없다**: 기존 backfill 11개는 전부 `TABLE_NAME = 'users'`처럼 **리터럴**(coercibility 4 → 안전)
또는 `TABLE_SCHEMA = DATABASE()`만 쓴다. **컬럼 대 컬럼 비교는 이 preflight가 처음이다.**
그리고 이 preflight는 아직 어떤 환경에서도 실행된 적이 없다(`docs/설계-초안/2차-QA-실행-감사-codex-2026-08-22.md:98`).

**해당 행** (총 11곳)

| 절 | 행 | 식 |
|---|---|---|
| §1 | `62` | `actual.TABLE_NAME = required.table_name` |
| §2 | `97`, `98` | `actual.TABLE_NAME = ...`, `actual.COLUMN_NAME = ...` |
| §3 | `110~111` | `GROUP_CONCAT(actual.COLUMN_NAME ...) = required.expected_columns` |
| §3 | `143`, `144` | `actual.TABLE_NAME = ...`, `actual.INDEX_NAME = ...` |
| §4 | `171`, `172` | `actual.TABLE_NAME = ...`, `actual.COLUMN_NAME = ...` |
| §5 | `183`, `184` | `MIN(actual.REFERENCED_TABLE_NAME) <> required.referenced_table`, `MIN(actual.REFERENCED_COLUMN_NAME) <> ...` |
| §5 | `185` | `MIN(actual.CONSTRAINT_NAME) <> required.expected_name` |
| §5 | `198`, `199` | `actual.TABLE_NAME = ...`, `actual.COLUMN_NAME = ...` |

`actual.TABLE_SCHEMA = DATABASE()`(61·96·142·170·197행), `actual.TABLE_TYPE = 'BASE TABLE'`(63행),
`actual.COLUMN_TYPE = 'enum(...)'`(160행)은 리터럴/함수 쪽이라 **안전하다. 고치지 말 것.**

**판별 프로브** (운영 DB에 붙여 그대로 실행, 읽기 전용·1초)

```sql
SELECT 1
  FROM (SELECT 'users' AS t) AS x
  JOIN information_schema.TABLES AS a
    ON a.TABLE_SCHEMA = DATABASE() AND a.TABLE_NAME = x.t
 LIMIT 1;
```
> ⚠️ 위 프로브는 파생 테이블이 **병합**될 수 있어 통과하고도 본문은 실패할 수 있다.
> 확실하게 보려면 `UNION ALL`을 넣어 구체화를 강제한다:
> ```sql
> SELECT 1
>   FROM (SELECT 'users' AS t UNION ALL SELECT 'department') AS x
>   JOIN information_schema.TABLES AS a
>     ON a.TABLE_SCHEMA = DATABASE() AND a.TABLE_NAME = x.t;
> ```
> 2행이 나오면 안전, `ERROR 1267`이면 아래 수정안을 적용한다.

**수정안** — information_schema 쪽을 연결 문자셋으로 명시 변환한다. `CONVERT(x USING utf8mb4)`의 결과는
`utf8mb4_0900_ai_ci`이므로 파생 테이블 컬럼과 collation이 같아져 충돌이 사라진다.

```sql
-- §1 62행
      AND CONVERT(actual.TABLE_NAME USING utf8mb4) = required.table_name

-- §2 97~98행
      AND CONVERT(actual.TABLE_NAME  USING utf8mb4) = required.table_name
      AND CONVERT(actual.COLUMN_NAME USING utf8mb4) = required.column_name

-- §3 110~111행 (두 군데 — CASE 안과 SELECT 목록 118행 모두 같은 형태로)
        WHEN GROUP_CONCAT(CONVERT(actual.COLUMN_NAME USING utf8mb4)
                          ORDER BY actual.SEQ_IN_INDEX SEPARATOR ',')
                 = required.expected_columns

-- §3 143~144행 / §4 171~172행 / §5 198~199행 — 위와 같은 형태로 TABLE_NAME·COLUMN_NAME·INDEX_NAME 감싸기

-- §5 183~185행
        WHEN CONVERT(MIN(actual.REFERENCED_TABLE_NAME)  USING utf8mb4) <> required.referenced_table
          OR CONVERT(MIN(actual.REFERENCED_COLUMN_NAME) USING utf8mb4) <> required.referenced_column THEN 'MISMATCH'
        WHEN CONVERT(MIN(actual.CONSTRAINT_NAME) USING utf8mb4) <> required.expected_name THEN 'NAME_MISMATCH'
```

이 수정은 P2-F(`SET NAMES utf8mb4`)와 반드시 **짝으로** 넣는다. 연결 문자셋이 utf8mb4가 아니면 변환 방향이 어긋난다.

## 3. 남은 P1

### P1-A. §6·§7이 실패하면 스크립트가 통째로 중단되어 뒤 결과가 사라진다

**해당 행**: §6 `212~222`행, §7 `226~256`행.

`212~222`행의 주석(`209~211`행)은 "PRE 테이블·컬럼이 없으면 오류가 난다"고 인정만 하고 방어하지 않는다.
`mysql --database=... < file` 은 첫 오류에서 **즉시 중단**하므로(`--force` 없을 때) §6이 `ERROR 1146`/`1054`로
터지면 §7은 아예 출력되지 않는다.

더 나쁜 건 §7이다. **4개 카운트가 하나의 `UNION ALL` 단일 문장**이라, `department` 테이블 하나가 없으면
`users` 관련 3개 카운트까지 함께 사라진다. §7은 "#1·#2·#5·#11을 돌릴지" 판단하는 유일한 자료다.

§1~§5는 `LEFT JOIN` 구조라 대상이 없어도 안전하게 `STOP`/`PENDING`을 출력한다 — DATA 절만 이 성질이 없다.

**수정안 1 (§6)** — 다른 backfill이 이미 쓰는 prepared statement 관용구로 감싼다. 읽기 전용을 유지한다.

```sql
SET @orphan_ready := (
  (SELECT COUNT(*) FROM information_schema.TABLES
    WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME IN ('welfare_requests','users')) = 2
  AND
  (SELECT COUNT(*) FROM information_schema.COLUMNS
    WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'welfare_requests'
      AND COLUMN_NAME IN ('primary_approver_id','sub_approver_id')) = 2
);
SET @sql := IF(@orphan_ready,
  'SELECT ''DATA'' AS check_group, ''welfare approver orphans'' AS check_name,
          COUNT(*) AS observed_count, IF(COUNT(*) = 0, ''OK'', ''STOP'') AS result,
          ''#7이 SIGNAL 45000으로 중단된다 — 먼저 고아 행을 고칠 것'' AS rule
     FROM welfare_requests AS wr
     LEFT JOIN users AS up ON up.id = wr.primary_approver_id
     LEFT JOIN users AS us ON us.id = wr.sub_approver_id
    WHERE up.id IS NULL OR (wr.sub_approver_id IS NOT NULL AND us.id IS NULL)',
  'SELECT ''DATA'' AS check_group, ''welfare approver orphans'' AS check_name,
          NULL AS observed_count, ''SKIPPED'' AS result,
          ''PRE 테이블·컬럼 부재 — §1·§2의 STOP을 먼저 해결한 뒤 재실행'' AS rule');
PREPARE stmt FROM @sql; EXECUTE stmt; DEALLOCATE PREPARE stmt;
```

**수정안 2 (§7)** — `UNION ALL` 하나를 **4개 독립 SELECT 문장으로 분리**한다(각 문장 뒤 `;`).
하나가 실패해도 나머지는 이미 출력된 뒤이고, 나눠 두면 위와 같은 가드를 개별로 붙일 수도 있다.

**수정안 3 (문서)** — 실행 예(`8`행)에 대안을 병기한다:
`mysql --database=mlsoft_leave --force < preflight-2026-08-23-operational.sql`
(`--force`는 오류를 넘기지만 **오류 자체를 놓치기 쉬우므로** 수정안 1·2를 우선한다.)

### P2-E. §4 ENUM 판정이 `#10`의 멱등 조건보다 엄격해 오탐(중단)이 날 수 있다

`160`행은 **문자열 완전 일치**를 요구한다. 반면 `#10`(`backfill-2026-08-16-user-restore.sql:26`)은
`COLUMN_TYPE LIKE '%USER_RESTORED%'` 로 건너뛴다. 두 판정이 갈리는 구간이 있다:

- 값 목록에 `USER_RESTORED`는 있으나 **순서만 다른** DB → preflight `MISMATCH`(헤더 `14`행 규칙상 중단)이지만
  `#10`은 스킵하고 애플리케이션은 정상 동작한다. → **불필요한 배포 중단**
- `USER_RESTORED`는 있으나 **다른 값이 빠진** DB → `#10`이 스킵해 구멍이 남는다. preflight가 이걸 잡는 건 **정상이고 가치 있다.**

**수정안** — 완전 일치는 그대로 두고 두 경우를 구분할 컬럼을 하나 더 낸다(§4 `164`행 뒤):

```sql
    IF(actual.COLUMN_TYPE LIKE '%USER_RESTORED%',
       'CONTAINS_USER_RESTORED (#10은 스킵한다)',
       'MISSING_USER_RESTORED (#10이 MODIFY를 수행한다)') AS enum_note,
```
헤더 `14`행에도 "ENUM MISMATCH는 `enum_note`를 함께 볼 것"을 덧붙인다.

### P2-F. `SET NAMES utf8mb4;` 부재 — 한글 리터럴 비교·출력이 클라이언트 설정에 좌우된다

`248`행 `WHERE name = '미배정'`, `217`행의 한글 출력 문자열이 클라이언트 기본 문자셋에 의존한다.
Windows의 `my.ini`에 `default-character-set`이 다르게 잡혀 있으면 `248`행이 조용히 0을 반환해
"미배정 부서 없음"이라는 잘못된 결론이 나온다(`#11` 2부는 같은 조건으로 UPDATE하므로 실제와 어긋난다).

**수정안** — 헤더(`17`행) 직후에 한 줄. 세션 설정이라 읽기 전용 원칙을 깨지 않는다:
```sql
SET NAMES utf8mb4;
```
**P0-A 수정안의 전제이기도 하다.**

### P2-G. `NAME_MISMATCH`를 중단 사유로 묶은 것은 과하다

헤더 `14`행이 `MISMATCH / DUPLICATE / NAME_MISMATCH`를 동급으로 "중단"시킨다.
그런데 `#7`의 `add_fk_if_missing`(`backfill-2026-08-10-welfare-fk-indexes.sql:48~66`)은 **이름이 아니라 컬럼으로**
존재 여부를 본다(그 파일 `44~47`행에 이유가 적혀 있다). 이름이 달라도 `#7`은 스킵하므로 중복 FK가 생기지 않고,
Hibernate `validate`는 FK 이름을 검사하지 않는다. → **순수 표기 차이인데 배포가 멈춘다.**

**수정안** — `14`행을 둘로 나눈다:
```
--   MISMATCH / DUPLICATE는 중단 후 staging에서 원인을 확인한다.
--   NAME_MISMATCH는 진행 가능 — #7이 컬럼 기준으로 건너뛰고 validate는 FK 이름을 보지 않는다.
--   배포 기록에만 남긴다.
```

### P2-H. §7 `new-hires` 카운트가 `#5`의 실제 대상보다 넓다 (라벨 문제)

`240`행은 `hire_date > DATE_SUB(CURDATE(), INTERVAL 1 YEAR)`만 본다.
`#5`(`backfill-2026-08-08-scheduler.sql:56~60`)의 UPDATE는 여기에 `AND monthly_granted_count = 0`이 더 붙는다.
그 컬럼은 `POST:#5`라 `#5` 실행 전에는 참조할 수 없으므로 **구조상 불가피하다** — 다만 숫자의 의미가 다르다.

**수정안** — `238`행 라벨을 바꿔 오해를 막는다:
`'review before #5 (상한값 — 실제 변경 행은 이보다 적거나 같다)'`

같은 맥락으로 `230`행 `'review before #2'`도 의미를 적어 두면 좋다 —
이 인원은 `#2` 2부로도 `COMPLETED`가 되지 않아 **온보딩을 다시 밟아야 하는 사람**이다.

### P2-I. §3·§5의 CASE가 `expected_state`를 쓰지 않는다 (잠복)

§3 `108~115`행, §5 `180~187`행의 CASE에는 PRE 분기가 없다. 지금은 두 절 모두 POST 행뿐이라 무해하다.
그러나 나중에 PRE 인덱스/FK 행을 한 줄 추가하는 순간 **`STOP`이 아니라 `PENDING`으로 조용히 오판**한다 —
P0-2가 고친 것과 정확히 같은 종류의 혼선이다.

**수정안** — §1·§2와 같은 형태의 가드를 미리 넣어 둔다:
```sql
        WHEN COUNT(actual.INDEX_NAME) = 0 AND required.expected_state = 'PRE' THEN 'STOP'
        WHEN COUNT(actual.INDEX_NAME) = 0 THEN 'PENDING'
```

### P2-J. ENUM 값 목록 검사가 `admin_audit_log.action` 하나뿐이다

`CLAUDE.md`가 경고하듯 `ddl-auto: validate`는 **ENUM 값 목록을 전혀 검사하지 않는다**.
`schema.sql`에는 ENUM 컬럼이 13개(고유 enum 10종) 있는데 §4는 1개만 본다.
나머지는 값을 처음 저장하는 요청에서 500(`Data truncated`)으로 조용히 터지는, `#10`과 **동일한 실패 유형**이다.

미검사 12개: `email_history.email_type`(`schema.sql:93`), `email_history.status`(`97`),
`leave_action_history.action`(`125`), `leave_requests.leave_type`(`182`), `leave_requests.status`(`184`),
`schedule_entries.schedule_type`(`235`), `users.onboarding_status`(`260`), `users.role`(`263`),
`welfare_action_history.action`(`279`), `welfare_policies.target`(`306`),
`welfare_requests.status`(`320`), `welfare_requests.target`(`322`).

**수정안** — §4를 §1·§2와 같은 파생 테이블 목록 방식으로 일반화하고, 기대 문자열은 위 `schema.sql` 행에서 그대로 복사한다.
(이번 배포 범위에서는 `#10`만 값이 늘었으므로 **배포 차단 사유는 아니다.** 다음 enum 확장 전에 넣어 두는 것이 목적이다.)

## 5. 실행 전 권고 순서

1. **P0-A 프로브를 먼저 돌린다.** `ERROR 1267`이면 preflight는 한 줄도 출력하지 않는다 — 이것부터 판별해야 나머지가 의미 있다.
2. P2-F(`SET NAMES utf8mb4;`)를 넣는다. P0-A 수정안의 전제이자 `248`행 한글 비교의 전제다.
3. P1-A(§6·§7 가드/분리)를 넣는다. 초기 DB일수록 이 절이 먼저 터지고, 터지면 판단 자료를 통째로 잃는다.
4. P1-B·P1-C·P2-D는 목록에 행만 추가하는 변경이라 함께 처리한다.
5. P2-E·P2-G는 판정 문구 조정이다. **오탐으로 배포를 멈추지 않기 위해** 실행 전에 정리하는 편이 낫다.
6. P2-I·P2-J는 이번 배포를 막지 않는다. 다음 스키마 변경 전까지 처리.

## 6. 확인하지 못한 것

- **preflight를 실제 DB에서 실행하지 못했다.** 로컬 MySQL 자격증명이 `application-local.yml`에만 있고
  이번 작업 지시가 비밀 파일 열람을 금지했다. `mysql -u root`(무암호) 접속은 `ERROR 1045`로 거부됐다.
  따라서 P0-A는 **정적 분석에 근거한 위험 판정**이며, 확정 결함으로 보고하지 않는다.
- 운영 DB의 실제 상태(테이블·컬럼·인덱스·ENUM 현황)는 여전히 미확인이다.
  `docs/설계-초안/2차-QA-실행-감사-codex-2026-08-22.md`의 M-4·M-5가 그대로 열려 있다.
- 로컬은 MySQL 9.6, 운영 이미지는 `mysql:8.0`(`docker-compose.prod.yml:8`)이다.
  로컬에서 통과해도 운영 버전에서 한 번 더 확인해야 한다 — 특히 P0-A의 collation 동작이 그렇다.

## 7. 코디네이터 반영 결과

재감사 권고 중 배포 전 안정성에 직접 영향을 주는 항목을 반영했다.

- P0-A: `SET NAMES utf8mb4`와 `CONVERT(... USING utf8mb4)` 적용
- P1-A: §6·§7을 PRE 객체 부재 시 `SKIPPED_PRE_MISSING`으로 반환하는 독립 prepared SELECT로 전환
- P1-B/P1-C: 기반 컬럼, #6 감사 로그 대표 컬럼·인덱스 3개 추가
- P2-D/E/F/G/H/I: `users.name`, ENUM note, 한글 세션, FK 이름 판정, 영향량 라벨, PRE 가드 보완

수정 후에도 실제 MySQL 8 staging 실행은 하지 않았다. 전체 ENUM 13개 대조(P2-J)는 다음 ENUM
확장 작업 전의 후속 보강 항목으로 남긴다.

최종본에 대한 Opus 중간 노력 재검증도 통과했다(P0/P1 없음). 남은 관찰은 대상 DB명을
`mlsoft_leave`로 고정한 안전장치, `USER_RESTORED`가 있으나 ENUM 순서가 다른 환경의 `MISMATCH`
판독, 그리고 UNION 분기의 불필요한 별칭 정도이며 배포 차단 항목은 아니다.
