# mlsoft-leave-system 2차 QA 실행 보고서

> 관련: [`docs/13-QA-체크리스트.md`](../13-QA-체크리스트.md) · [`docs/12-남은-작업.md`](../12-남은-작업.md) · `01 Projects/mlsoft-leave-system 2차 QA 실행 보고서.md`

## 이 보고서의 성격

이번 문서는 읽기 전용 코드 감사만 한 보고서가 아니라, 최신 `design/cobalt-glass-redesign` 브랜치에서
백엔드·프론트 전체 자동 테스트를 실제 실행한 회귀 검증 기록이다. 브라우저를 띄운 수동 QA와
운영 DB backfill 실행은 포함하지 않는다.

검증 기준은 커밋 `12bb2d0`과 그 위의 미커밋 변경이다.

- `frontend/src/pages/TeamPage.jsx`
- `frontend/src/pages/TeamPage.test.jsx`
- `docs/12-남은-작업.md`
- `docs/13-QA-체크리스트.md`

Gradle의 첫 실행은 `UP-TO-DATE`였으므로, 최종 수치는 `--rerun-tasks`로 캐시를 우회한 실행을 기준으로 삼았다.

Claude Opus가 같은 브랜치를 읽기 전용으로 교차 검증했다. 테스트 수치와 E-1 회귀 범위는 일치했고,
backfill의 `email_history`·`department.parent_id` 선행 조건과 테이블 inventory 보강 필요성을 추가로 확인했다.
Opus는 코드·문서·커밋을 변경하지 않았다.

## 2. 이번 변경점 검증

### E-1 — 미배정 부서와 팀장 공석 표시 분리

`TeamPage`는 부서 이름 문자열이 아니라 서버의 `DepartmentResponse.unassigned` 플래그를 사용한다.

| 데이터 상태 | 화면 표시 | 검증 |
|---|---|---|
| 실제 부서 + 팀장 지정 | 팀장 이름 | 기존 회귀 테스트 통과 |
| 실제 부서 + `leader_id` 없음 | `미지정` | 신규 테스트 통과 |
| `unassigned=true` | `부서 미배정` | 신규 테스트 통과 |

관련 구현은 [`TeamPage.jsx`](../../frontend/src/pages/TeamPage.jsx:65), 회귀 케이스는
[`TeamPage.test.jsx`](../../frontend/src/pages/TeamPage.test.jsx:53)에 있다.

이 수정은 잘못된 화면 표시만 분리한다. 팀장을 다른 부서로 옮긴 뒤 원래 부서의 `leader_id`가 남는
S-8 백엔드 원인 자체는 수정하지 않았으며, 제품 정책 결정이 필요하다.

### P0 — 운영 backfill 런북 정합성

[`docs/12-남은-작업.md`](../12-남은-작업.md:6)의 배포 표를 운영 대상 11개 기준으로 갱신했다.

- `backfill-2026-08-12-email.sql` 추가
- `backfill-2026-08-21-department-system-default.sql` 추가
- `backfill-2026-08-16-demo-email-domain.sql`은 로컬 전용으로 명시
- 컬럼·ENUM·인덱스·FK 누락을 확인하는 읽기 전용 `db/preflight-2026-08-23-operational.sql` 추가
- Flyway 도입 선행 조건을 운영 대상 11개 실행으로 정정

추가로 `backfill-2026-08-12-email.sql`은 `email_history` 테이블을 생성하지 않고 컬럼·인덱스만
보정한다. 기존 3개 누락 테이블 backfill에도 이 테이블은 없다. 따라서 preflight에서 테이블이 없으면
해당 SQL을 중단하고 `db/schema.sql`의 해당 CREATE TABLE만 바탕으로 별도 멱등 생성 migration을
staging에서 검토해야 한다. `schema.sql` 전체를 운영 DB에 재실행해서는 안 된다.

실제 운영 DB에 SQL을 실행하지 않았으므로 적용 완료로 표시하지 않는다.

## 3. 새로 발견된 결함

### [P0] 11개 backfill 순서만으로는 모든 운영 DB를 준비할 수 없음

`backfill-2026-08-12-email.sql`은 `email_history` 테이블이 이미 있다는 전제에서
`retry_count`와 인덱스만 추가한다. `backfill-2026-08-11-missing-tables.sql`도
`holidays`, `schedule_entries`, `schedule_dates`만 만든다. 따라서 email 기능 도입 전의
운영 DB에 `email_history`가 없으면 #8의 UPDATE에서 `ERROR 1146`으로 중단된다.

`backfill-2026-08-21-department-system-default.sql`도 `department.parent_id` 뒤에 컬럼을
추가하도록 작성되어 있어, 해당 선행 컬럼이 없는 DB에서는 `ERROR 1054`가 난다.
운영 DB inventory에서 두 전제조건을 확인하기 전에는 11개를 일괄 실행하면 안 된다.

### [P1 보완 완료] 기존 preflight가 컬럼 조회만으로는 테이블 부재를 명확히 표시하지 못함

`information_schema.COLUMNS` 결과에 행이 없는 이유가 테이블 자체 부재인지 컬럼 부재인지
구분되지 않았다. 이를 보완하기 위해 `db/preflight-2026-08-23-operational.sql`에서
`information_schema.TABLES`와 `COLUMNS`를 별도로 대조하고, `department.active`·`parent_id`,
`email_history.error_message`, 인덱스 컬럼 순서·UNIQUE 여부, 전체 `USER_RESTORED` ENUM,
복리후생 승인자 FK와 고아 데이터까지 확인하도록 했다.

2026-08-23 Opus 1차 재감사에서 발견한 판정 혼선도 수정했다. PRE 선행조건의 `STOP`과 POST
산출물의 `PENDING`을 분리했고, POST가 이미 있으면 `ALREADY_APPLIED`로 표시한다. 따라서
`PENDING` 자체는 오류가 아니며, `MISMATCH`·`DUPLICATE`가 중단 대상이다. `NAME_MISMATCH`는
참조 대상이 맞을 때 기록만 남긴다.
수정본은 아직 운영 DB에서 실행하지 않았으므로 실제 환경 상태는 미확인이다.

### [Opus 2차 재감사 반영] 실행 안정성 보완

Opus가 `schema.sql`·운영 대상 backfill 11개와 수정본을 다시 대조했다. 이전 감사 5건은 모두
반영됐지만, 실제 실행 전 확인이 필요한 신규 위험을 추가로 발견해 다음을 반영했다.

- `SET NAMES utf8mb4`와 `CONVERT(... USING utf8mb4)`를 추가해 MySQL 8
  `information_schema`와 파생 테이블의 collation 충돌 가능성을 낮췄다.
- §6·§7 데이터 점검을 세션 전용 prepared SELECT와 독립 SELECT로 바꿔 PRE 테이블·컬럼이
  없을 때 `SKIPPED_PRE_MISSING`을 남기고 다른 점검 결과를 잃지 않게 했다.
- §2에 `users.name`·기반 잔액 컬럼·`department.name`을 추가하고, #6 감사 로그 대표 컬럼과
  인덱스 3개를 추가 대조한다.
- FK의 참조 schema까지 확인하고, `NAME_MISMATCH`는 대상이 올바르면 기록만 남기는 상태로
  구분했다. ENUM에는 `enum_note`를 추가했다.

상세 재감사 결과는 [`preflight-2차-재감사-2026-08-23.md`](preflight-2차-재감사-2026-08-23.md)에
남겼다. 아직 실제 MySQL 8 staging 실행은 하지 않았고, 전체 ENUM 목록(이번 배포 범위 외)은
다음 스키마 확장 전 보강 항목으로 남아 있다.

최종 수정본을 Opus가 다시 읽기 전용 검증한 결과는 **P0/P1 없음**이다. 남은 관찰은 대상 schema
고정, ENUM 순서가 다른 환경의 판독, UNION 별칭 형식뿐이며 기능·배포 차단 항목은 아니다.

다음 위험은 기존 미해결 항목이며 이번 QA에서 해결하지 않았다.

| 우선순위 | 항목 | 현재 상태 |
|---|---|---|
| P0 | 운영 DB backfill 및 선행 테이블·컬럼 존재 여부 | staging 백업·inventory·조건부 실행·validate 기동 검증 필요. 문서만 갱신 |
| P1 | S-8 팀장 부서 이동 정책 | 해제·자동 이동·이동 거부 중 제품 결정 필요. 권고는 이동 거부 + 409 |
| P1 | S-9 팀장 교체·강등 동시성 | Department/승인자 잠금 및 재검증 설계 필요 |
| P2 | 프론트 JS chunk 551.78 kB | 기능 실패 아님. 추후 code splitting 검토 |
| P2 | `StatusBadge.jsx` Fast Refresh 경고 | 기존 경고. 기능 테스트는 통과 |

## 5. 다음 작업 순서

1. 운영 DB 접근 권한이 있는 환경에서 원본 백업과 staging restore를 수행한다.
2. `db/preflight-2026-08-23-operational.sql`에서 대상 schema가 맞고 PRE `STOP`·구조 `MISMATCH`가 없는지 확인한다. POST `PENDING`은 해당 단계 실행 전 정상으로 기록한 뒤, 운영 대상 backfill 11개를 문서 순서대로 검증하고 `ddl-auto=validate` 기동을 확인한다.
3. S-8 정책을 확정한다. 권고안은 현재 팀장 부서 이동을 거부하고 명시적 409를 반환하는 방식이다.
4. S-9 잠금·승인자 재검증을 구현한 뒤 MySQL 8 동시성 테스트를 추가한다.
5. M-1~M-6과 docs/13의 미확인 수동 QA를 실제 브라우저·staging에서 수행한다.

## 결론

최신 브랜치의 자동 회귀 검증은 백엔드 361건과 프론트 219건 모두 통과했다.
이번 E-1 표시 수정은 회귀 테스트와 빌드/lint를 통과했고, 배포 문서의 누락된 backfill도 보완했다.
다만 운영 DB 적용과 브라우저 수동 QA는 아직 완료되지 않았으며, S-8·S-9 백엔드 동작은 정책 결정 후
별도 구현·동시성 검증이 필요하다. 수정된 preflight도 운영 DB에서 실행한 결과가 없어 배포 가능 판정은
아직 내리지 않았다.
