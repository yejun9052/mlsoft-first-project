## 변경 목록

| # | 파일 경로 | 변경 | 적용 이유 |
|---|---|---|---|
| 1 | `backend/build.gradle` | Flyway starter·MySQL 모듈 추가 | Spring Boot 기동 시 MySQL 마이그레이션 실행 |
| 2 | `backend/src/main/resources/application.yml` | 공통 Flyway 활성화, JPA `validate` 전환 | 로컬·운영 모두 Flyway가 스키마를 관리 |
| 3 | `backend/src/main/resources/application-prod.yml` | 운영 Flyway 정책 명시 | 기존 DB 자동 baseline 후 누락 migration 실행 |
| 4 | `backend/src/test/resources/application.yml` | Flyway 비활성화 | MySQL 전용 SQL을 H2에서 실행하지 않고 기존 `create-drop` 유지 |
| 5 | `backend/src/main/resources/db/migration/V1__baseline_schema.sql` | 현재 `schema.sql`을 baseline migration으로 이동 | 빈 DB 전체 16테이블 생성 |
| 6 | `backend/src/main/resources/db/migration/V2__backfill_O3.sql` | O-3 backfill 등록 | `department.active`, `advance_days` 정합화 |
| 7 | `backend/src/main/resources/db/migration/V3__onboarding_status.sql` | 온보딩 migration 등록 | 컬럼 추가와 기존 사원 상태 보정 |
| 8 | `backend/src/main/resources/db/migration/V4__query_indexes.sql` | 조회 인덱스 migration 등록 | 기존 DB 인덱스 보강 |
| 9 | `backend/src/main/resources/db/migration/V5__scheduler.sql` | 스케줄러 migration 등록 | 컬럼 3개 및 기존 사원 값 보정 |
| 10 | `backend/src/main/resources/db/migration/V6__admin_audit_log.sql` | 감사 로그 migration 등록 | 기존 DB에 감사 테이블 추가 |
| 11 | `backend/src/main/resources/db/migration/V7__welfare_fk_indexes.sql` | 복리후생 FK·인덱스 migration 등록 | 승인자 참조 무결성 보강 |
| 12 | `docker-compose.prod.yml` | `schema.sql` initdb 마운트 제거 | Flyway를 유일한 스키마 적용 경로로 통일 |

## 코드

### `backend/build.gradle`

기존 `dependencies` 블록의 JPA 의존성 다음에 추가한다.

```groovy
implementation 'org.springframework.boot:spring-boot-starter-flyway'
runtimeOnly 'org.flywaydb:flyway-mysql'
```

Spring Boot의 의존성 관리가 호환 버전을 결정하므로 버전은 직접 지정하지 않는다. MySQL은 별도 Flyway 데이터베이스 모듈이 필요하다. [Spring Boot 공식 문서](https://docs.spring.io/spring-boot/how-to/data-initialization.html)

### `backend/src/main/resources/application.yml`

기존 `spring.jpa` 설정을 다음과 같이 변경하고 `flyway`를 추가한다. 나머지 설정은 그대로 유지한다.

```yaml
spring:
  application:
    name: backend

  datasource:
    url: ${DB_URL:jdbc:mysql://localhost:3306/mlsoft_leave?serverTimezone=Asia/Seoul&characterEncoding=UTF-8}
    username: ${DB_USERNAME:root}
    password: ${DB_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver

  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true
    baseline-version: 1
    validate-on-migrate: true
    clean-disabled: true

  jpa:
    hibernate:
      ddl-auto: validate
    open-in-view: false
    properties:
      hibernate:
        format_sql: true
```

`baseline-version: 1`의 동작은 다음과 같다.

- 빈 DB: baseline을 만들지 않고 `V1`부터 전부 실행한다.
- 테이블은 있지만 `flyway_schema_history`가 없는 DB: 버전 1로 baseline하고 `V2`부터 실행한다.
- 이미 최신 backfill이 수동 적용된 DB: `V2`~`V7`이 멱등 조건에 따라 no-op 처리된 뒤 이력만 기록된다.
- 일부 backfill만 적용된 DB: 존재하지 않는 컬럼·인덱스·FK만 추가되고 필요한 DML이 실행된다.

### `backend/src/main/resources/application-prod.yml`

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true
    baseline-version: 1
    validate-on-migrate: true
    clean-disabled: true

  jpa:
    hibernate:
      ddl-auto: validate
    open-in-view: false
    properties:
      hibernate:
        format_sql: false

  datasource:
    hikari:
      initialization-fail-timeout: 30000

logging:
  level:
    com.mlsoft.backend: info
    org.hibernate.SQL: warn
```

`application-local.yml`은 시크릿 파일이므로 확인하거나 수정하지 않는다. 공통 설정을 상속하면 로컬도 Flyway + `validate`로 동작한다.

### Flyway migration 파일 배치

질문의 “backfill 5개”와 달리 실제 목록에는 6개가 있다. 누락 없이 다음처럼 버전을 부여한다.

```text
backend/src/main/resources/db/migration/
├── V1__baseline_schema.sql
├── V2__backfill_O3.sql
├── V3__onboarding_status.sql
├── V4__query_indexes.sql
├── V5__scheduler.sql
├── V6__admin_audit_log.sql
└── V7__welfare_fk_indexes.sql
```

원본 대응은 다음과 같다.

```text
db/schema.sql
→ backend/src/main/resources/db/migration/V1__baseline_schema.sql

db/backfill-2026-08-07-O3.sql
→ backend/src/main/resources/db/migration/V2__backfill_O3.sql

db/backfill-2026-08-08-onboarding-status.sql
→ backend/src/main/resources/db/migration/V3__onboarding_status.sql

db/backfill-2026-08-08-query-indexes.sql
→ backend/src/main/resources/db/migration/V4__query_indexes.sql

db/backfill-2026-08-08-scheduler.sql
→ backend/src/main/resources/db/migration/V5__scheduler.sql

db/backfill-2026-08-10-audit-log.sql
→ backend/src/main/resources/db/migration/V6__admin_audit_log.sql

db/backfill-2026-08-10-welfare-fk-indexes.sql
→ backend/src/main/resources/db/migration/V7__welfare_fk_indexes.sql
```

`V1__baseline_schema.sql`에서는 Flyway 접속 DB 밖을 조작하지 않도록 다음 두 문장만 제거한다.

```sql
CREATE DATABASE IF NOT EXISTS `mlsoft_leave`
  DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE `mlsoft_leave`;
```

나머지 16테이블 DDL은 현재 `db/schema.sql`과 동일하게 유지한다. `V2`~`V7`도 기존 SQL 본문을 변경하지 않고 그대로 옮긴다. 현재 스크립트들은 `information_schema` 검사 또는 `CREATE TABLE IF NOT EXISTS`를 사용하므로 세 DB 상태를 모두 수용한다.

### `docker-compose.prod.yml`

`mysql.volumes`에서 `schema.sql` 마운트를 제거한 완성 형태다.

```yaml
services:
  mysql:
    image: mysql:8.0
    container_name: mlsoft-leave-mysql-prod
    restart: unless-stopped
    env_file:
      - .env.prod
    environment:
      MYSQL_ROOT_PASSWORD: ${DB_PASSWORD:?.env.prod에 DB_PASSWORD를 설정하세요}
      MYSQL_DATABASE: mlsoft_leave
      TZ: Asia/Seoul
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_unicode_ci
    volumes:
      - mysql-prod-data:/var/lib/mysql
    healthcheck:
      test: ['CMD', 'mysqladmin', 'ping', '-h', 'localhost', '-uroot', '-p${DB_PASSWORD}']
      interval: 5s
      timeout: 5s
      retries: 20

  app:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: mlsoft-leave-app
    restart: unless-stopped
    depends_on:
      mysql:
        condition: service_healthy
    env_file:
      - .env.prod
    environment:
      DB_URL: jdbc:mysql://mysql:3306/mlsoft_leave?serverTimezone=Asia/Seoul&characterEncoding=UTF-8
      DB_USERNAME: root
      SPRING_PROFILES_ACTIVE: prod
      TZ: Asia/Seoul
    ports:
      - '8080:8080'

volumes:
  mysql-prod-data:
```

## 적용 주의사항

- 운영 적용 직전 DB 백업이 필요하다.
- `V1`~`V7`은 병합 후 절대 수정하지 않는다. 수정하면 기존 환경에서 checksum mismatch가 발생한다.
- 이후 변경은 반드시 `V8__...sql`처럼 새 파일로 추가한다.
- `baseline-on-migrate`는 테이블이 있는 모든 비관리 DB를 버전 1로 인정한다. 따라서 `DB_URL`이 올바른 운영 DB인지 배포 전에 확인해야 한다.
- 첫 적용 후 `flyway_schema_history`에 `1` baseline과 `2`~`7` 성공 이력이 있는지 확인한다.
- 읽기 전용 환경이므로 파일 변경과 테스트 실행은 수행하지 않았다.
