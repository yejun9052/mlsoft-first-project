# 재입사자 처리 설계 (2026-09-07)

> 퇴직자가 다시 입사했을 때 연차·근속을 어떻게 다룰 것인가.
> 현재 상태·우선순위의 단일 원본은 `docs/12`다. 이 문서는 착수 전 설계와 결정 근거를 보존한다.
>
> **사용자 결정 (2026-09-07)**
> 1. 이전 근속 기록은 **근속 구간으로 나눠 표시**한다 (현재 근속이 기본, 이전은 접어 둔다)
> 2. 재입사 시 **역할·부서·직책을 승계하지 않는다** — 관리자가 폼에서 부서만 지정
> 3. 재입사일은 **관리자가 직접 넣는다** — 온보딩을 다시 받지 않는다

## 1. 법이 정하는 것

연차는 근로기준법 제60조의 **계속근로기간**을 기준으로 산정한다. 퇴직으로 근로관계가 종료되고
퇴직금·연차수당을 정산했다면 그 기간은 단절이므로, 재입사자는 **신입과 동일**하게 간다.

```
재입사일부터 1년 미만  →  1개월 개근당 1일 (월차)
재입사 1년 후          →  15일
3년 이상부터           →  2년마다 1일 가산 (상한 25일)
```

**예외가 있다.** 형식만 퇴사·재입사이고 실질적으로 근로가 이어진 경우(공백이 매우 짧거나 회사
편의로 형식만 끊은 경우 등)에는 계속근로로 인정될 수 있다. **이건 사실관계 판단이라 회사가 정한다** —
애매하면 노무사 확인이 필요하다. 시스템은 두 경우를 **모두 표현할 수 있어야 한다.**

## 2. 지금은 처리할 방법이 없다

두 경로가 있지만 어느 쪽도 재입사가 아니다.

**퇴직 복구를 쓰면 연차가 틀린다.** `User.restore()`는 `is_active`·`retired_at` 두 플래그만 되돌리고
입사일·잔액·기산일을 그대로 둔다(`UserService.java:355-390`). 5년 근무 후 2년 공백을 두고 재입사한
사람에게 쓰면 **7년차 연차**가 된다. 더 나쁜 것은 그다음이다 — `restore`의 Javadoc이 적어 둔 대로
스케줄러가 `is_active = true`만 보고 대상을 고르므로 **공백 2년치 기산일 리셋이 catch-up으로 돈다.**
재직하지 않은 기간의 연차가 부여됐다 소멸하는 이력이 남는다.

**신규 가입도 안 된다.** `users.email`이 UNIQUE라 같은 이메일로 계정을 새로 만들 수 없고, 퇴직 상태로
로그인하면 `/login?error=retired`로 튕긴다(`CustomOAuth2UserService.ERROR_RETIRED`).

정리하면 **파기 전(3년 내) 재입사는 현재 시스템에서 불가능하거나, 복구를 쓰면 연차가 틀린다.**
파기 후라면 이메일이 바뀌어 신규 가입이 되는데 그건 정상 동작이다.

## 3. 두 액션을 분리한다

| 액션 | 언제 쓰나 | 무엇을 하나 |
|---|---|---|
| **퇴직 복구** (기존) | 착오 퇴직 취소, **계속근로로 인정**하는 경우 | 플래그 2개만 되돌린다. 근속이 이어진 것으로 본다 |
| **재입사 처리** (신규) | 근로관계가 끊어졌다 다시 입사 | 입사일·기산일을 재입사일로, 연차를 0부터 |

§1의 예외(계속근로 인정)가 **기존 복구를 그대로 두는 이유**다. 둘을 합치면 그 판단을 표현할 수단이
사라진다. 화면에서 **언제 어느 것을 쓰는지**를 버튼 옆에 적는다 — 이름만으로는 구분이 안 된다.

## 4. 재입사 처리가 바꾸는 것

`User.rehire(LocalDate hireDate)` 도메인 메서드 하나가 `users`를 바꾼다. Setter를 쓰지 않는다.

| 필드 | 값 | 이유 |
|---|---|---|
| `hire_date` | 재입사일 | 근속연수 정책의 입력이다 |
| `last_reset_date` | **재입사일** | **이 설계에서 가장 중요한 한 줄이다.** 이전 값을 두면 스케줄러가 공백 기간을 catch-up으로 돈다 |
| `base_days`·`bonus_days`·`use_days`·`advance_days` | `0` | 계속근로 단절 — 이전 배정과 빚을 함께 끊는다 |
| `monthly_granted_count` | `0` | 재입사 1개월 후부터 월차를 새로 센다 |
| `last_birthday_grant_year` | `NULL` | 새 근속의 복리는 새로 시작한다 (§8 엣지 참고) |
| `is_active` | `true` | |
| `retired_at` | `NULL` | |
| `role` | `EMPLOYEE` | **승계하지 않는다** — 팀장·총관리자가 재입사만으로 권한을 되찾으면 안 된다 |
| `position` | `NULL` | 인사 정보는 다시 받는다 |
| `department_id` | 폼에서 지정 (기본 미배정) | 2년 사이 조직이 바뀌었을 수 있다 |
| `birth_day` | **유지** | 이미 확인된 값이고 바뀌지 않는다 |
| `onboarding_status` | `COMPLETED` **유지** | 관리자가 입사일을 확정하므로 온보딩을 다시 받지 않는다 |

`advance_days`는 파생값이므로 잔액 3필드를 0으로 만든 뒤 `syncAdvanceDays()`를 호출한다 —
이 필드에 단독 대입하지 않는다는 규칙에 예외를 만들지 않는다.

### 이전 근속의 살아 있는 신청은 종결시킨다

**여기가 조용히 깨지는 자리다.** 잔액을 0으로 만드는데 `PENDING`·`CANCEL_PENDING` 신청이 남아 있으면
불변식이 깨진다 —

> `use_days` = 살아 있는 신청 중 현재 회차 창 안의 날짜 합
> (미래-차감-연차-분리-설계-2026-09-07.md §2)

재입사 처리는 이전 근속의 `PENDING`·`CANCEL_PENDING`을 **`CANCELLED`로 종결**시킨다.
`APPROVED`는 실제로 사용한 기록이므로 건드리지 않는다(이력으로 남는다). 종결도 같은 트랜잭션에서 한다.

## 5. 근속 구간 — 새 테이블 하나

"1기 2019-01-02 ~ 2024-03-15"를 보여주려면 **이전 입사일이 어딘가 남아야 한다.**
지금은 `hire_date`를 덮어쓰면 사라진다.

`employment_periods` 테이블을 만든다 (21번째 테이블).

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | bigint PK | |
| `user_id` | bigint FK | |
| `seq` | int | 1부터. `UNIQUE(user_id, seq)` |
| `hire_date` | date | 그 근속의 입사일 |
| `retired_at` | date | 그 근속의 퇴직일 |
| `created_at` | datetime | |

**행은 재입사 처리 시점에만 생긴다.** 지나간 근속만 여기 남고, **현재 근속은 `users`에 있다.**
그래서 같은 사실이 두 곳에 저장되지 않는다 — `users.role`과 `department.leader_id`에서 한 번 겪은
이중 출처 문제(docs/12 B-9)를 반복하지 않기 위해서다.

- 기존 사원은 행이 0개다. **backfill이 필요 없다** — 재입사한 적이 없으면 이전 근속도 없다
- 현재 근속의 구간 번호 = `이전 근속 수 + 1`

### 신청이 어느 구간에 속하는가

`leave_requests.created_at < 현재 hire_date`면 이전 근속이다. 신청 **시각**으로 가른다 —
날짜(`leave_dates`)로 가르면 퇴직 직전에 낸 미래 연차가 새 근속에 섞인다.

## 6. 화면

### 내 연차 내역 (`HistoryPage`)

```
▼ 2기  2026-09-08 ~ 현재          부여 0 · 사용 0
     (입사 1년 미만 — 월차 적립 중)

▶ 1기  2019-01-02 ~ 2024-03-15   부여 78 · 사용 71   [펼치기]
```

- **현재 근속이 기본으로 펼쳐지고** 이전 근속은 접혀 있다
- **대시보드·사이드바·내 정보의 잔여 숫자는 현재 근속만** 계산한다 (이미 `users` 값이라 그대로다)
- **연차 히트맵도 현재 근속 기간만** 그린다 — 공백 2년이 빈칸으로 남으면 오해를 부른다
- 이전 근속이 없는 사원(대부분)에게는 **구간 UI 자체가 보이지 않는다**. 지금과 똑같이 보인다

### 관리자 — 퇴직 탭

버튼 두 개를 나란히 두고 **언제 쓰는지**를 함께 적는다.

```
[퇴직 복구]   착오 처리를 되돌리거나 계속근로로 인정할 때. 연차·기산일이 그대로 이어집니다.
[재입사 처리] 그만뒀다 다시 입사했을 때. 연차가 0부터 다시 시작합니다.
```

재입사 처리는 모달에서 **재입사일(필수)과 부서**를 받는다. 적용 결과를 모달에 그대로 적는다 —
`역할 팀장 → 사원`, `연차 78/71 → 0/0`, `기산일 2026-09-08`.

## 7. API·스키마

| Method | URL | 설명 | 권한 |
|---|---|---|---|
| POST | `/api/users/{id}/rehire` | 재입사 처리. body `{hireDate, departmentId?}` | SA |
| GET | `/api/leaves/me/periods` | 내 근속 구간 목록 (없으면 빈 배열) | 전체 |

- `AdminAction`에 **`USER_REHIRED`** 추가 — **ENUM 스키마 변경이다.** `admin_audit_log.action`의 값
  목록을 넓히지 않으면 첫 재입사에서 `Data truncated`로 터지고, `ddl-auto: validate`는 이를 잡지 못한다.
  backfill에 `MODIFY COLUMN`을 함께 넣는다
- `employment_periods` 테이블 신설 → `db/schema.sql` + backfill `CREATE TABLE`
- 에러 코드: `NOT_RETIRED`(기존 재사용), `REHIRE_DATE_BEFORE_RETIREMENT`(400) — 재입사일이 퇴직일보다
  앞서면 거부
- **파기된 사원은 대상이 아니다** (`purged_at != null`) — 이메일이 바뀌었으므로 그 사람은 신규 가입으로
  들어온다. 서버에서 막고 이유를 말한다

## 8. 엣지

- **재입사일이 오늘보다 미래**: 허용한다(입사 예정 등록). 단 그날까지는 스케줄러 대상에서 자연히 빠진다
  (`hire_date`·`last_reset_date`가 미래라 `+1년`이 오늘을 넘지 않는다)
- **같은 해에 생일 반차 중복**: 이전 근속에서 올해 생일 반차를 받았고 재입사 후 생일이 또 오면 다시
  받는다. `last_birthday_grant_year`를 비우기 때문이다. **새 근속의 복리는 새로 시작한다**는 판단이고,
  이전 근속에서 받은 보너스는 잔액 초기화로 이미 사라졌으므로 이중 수혜가 아니다
- **퇴직 당일 재입사**: 공백 0일이면 §1의 "실질적 계속근로"에 해당할 가능성이 높다. 시스템은 막지
  않지만 **화면에서 경고**한다 — "공백이 없습니다. 계속근로로 인정해야 하는지 확인하세요"
- **재입사 후 다시 퇴직**: 그냥 퇴직이다. 그 상태에서 또 재입사하면 구간이 3기가 된다
- **이전 근속의 결재 이력**: 그 사람이 남의 건을 결재한 기록은 그대로 남는다. 근속과 무관한 사실이다

## 9. 테스트 계획

1. 재입사 처리 → `hire_date`·`last_reset_date`가 재입사일, 잔액 4필드 0
2. **스케줄러가 공백 기간을 catch-up으로 돌지 않는다** — 재입사 처리 후 리셋 잡을 실행해 확인
3. 이전 근속의 `PENDING`이 `CANCELLED`로 종결되고 `use_days`가 0으로 유지된다
4. `APPROVED`는 그대로 남는다
5. 역할이 `EMPLOYEE`로, 직책이 비고, 부서는 폼 값으로 들어간다
6. `employment_periods`에 이전 근속 행이 1개 생기고 `seq`가 1이다
7. 두 번째 재입사에서 `seq`가 2가 된다
8. 재입사일이 퇴직일보다 앞서면 거부
9. 파기된 사원은 재입사 처리 대상이 아니다
10. 재입사 1개월 후 월차가 1일 적립된다 (`monthly_granted_count` 0부터)
11. 재입사 1년 후 리셋에서 15일이 부여된다 (근속 1년차 정책)
12. 화면: 이전 근속이 없는 사원에게는 구간 UI가 보이지 않는다
13. 화면: 구간이 있으면 현재 근속이 펼쳐지고 이전은 접혀 있다
14. 화면: 퇴직 탭의 두 버튼이 각각 다른 모달을 연다

## 10. 구현 순서

1. **W1 도메인·스키마** — `User.rehire()`, `employment_periods`, `AdminAction` 확장,
   `schema.sql`·backfill. 이전 근속 신청 종결까지. 테스트 1~11
2. **W2 API·관리자 화면** — `POST /rehire`, 퇴직 탭 버튼 2개와 모달. 테스트 14
3. **W3 근속 구간 표시** — `GET /me/periods`, `HistoryPage` 구간 UI, 히트맵 기간 제한. 테스트 12~13

W1만 넣어도 안전하다 — 호출하는 API가 없으면 아무 일도 일어나지 않는다.

## 11. 이 설계가 정한 것 (바꾸려면 여기부터)

1. 복구와 재입사를 **분리한다** — 계속근로 인정 케이스를 표현할 수단이 필요하다 (§3)
2. `last_reset_date`를 재입사일로 **반드시** 바꾼다 — catch-up이 공백을 도는 것을 막는 유일한 지점 (§4)
3. 이전 근속의 살아 있는 신청은 **종결**시킨다 — 잔액 불변식이 깨지지 않게 (§4)
4. 이전 근속은 **별도 테이블**에 남기고 현재 근속은 `users`에 둔다 — 이중 출처를 만들지 않는다 (§5)
5. 역할·직책은 **승계하지 않는다**. 부서만 폼에서 받는다 (§4)
6. 온보딩을 다시 받지 않는다 — 관리자가 입사일을 확정한다 (§4)
