## O. 배포·운영 — 확인 완료 (실측)

### O-1 🔴 `ALLOWED_DOMAIN` 빈 값 배포 시 도메인 검증 fail-open
`.env.prod.example:20`이 `ALLOWED_DOMAIN=`(빈 값)이다. Spring은 **"정의됐으나 빈 문자열"인 환경변수에 기본값(`${ALLOWED_DOMAIN:mlsoft.com}`)을 적용하지 않는다.** `CustomOAuth2UserService:66`의 `isBlank()`가 참이 되어 **도메인 검사를 통째로 건너뛴다.**

docs/08 R-2의 3중 방어 중 ①(OAuth 앱 Internal)은 ⏳ 미적용, ②(`hd` claim)는 `TODO`로 미구현이므로 **이것이 유일하게 살아있는 방어선**인데 스스로를 비활성화한다. 아무 Google 계정으로 로그인·자동가입 후 `/api/leaves/calendar`로 전 직원 일정, `/api/users/approvers`로 팀장·관리자 명부를 수집할 수 있다.

`COOKIE_SECURE`는 `CookieSecurityCheck`로 기동 fail-fast하는데 `ALLOWED_DOMAIN`에는 동등한 장치가 없다 — **비대칭**. 같은 방식의 가드를 추가할 것.

### O-2 🔴 `application-prod.yml` 부재 — 운영이 `ddl-auto: update`를 상속
`docker-compose.prod.yml:44`가 `SPRING_PROFILES_ACTIVE: prod`인데 해당 프로필 파일이 없다(resources에 `application.yml`·`application-example.yml`·`application-local.yml`만 존재). 기동 시 에러도 아니라 조용히 넘어가며, base의 `ddl-auto: update`가 그대로 적용된다. 홈서버 데모가 이미 **운영 DB에 Hibernate가 자동 ALTER를 거는 상태**다 (docs/08 Y-6 위반).

### O-3 🔴 `department.active` backfill 누락 — 현재 로컬 DB가 깨져 있음
커밋 `87be571`에서 `Department.active`가 NOT NULL로 추가됐는데 `ddl-auto: update`는 컬럼 추가만 하고 backfill하지 않는다. MySQL이 기존 행을 `0`으로 채웠다.

```sql
SELECT id, name, active FROM department;
 1 | 미배정 | 0     ← 실측 확인 (2026-07-29)
```

`findByActiveTrueOrderByIdAsc()`가 빈 목록을 반환 → 부서 드롭다운 공백, 부서 수정·팀장 지정·부서 배정이 전부 `NOT_FOUND`. `DataInitializer`는 `existsByName`으로만 판단해 재생성도 안 한다.

```sql
UPDATE department SET active = 1 WHERE active = 0;
```

같은 커밋의 `advance_days`·`advance_used_days`는 암묵 기본값 0이 마침 정답이라 우연히 살아남았다. **`ddl-auto: update`로 NOT NULL 컬럼을 추가할 때마다 재발하는 문제**이므로, Flyway 전환(docs/08 Y-6) 전까지는 컬럼 추가 시 backfill SQL을 함께 남길 것.

### O-4 🟡 `.dockerignore`에 `application-local.yml` 제외 없음
`Dockerfile:20`의 `COPY backend/ ./` → `bootJar`의 `processResources`가 `BOOT-INF/classes/`로 패키징 → **실제 DB 비밀번호·Google client-secret·JWT secret·공휴일 API 키가 운영 이미지에 평문 잔존.** git에서는 정상 제외되나 Docker 컨텍스트에서는 빠져 있다. `prod` 프로필이라 값이 *사용*되지는 않고 노출만 된다.

## I. 연차 정합성 — 돈이 새는 곳

> **✅ I-1·I-2·I-4·I-8 해결 (2026-08-06)** — 네 결함이 한 원인이었고 한 번에 닫혔다.
> `advance_days`를 파생값으로 격하하고 `User.syncAdvanceDays()` 하나만 이 필드에 쓰게 했다.
> 상세는 이 문서 맨 아래 [1순위 수정 결과](#1순위-수정-결과-2026-08-06) 참고.
> **남은 정합성 항목: I-3(당겨쓰기 상한), I-5, I-6, I-7, 신규 I-10·I-11(둘 다 스케줄러 §5 선행).**

### I-1 🔴 → ✅ 해결 `advance_days` 복구가 순서 의존적 — 신청 2건 이상이면 invariant 붕괴
`User.java:158-171`(deduct) / `:180-183`(restore)

`deductLeave`는 invariant를 정확히 유지하지만, `restoreLeave`의 **스냅샷 차감 방식은 복구가 차감의 정확한 역순일 때만** 성립한다.

```
base=10, bonus=0, advance_leave_enabled=true
 A(12일) 신청 → advanceUsed=2 스냅샷, use=12, advance=2
 B(3일)  신청 → advanceUsed=3 스냅샷, use=15, advance=5
 A를 취소     → restoreLeave(12, 2) → use=3, advance=3
                실제 초과분 = max(0, 3−10) = 0  ≠  advance 3
```

다음 기산일에 `User.java:197`의 `baseDays = newBaseDays.subtract(advanceDays)`가 **쓰지도 않은 3일을 삭감**한다. `GET /api/leaves/me/summary`의 `advanceDays`도 즉시 잘못 표시된다.

### I-2 🔴 → ✅ 해결 복리후생 승인이 같은 붕괴를 유발 — 취소 없이, 정상 흐름만으로
`WelfareService.java:123` → `User.addBonusDays`

base=10, use=12, advance=2 상태에서 복리후생 5일 승인 → bonus=5 → 잔여 = 10+5−12 = **+3**. 당겨쓴 게 없어졌는데 `advance_days`는 2로 남아 다음 기산일에 base가 2일 삭감된다.

> **I-1·I-2는 뿌리가 같다.** 복구·가산 시 `advanceDays`를 스냅샷 차감이 아니라 **`max(0, use − base − bonus)`로 재계산**하면 두 결함이 한 번에 사라지고 순서 의존성도 없어진다. `LeaveRequest.advanceUsedDays`는 감사 기록으로만 남긴다.

### I-3 🔴 → ✅ 해결 당겨쓰기 상한 미구현 — 계정이 자력 복구 불가 상태로
docs/02 메모 11이 "확정"한 config `advance_max_days`와 `ErrorCode.ADVANCE_LIMIT_EXCEEDED`가 **둘 다 코드에 없다.** `DataInitializer:78-82`는 3키만 시딩하고, `LeaveService:318`은 on/off만 판정한다.

`LeaveCreateRequest:20`에 날짜 개수 상한(`@Size`)도 없어, 평일 100개를 담아 신청하면 `advance=85` → 다음 기산일에 `base = 15 − 85 = −70` → 이후 모든 신청 실패, **관리자가 `base-days`를 직접 손대기 전까지 복구 불가.** 1000일을 넘기면 `DECIMAL(4,1)` 초과로 400이 아닌 **500**.

**✅ 2026-08-06 해결.** 두 상한을 모두 **관리자 설정**으로 도입했다 (docs/02 3-11 카탈로그):

| 설정 | 기본값 | 검사 위치 | 초과 시 |
|---|---|---|---|
| `advance_max_days` | 5.0 | `User.deductLeave` | `ADVANCE_LIMIT_EXCEEDED` (400) |
| `leave_max_dates_per_request` | 30 | `LeaveService.validateDates` | `TOO_MANY_LEAVE_DATES` (400) |

상한은 **이번 신청분이 아니라 누적 당겨쓰기 총량**에 걸린다 — 건마다 조금씩 당겨써서 누적하는 것이
이 결함의 본질이었다. 날짜 개수는 중복 제거 전 원본 개수로 판정하고, `LeaveCreateRequest`에는
`@Size(max = 366)` 절대 가드를 둬 비정상 페이로드가 DB 조회까지 가지 않게 했다.

판정은 **차감 전에** 한다 — 예외를 던지기 전에 상태를 바꾸면 호출부가 트랜잭션 롤백에 의존한다.
회귀 테스트 5건(도메인) + 3건(서비스)으로 경계값·누적·비허용 분기를 고정했다.

### I-4 🟡 → ✅ 소멸 리셋 시 잔존 PENDING 건의 advance 스냅샷 미처리 — docs/09 설계 누락

## S. 보안

권한 구조 자체는 견고하다. 관리자 전용 엔드포인트 `@PreAuthorize` 누락 0건, IDOR 없음(소유권·승인자 식별이 전부 서비스 계층), 사유 마스킹은 필드를 `null`로 비워 클라이언트 필터링에 의존하지 않으며, `OnboardingCheckInterceptor`가 `@PreAuthorize`보다 먼저 실행돼 강등이 즉시 반영된다. 커밋된 시크릿도 0건(히스토리 스캔 포함). 문제는 입력 경계다.

### S-1 🔴 입사일 자가 신고로 연차 자가 부여
`AuthService.java:51-76`. `OnboardingRequest.hireDate`의 검증이 `@PastOrPresent` 뿐이다. 온보딩에서 입사일을 `2005-01-01`로 넣으면 `MIN(15+(N-1)/2, 25)` 상한인 **연차 25일을 즉시 자가 부여**한다. 관리자 승인·대조 절차가 없다.

**되돌리기 어렵다** — `hire_date`를 수정하는 API가 존재하지 않아(`updateProfile`은 이름·생일만, 관리자 API는 `base-days`만) **영구 고착**되고 기산일 기준까지 오염된다.

docs/01 §2-1이 "위조 방지"를 명시했지만 `base_days` 직접 입력만 막았을 뿐, **그것을 결정하는 입력값이 사용자 통제 하에** 있다. docs/02 메모 9가 이미 지적해둔 항목.

### S-2 🟡 마지막 SYSTEM_ADMIN 락아웃
`UserService:111-116, 156-167`. `changeRole`·`retire` 모두 대상이 마지막 SA인지 검사하지 않는다(`reassignPendingApprovals:183-186`은 이관 대상이 없으면 fallback 조회 자체를 건너뛴다). SA가 0명이 되면 `resolvePrimaryApprover`의 fallback이 비어 **전 직원의 신청이 `INVALID_APPROVER`로 전면 실패**하고, 권한 변경은 SA 전용이라 **DB 직접 UPDATE 외 복구 불가.**

### S-3 🟡 연차·권한 관리자 조작에 감사 흔적 전무
`UserService:110-142`. `changeRole`·`updateBaseDays`에 로그 한 줄도, 이력 테이블 기록도 없다(`retire`만 `log.info`). 내부자가 연차를 25→40일로 올려도 **누가 언제 무엇을 바꿨는지 기록이 없다.** 연차는 급여 직결 수치다.

### S-4 🟡 조회 상한 부재
- `GET /api/leaves/team?from=1900-01-01&to=2999-12-31` — 기간 상한·페이징 없이 `List` 반환. 부서 전원의 전체 연차 이력을 1회 호출로 덤프.
- `POST /api/leaves` — 날짜 개수 상한 없음. `findOverlapping`(IN절 조인)이 잔여 검증보다 **먼저** 실행돼 저비용 요청으로 DB 부하 유발.

### S-5 🟢 수용된 잔존 리스크
- **로그아웃이 토큰을 무효화하지 않음** — 쿠키만 만료, 서버 블랙리스트 없어 유출 토큰은 최대 24h 유효. docs/08 Y-5에서 이미 수용된 결정이며, 퇴직 차단은 인터셉터가 커버하므로 잔존 리스크는 "토큰 탈취" 하나로 좁혀진다.
- `GET /api/leaves/calendar?year=1000000000` → `year` 미검증으로 400이 아닌 **500**.
- 단일 컨테이너 배포 시 `/assets/**`가 `permitAll`이 아니라 **미로그인 사용자가 로그인 화면을 못 봄** (fail-closed라 취약점은 아니나 실배포 시 즉시 드러남).

## D. DB 구조

### D-1 🟡 인덱스 선언 0건
`@Index`·`@Table(indexes=)` grep 전체 0건. docs/02 메모 5가 지정한 5개 중 `users.email`만 `@Column(unique=true)`로 충족. 특히 `leave_dates`의 UK가 `(leave_requests_id, day)` 순서라 **선두 컬럼이 `leave_requests_id`** → `findOverlapping`·`findInDateRange`·`findByDepartmentInDateRange`의 `day between/in` 조건이 인덱스를 못 탄다. 캘린더·팀 현황·중복검사가 전부 풀스캔.

### D-2 🟡 N+1 — fetch join·`@EntityGraph`·`@BatchSize` 모두 0건
`LeaveResponse.of()`(`:37-60`)가 건당 `user`→`department`→`dates`→`primaryApprover`→`subApprover` 5개 LAZY를 건드린다. 20건 페이지 = 최대 100+1 쿼리. 같은 패턴이 `LeaveCalendarResponse.of`·`WelfareResponse.of`·`UserResponse.of`·`DepartmentResponse.of`·`LeaveResetHistoryResponse.of`에 반복.

### D-3 🟡 `holidays.date`에 UNIQUE 없음
공휴일 동기화 재실행 시 같은 날짜가 중복 적재된다. 중요한 건 순서 — **`ddl-auto: update`는 중복 데이터가 쌓인 뒤에는 UNIQUE를 걸어주지 못하고 조용히 실패**하므로 동기화 기능 구현 **전에** 넣어야 한다.

### D-4 🟡 `email_history`에 `retry_count` 없음

`WelfareRequest:56-61`. 연차 쪽(`leave_requests`)은 FK가 있는데 비대칭이다. 참조 무결성이 없어 존재하지 않는 승인자 id가 들어가도 DB가 막지 못하고, FK 자동 인덱스도 없어 `findPendingForApprover`가 풀스캔.

## 2차 리뷰 추가분 (2026-08-06)

전 항목 상태를 실측한 결과 **해결된 항목은 D-2(부분)뿐이고 나머지는 전부 열려 있다.**

### I-8 🔴 → ✅ 해결 관리자 `baseDays` 변경도 `advance_days`를 재계산하지 않음 — I-1·I-2와 같은 붕괴의 세 번째 경로
`User.updateBaseDays()`(`User.java:232`)는 순수 setter다 — `this.baseDays = baseDays`뿐.
`base=10, use=12, advance=2`인 사용자의 base를 관리자가 15로 올려도 `advance=2`가 남는다.
실제 초과 사용은 0인데 다음 기산일에 2일이 또 삭감된다.

1차 리뷰는 복리후생 가산(I-2)만 지적하고 **관리자 기본연차 변경 경로를 놓쳤다.**
→ I-1·I-2·I-8은 **한 가지 원인**이다: `advance_days`가 파생값인데 여러 경로에서 독립적으로 누적·차감된다.

**수정: 단일 재계산 규칙으로 통합**
```
advance_days = max(0, use_days − base_days − bonus_days)
```
잔액 구성요소(`base`/`bonus`/`use`)를 건드리는 **모든** 도메인 메서드가 이 함수를 호출하게 한다.
순서 의존성이 사라지므로 I-1의 "취소 순서에 따라 결과가 달라짐"도 함께 닫힌다.

### I-10 🟡 기산일을 걸친 신청의 반려·취소가 `use_days`를 과다 복구 — 스케줄러 착수 시 발현
`LeaveService.restoreAndRecord:312` 외 복구 3경로가 `fresh.getDays()`(신청 전체 일수)를 되돌린다.

지금은 스케줄러가 없어 발현하지 않지만, docs/09 §5의 "미래 승인분 재차감"이 들어오면 즉시 문제가 된다 —
재차감은 **날짜 단위**로 기산일 이후만 새 `use_days`에 넣는데, 복구는 **신청 단위**로 전체를 뺀다.

```
기산일 3/1인 사원, 2/28~3/2 3일 신청(승인)
 3/1 리셋 → newUse = 2  (3/1·3/2만 재차감, 2/28은 지난 연도에서 이미 소비)
 이후 그 신청을 소급 취소·반려 → restoreLeave(3.0) → use = −1
결과: 잔여 1일 과다 — 연차를 공짜로 하루 더 받는다
```

불변식 자체는 깨지지 않는다(`advance`는 여전히 0). **틀리는 건 `use_days`다.**

**수정 방향**: 복구량을 "리셋 이후 실제로 재차감된 날짜의 일수"로 계산해야 한다.
신청의 전체 일수가 아니라 `dates`에서 `lastResetDate` 이후 날짜만 세는 것이 자연스럽다.
스케줄러 §5 구현과 **같은 커밋에서** 처리할 것 — 따로 하면 한쪽만 반영돼 부호가 뒤집힌다.

> 발견: Codex(leave-invariant-auditor), 1순위 수정 감사 중. I-4를 닫으면서 그 자리에 남는
> 별개 문제로 분리했다.

### I-11 🟡 `carriedUse` 도입 시 기존 `advance`와 이중 반영 — 스케줄러 §5 선행 결정 필요
docs/09 §4가 지시하는 `resetAnnualLeave(newBase, carriedUse, carriedBonus, resetDate)` 시그니처로 가면,
**기존 `advance_days`와 `carriedUse`가 같은 신청에서 유래해 같은 일수를 두 번 센다.**

```
리셋 전  base=15, use=20, advance=5   (20일 전부 새 연도 날짜의 승인분)
리셋     base = 15 − 5 = 10,  use = 20  → 재계산 advance = 10
경제적 초과분 5일 → 10일로 잡힘
```

그 20일은 이전 연도에 선차감돼 이미 `advance=5`를 만들었는데, `carriedUse`로 새 연도에 또 차감된다.

**수정 방향은 셋 중 하나**(docs/09 §5 정정 블록에 상세): ① 리셋에서 차감할 `advance` 중 `carriedUse`와
겹치는 몫 제외 ② 채무를 발생 연도 기준 분리 ③ 기존 채무·미래 사용분을 한 번씩만 반영하는 통합 전이식.

지금은 `carriedUse` 인자가 없어 발현하지 않는다. **I-10과 함께 스케줄러 §5 착수 시 같은 커밋에서** 결정할 것.

> 발견: Codex(leave-invariant-auditor) 시나리오 F 검증. 1순위 수정(리셋 재계산)이 현재 시그니처에서는
> 정확하지만 `carriedUse`가 들어오면 불충분해진다는 것을 확인했다.

### I-9 🟡 부서가 자기 자신을 상위 부서로 지정 가능 — 트리에서 사라짐
`DepartmentService.update()`가 `validateParent(request.parentId())`를 호출하는데 **수정 대상 `id`를 넘기지 않는다**(`DepartmentService.java:73`).
루트 부서가 자기 ID를 `parentId`로 보내면 — 조회된 parent(=자기 자신)의 `parentId`가 null이라 검증을 통과한다.
결과: 자기참조 사이클. `getTree()`는 `parentId == null`만 루트로 뽑으므로 **그 부서가 트리에서 사라진다.**

**수정**: `parentId.equals(id)` 명시적 거부 + `validateParent(id, parentId)`로 시그니처 변경.
기존 테스트에 자식 부서를 parent로 지정하는 케이스는 있으나 자기참조는 없다(`DepartmentServiceTest.java:62`).

### S-6 🟡 팀장 처리 이력 스코프가 "리더인 부서"가 아니라 "소속 부서"
`LeaveHistoryService.java:46`·`WelfareHistoryService.java:40`이 `requester.department.id`만 쓰고
`department.leader.id == requester.id`를 검증하지 않는다. 컨트롤러도 역할만 본다.

따라서 **TEAM_LEADER 역할이지만 다른 사람이 리더인 부서에 배정된 사용자**가 그 부서 전원의
처리 이력을 볼 수 있다 — 처리 의견·신청 사유까지 포함된다(`LeaveHistoryLogResponse.java:39`).

주의: 이건 "파라미터 대신 서버가 결정"이라는 원래 설계 의도는 지킨다. 다만 그 결정 기준이
의도보다 넓다. **정책 확정이 먼저다** — 팀장 소유권 기준으로 좁힐 것인지, "소속 부서면 열람 가능"이
의도된 정책인지. 후자라면 민감 필드 마스킹을 검토한다.

기존 테스트가 **현재의 넓은 동작을 정답으로 고정**하고 있다(`LeaveHistoryServiceTest.java:96`) —
정책을 좁히면 테스트도 함께 고쳐야 한다.

## 1순위 수정 결과 (2026-08-06)

**I-1 · I-2 · I-4 · I-8을 한 번에 닫았다.** 네 결함의 원인이 하나였다 —
`advance_days`가 파생값인데 도메인 메서드 5개가 각자 이 필드를 더하고 뺐다.

### 무엇을 바꿨나

`User`에 파생값 재계산을 하나 두고, **이 메서드만 `advance_days`에 쓴다**:

```java
private void syncAdvanceDays() {
    // getRemainingDays() = base + bonus − use 이므로 negate() = use − base − bonus
    this.advanceDays = getRemainingDays().negate().max(BigDecimal.ZERO);
}
```

잔액 3필드를 바꾸는 메서드가 마지막에 이걸 호출한다 — **예외 없이 6곳 전부**:
`deductLeave` / `restoreLeave` / `addBonusDays` / `updateBaseDays` / `addMonthlyLeave` / `resetAnnualLeave`.

### 리셋도 재계산 대상이다 — docs/09 §5 정정

처음에는 `resetAnnualLeave`를 예외로 뒀다. docs/09 §5가 *"여기서 다시 `advance_days`를 쌓으면
정산이 재귀적으로 이어진다"* 고 명시했기 때문이다. **다년 검산 결과 그 서술이 틀렸다.**

핵심은 리셋이 `base`를 **덮어쓴다**는 것이다 — `base = newBase − advance`는 가감이 아니다.
따라서 음수 `base`(=남은 빚)는 다음 리셋에서 그냥 버려진다.

| 시나리오 | Y3 시작 잔여 | 항등식 정답 | 판정 |
|---|---:|---:|---|
| 리셋 예외, 이후 활동 없음 | 15 | 45−35 = 10 | **5일 과다 (빚 면제)** |
| 리셋 예외, 월차 1일 적립 | 11 | 46−35 = 11 | 정확 |
| 리셋도 재계산, 활동 없음 | 10 | 45−35 = 10 | 정확 |
| 리셋도 재계산, 월차 1일 | 11 | 46−35 = 11 | 정확 |

**같은 상태인데 무관한 후속 이벤트 유무로 결과가 갈린다** — 활동이 없으면 빚이 사라지고,
월차가 1일이라도 적립되면 그 재계산에 빚이 되살아난다. **I-1과 같은 종류의 경로 의존 결함이다.**

재귀도 없다. `advance`는 리셋마다 새 정책 연차만큼 줄어 단조 감소한다 (50 → 35 → 20 → 5 → 0, 4회 종료).
회귀 테스트 4건으로 고정했다 (`UserTest.resetAnnualLeave_*` — 단일 리셋 2건 + 다년 2건 + 대형 채무 종료 1건).

단, `carriedUse`가 들어오면 이 재계산만으로 부족하다 → **I-11**.

### 부수 정리

| 변경 | 이유 |
|---|---|
| `restoreLeave(days, advanceUsedDays)` → `restoreLeave(days)` | 복구가 스냅샷에 의존하지 않게 됐다. 2인자를 남기면 파생값을 다시 두 곳에서 쓰게 된다 |
| `resetAnnualLeave`도 재계산 호출 | 위 검산 — 빼면 빚이 면제된다 |
| `LeaveRequest.advanceUsedDays` → 감사 기록 전용 | 필드·컬럼은 유지(그 신청이 잔여를 얼마나 초과했는지 기록). 복구 계산에서는 빠짐 |
| docs/09 §4의 4단계(잔존 신청 스냅샷 0 재기록) 폐기 | 전제가 사라졌다 (I-4 소멸) |

호출부: `LeaveService` 3곳(반려 219 / 소급취소 승인 292 / 즉시 취소 314).

### 검증

- 신규: `UserTest` 15건(신설) + `LeaveServiceTest` 2건 + `UserServiceTest` 1건 + `WelfareServiceTest` 1건
- **역검증**: `syncAdvanceDays` 본문을 주석 처리하면 **13건이 실패**한다 — 테스트가 실제로 이 로직에
  의존함을 확인했다(통과가 우연이 아님). 확인 후 원복.
- T-2가 지적한 "2건 이상 비역순 복구"를 도메인·서비스 두 층에서 각각 고정했다.

### 기존 데이터 backfill (O-3와 같은 성격)

**코드만 고쳐도 이미 틀어진 DB 행은 자동으로 낫지 않는다.** 그 사원에게 잔액 변경이 한 번
일어나야 재계산이 걸린다. 손대지 않은 행은 다음 기산일까지 틀린 값을 들고 있다. 1회 실행:

```sql
UPDATE users
SET advance_days = GREATEST(0, use_days - base_days - COALESCE(bonus_days, 0));
```

`base_days`가 음수인 행(과다 당겨쓰기 정산 이력)도 이 식이 그대로 처리한다.

## 3순위 수정 결과 — 프론트엔드 실사용 결함 (2026-08-06)

**F-1·F-2·F-3·F-5·F-6을 한 라운드에 닫았다.** 가짜 데이터를 지우는 방식이 아니라
**DB에 실제 데이터를 만들어** 화면이 실 API를 그대로 타게 했다.

### F-2 — mock 대신 시연 데이터 시더

`frontend/src/mocks/data.js`에서 사원·연차·결재 이력 mock을 전부 삭제하고
`backend/.../config/DemoDataInitializer.java`를 새로 만들었다. 남은 mock은 공휴일 하나뿐이다
(`/api/holidays` 컨트롤러가 아직 없다).

왜 mock을 다른 이름으로 바꾸는 걸로 끝내지 않았나 — mock은 실 API·권한·페이징을 타지 않으므로
화면만 그럴듯해지고 검증되는 게 없다. 게다가 유명인 실명이 결재 이력에 감사 기록처럼 렌더됐다.

시더가 만드는 것: 부서 3 · 사원 8 · 연차 신청 8(PENDING·APPROVED·REJECTED·CANCELLED·CANCEL_PENDING
전부) · 복리후생 2 · 처리 이력.

| 안전장치 | 내용 |
|---|---|
| `@Profile("local")` | 운영·테스트 프로필에서는 **빈으로 등록조차 되지 않는다**. `@Import`로도 우회되지 않음 |
| 도메인 메서드만 사용 | 행을 직접 짜 넣지 않고 `deductLeave`/`restoreLeave`를 실제 흐름 순서로 호출 |
| 멱등 | 기준 계정이 있으면 전부 건너뜀 (재기동 안전) |
| 실명 금지 | 특정 인물을 연상시키지 않는 흔한 이름 조합만 |

`DemoDataInitializerTest` 4건으로 고정했다 — 그중 하나는 **시딩된 8명 전원의 잔액 불변식**
(`advance = max(0, use − base − bonus)`)을 검사한다. 시더가 값을 직접 넣으면 깨진 데이터 위에서
모든 화면 검증이 무의미해지기 때문이다. 다른 하나는 **local 프로필 밖에서 빈이 등록되지 않는지**를 고정한다.

### F-2(b) — "처리 완료" 탭을 실 API로

기존 주석("내가 처리한 결재 API가 없다")은 **맞았다.** `/leave-histories`는 전사,
`/my-team`은 **신청자 부서** 기준이라 남이 처리한 건도 섞인다. 그래서 엔드포인트를 새로 만들었다:

```
GET /api/leave-histories/my-actions     (action 필터, 최신순)
GET /api/welfare-histories/my-actions
```

actor가 본인인 이력만 나오므로 화면 의미와 정확히 일치하고, **부서 스코프 논쟁(S-6)과도 무관하다.**
역할 게이트를 두지 않았다 — 본인이 처리한 것만 보이므로 노출 위험이 없고, 일반 사원도 자기 신청을
취소한 이력을 갖는다.

기간 표시를 위해 `LeaveHistoryLogResponse`에 `dates`를 추가했다. 컬렉션이라 `@EntityGraph`에 넣으면
페이징이 메모리에서 처리되므로, `LeaveRequest.dates`에 **`@BatchSize(size = 50)`**를 걸어
배치 조회로 해결했다 (D-2에도 기여).

### F-1 — 쿼리 키 `size` (문서보다 심각했다)

9개 훅 전부에 `size`를 넣었다. **현재 재현되는 충돌이 2건 있었다**:

| 충돌 | 결과 |
|---|---|
| `Sidebar` `size:1` ↔ `ApprovalsPage` `size:50` (같은 키 `['leaves','pending',0]`) | 먼저 캐시된 응답이 재사용 → **결재 목록이 1건만 보일 수 있음** |
| `AdminDepartmentsPage` 팀장 후보 `size:200` ↔ `AdminMembersPage` `size:50` | **팀장 후보가 50명에서 잘림** (신규 발견) |

### F-6 — 실패를 빈 상태와 구분

`ErrorState` 컴포넌트를 만들고 `TableCard`에 `error`/`errorLabel`/`onRetry`를 추가했다.
**상태 우선순위는 loading → error → empty**다. 실패하면 목록이 빈 배열이라 empty 조건도 참이 되는데,
그때 "데이터가 없습니다"를 보여주면 결재 대기 건이 있는데도 놓친다.

무한 스피너였던 4곳(Dashboard·History·MyInfo·AdminPolicy 설정)은 `!data` 가드 앞에 `isError`
분기를 넣었다 — 그 가드만 있으면 실패해도 계속 "불러오는 중"이 표시된다.

### F-3 — 연차 취소 UI

`useCancelLeave` 훅을 만들고 사용 내역에 취소 버튼·확인 다이얼로그를 붙였다
(PENDING·APPROVED만 노출). 서버가 돌려주는 결과 상태로 안내를 갈랐다 —
`CANCEL_PENDING`이면 "결재자 승인 후 취소됩니다", `CANCELLED`면 즉시 취소.
즉시 취소된 것처럼 안내하면 사용자가 연차가 복구됐다고 오해한다.

### F-5 — invalidate

- 복리후생 승인이 `addBonusDays`로 **연차 잔액을 바꾸는데** `['leaves']`가 빠져 있었다 → 추가
- 퇴직 처리는 서버가 대기 결재를 이관하고 팀장을 해제하므로 `['leaves']`·`['welfare']`·`['departments']` 추가
- 연차·복리후생 상태 변경이 처리 이력 로그를 낡게 만드는 것도 함께 처리
- 관리자 연차 직접 설정 → `['leaves','summary']`
